# Модель угроз

Версия 1.0, этап 0. Метод: STRIDE. Пересматривается при добавлении компонента,
новой внешней интеграции или изменении границ доверия.

## Активы

- Трафик клиентов, проходящий через сенсор (пароли, токены, персональные данные).
- Доступность защищаемого приложения.
- Целостность конфигурации сенсоров.
- Журнал событий и профили атакующих.
- Секреты продукта: ключ подписи конфигурации, HMAC-ключи canary-токенов,
  токен Telegram-бота.
- Репутация продукта.

## Границы доверия

1. Интернет → сенсор. Весь вход враждебен.
2. Сенсор → control plane. Сенсор работает у клиента и может быть скомпрометирован.
3. Control plane → администратор (дашборд, Telegram).
4. CI/CD → артефакты (образы, релизы).

## Угрозы и меры

| # | Компонент | Угроза | STRIDE | Меры |
|---|---|---|---|---|
| T1 | Сенсор | Подделка X-Forwarded-For, чтобы заблокировать IP легитимных пользователей или партнёров | S, D | Доверять заголовку только от заданных прокси; блокировка по составному отпечатку; allowlist; ограниченный TTL блокировок |
| T2 | Сенсор | Межсайтовое срабатывание: страница атакующего заставляет браузер жертвы запросить приманку с её cookies, аккаунт жертвы замораживается | S, D | Учёт Sec-Fetch-Site; приманки высокой уверенности требуют CORS preflight (нестандартный заголовок или JSON); для аутентифицированных — реакция только по накопленному скорингу |
| T3 | Сенсор | Перегрузка сенсора для отключения защиты | D | Fail-open; лимиты памяти и соединений; таймауты; неблокирующая отправка событий; алерт при переходе в fail-open |
| T4 | Сенсор | Утечка паролей и персональных данных в логи и события | I | Только метаданные; запрет логирования тел и заголовков авторизации (правила Semgrep в CI); маскирование |
| T5 | Сенсор | Распознавание продукта по характерным ответам и обход приманок | I | Без баннеров и уникальных заголовков; рандомизация и ротация приманок; приманки в стиле стека клиента |
| T6 | Сенсор ↔ control plane | Взломанный control plane раздаёт вредоносную конфигурацию | T, E | Подпись конфигурации ключом вне сервера раздачи (KMS/офлайн); проверка подписи сенсором; mTLS |
| T7 | Сенсор | Подделка canary-токенов, чтобы вызвать ложные срабатывания на чужие сессии | S | HMAC-подпись токена; привязка к сессии выдачи; ротация ключей |
| T8 | Дашборд | XSS через данные атакующего (User-Agent, путь, параметры) | T, E | Экранирование вывода; строгий CSP; данные атакующего только как текст |
| T9 | Алерты | Подделка нажатий кнопок в Telegram | S, E | Проверка отправителя callback; подписанные одноразовые callback-данные с коротким сроком жизни |
| T10 | Администрирование | Невозможно доказать, кто выполнил действие (разбан, разморозка) | R | Журнал аудита только на добавление |
| T11 | Red-team валидатор | Использование продукта для атаки чужих ресурсов | E, D | Подтверждение владения доменом; лимиты скорости; аудит запусков; изолированная сеть |
| T12 | CI/CD | Подмена зависимости или GitHub Action | T | Actions по SHA; минимальные права GITHUB_TOKEN; lock-файлы; Dependabot; SBOM; подпись образов cosign |
| T13 | Хранилище | Избыточное хранение персональных данных (IP) | I | Минимизация; срок хранения по умолчанию 90 дней; удаление партициями |

## Принятые риски

- **R1.** В режиме fail-open обнаружение отключено. Принимаем ради доступности
  приложения клиента, компенсируем алертом о переходе в обход (T3).
- **R2.** При переполнении буфера события теряются. Принимаем, чтобы не замедлять
  приложение; потери учитываются счётчиком и видны в мониторинге.
- **R3.** Атакующий, который знает реальную уязвимость и идёт к ней напрямую,
  не касаясь приманок, обнаружен не будет. Продукт — слой обнаружения,
  а не замена WAF, пентеста и безопасной разработки.
