# Как вносить изменения

## Кто может вносить изменения

**Внешние pull request пока не принимаются.** В репозитории нет файла лицензии,
а значит, нет и условий, на которых чужой код может войти в коммерческий
продукт. Сначала будет выбрана лицензия и соглашение с контрибьюторами.

Нашли уязвимость — не открывайте issue, см. [SECURITY.md](SECURITY.md).

## Подготовка

Нужны Go 1.27, [uv](https://docs.astral.sh/uv/) и Docker.

```bash
make deps     # зависимости control plane строго по uv.lock
make hooks    # git-хуки: один раз на каждый клон репозитория
```

Хуки не включаются сами: git намеренно не запускает код из репозитория без
явного разрешения — иначе простое клонирование чужого репозитория запускало
бы чужой код на вашей машине.

**Что делают хуки:**

| Хук | Проверяет | Если инструмента нет |
|---|---|---|
| `pre-commit` | секреты в изменениях (gitleaks) | коммит блокируется: утёкший секрет не вернуть |
| `pre-commit` | форматирование изменённых файлов Go и Python | проверка пропускается: её повторит CI |
| `commit-msg` | формат сообщения коммита | проверка пропускается: её повторит CI |

Хуки — удобство, а не защита: `git commit --no-verify` их обходит.
Настоящая граница — CI и правила ветки `main`.

## Как устроена работа

1. **Одна задача — одна ветка — один PR.** Маленькие изменения, каждое с тестами.
2. **Перед PR:** `make lint`, `make test`, `make security`.
3. **Описание PR** — по шаблону: что делает изменение, почему так, где граница
   доверия, как проверено. Шаблон подставляется автоматически.
4. **Изменение модуля** обновляет [docs/guide.md](docs/guide.md) и
   [docs/roadmap.md](docs/roadmap.md) в том же PR.
5. **Слияние** — когда зелёный `ci-ok` и `CodeQL` и закрыты все обсуждения.
   Прямой push в `main` запрещён правилами ветки
   ([.github/rulesets/](.github/rulesets/README.md)).

Обязательные правила безопасности и запреты — в [CLAUDE.md](CLAUDE.md).

## Сообщения коммитов

Формат [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
тип(область): описание

Необязательное тело: что изменилось и, главное, почему.
```

| Тип | Когда |
|---|---|
| `feat` | новая возможность |
| `fix` | исправление ошибки, в том числе уязвимости |
| `docs` | только документация |
| `test` | только тесты |
| `refactor` | переделка без изменения поведения |
| `perf` | производительность |
| `build` | сборка, зависимости, образы |
| `ci` | CI и проверки |
| `chore` | прочее служебное |
| `style` | форматирование без изменения смысла |
| `revert` | откат |

Область — часть продукта строчными латинскими буквами: `sensor`, `controlplane`,
`deploy`, `deps`. Описание — на русском, с маленькой буквы, без точки в конце.
Первая строка — не длиннее 120 символов.

`!` после типа или области означает несовместимое изменение:
`feat(events)!: новый формат события касания приманки`.

Примеры:

```
fix(sensor): закрывать тело ответа при ошибке чтения
feat(controlplane): приём событий из NATS
docs: раздел о проверках безопасности в инструкции
build(deps): bump golang.org/x/net from 0.30.0 to 0.31.0 in /sensor
```

Формат проверяет хук `commit-msg` и задание `commits` в CI — для всех коммитов PR.

## Версии и changelog

Номер версии — по [семантическому версионированию](https://semver.org/lang/ru/):
`МАЖОРНАЯ.МИНОРНАЯ.ПАТЧ`. Пока мажорная версия 0, продукт считается
нестабильным: несовместимые изменения возможны в любой минорной версии.

Изменения, заметные пользователю продукта, записываются в раздел
«Не выпущено» файла [CHANGELOG.md](CHANGELOG.md) в том же PR.

## Обновления от Dependabot

Dependabot раз в неделю присылает PR с обновлениями зависимостей.
Что проверить перед слиянием:

- CI зелёный;
- для крупного обновления — что изменилось в новой версии (ссылка в описании PR);
- для GitHub Actions — что новый SHA указывает на коммит официального репозитория.

Слишком свежие версии Dependabot не предлагает — выдержка 7 дней
уже настроена ([ADR-0016](docs/adr/0016-security-scanning.md)).
