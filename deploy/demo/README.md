# Учебные цели

Намеренно уязвимые приложения, за которыми проверяется сенсор (ADR-0019).
Это **не** часть продукта: в его упаковку они не попадают никогда.

```
vulnbank/Dockerfile          свой образ VulnBank вместо штатного Dockerfile автора
vulnbank/requirements.in     зависимости VulnBank — копия из репозитория автора
vulnbank/requirements.txt    те же зависимости с хешами каждого файла
vulnbank/.dockerignore       в контекст сборки попадает только requirements.txt
```

Juice Shop собирать не нужно: автор публикует образ, он закреплён по digest
прямо в `deploy/compose/compose.yaml`.

## Запуск

```bash
make dev-demo        # Juice Shop за сенсором:  http://127.0.0.1:8080
make dev-vulnbank    # VulnBank за сенсором:    http://127.0.0.1:8081
make dev-down        # остановить всё
```

Напрямую, мимо сенсора, цели недоступны: у них нет портов на хосте.

## Почему не штатный запуск автора

В `docker-compose.yml` VulnBank база открыта в сеть с паролем `postgres`,
сервис autoheal получает `/var/run/docker.sock` (это root на хосте), образ
по тегу `latest`, всё от root. Сам Flask работает в режиме отладки —
это выполнение кода в контейнере, — и есть SSRF. Внутри контейнера это
допустимо: ради уязвимостей цель и берут. Наружу это выйти не должно
(угроза T16), поэтому:

| Что | Как |
|---|---|
| исходники | репозиторий автора по полному SHA коммита (правило C8) |
| зависимости | только готовые колёса, хеш каждого файла проверяется |
| базовый образ | по digest |
| процесс | не от root, файловая система только для чтения, загрузки — в памяти с пределом 16 МБ |
| сеть | своя, без выхода в интернет; не видит базу продукта, control plane, другую цель |
| база | своя, в памяти, без пароля — пароль в репозитории не был бы секретом |

## Обновление VulnBank

Dependabot за коммитами чужого репозитория не следит, поэтому вручную:

1. Посмотреть изменения у автора с текущего коммита:
   `https://github.com/Commando-X/vuln-bank/compare/<текущий SHA>...main`.
   Особое внимание — новым сетевым функциям (новые SSRF, обращения
   к внешним сервисам) и изменениям в `requirements.txt`.
2. Заменить SHA в `deploy/compose/compose.yaml` (`additional_contexts`)
   и в шапке `vulnbank/requirements.in`.
3. Если у автора изменился `requirements.txt` — перенести изменения
   в `vulnbank/requirements.in` и выполнить `make vulnbank-requirements`.
4. `make lint` (правило C8 проверит, что SHA полный),
   `make dev-vulnbank` и проверка руками: страница, вход, логи сенсора.
