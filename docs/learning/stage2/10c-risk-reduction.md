# Этап 2, шаг 10в. Снижение остаточных рисков наживок

> Снимок на момент шага: 2026-09-29. Решение — в
> [ADR-0029](../../adr/0029-lure-residual-risks.md). Текущее состояние —
> в [guide.md](../../guide.md), раздел «Сенсор».

## Что и зачем

После шага 10б остались четыре риска, и владелец спросил, можно ли их
уменьшить. Три закрываются небольшими правками:

| Риск | Что было | Что стало |
|---|---|---|
| Один атакующий выключает наживки у всех | бюджет памяти 32 МиБ общий, кто первый занял — того и память | один клиент — не больше 4 МиБ |
| По скрытой ссылке ходит предзагрузка браузера | касание неотличимо от действия человека | в событии `sec_fetch.purpose: prefetch` |
| `HEAD` выдаёт сенсор | `HEAD` не правился: другая длина, другой `ETag`, у `robots.txt` даже `404` против `200` | `HEAD` отвечает как `GET` |

Четвёртый — ссылка становится первым элементом `<body>` — требует другой
архитектуры правки и остаётся до этапа 8.

## Понятия

- **Доля клиента** — сколько памяти бюджета может занимать один адрес.
  См. [глоссарий](../../glossary.md).
- **Сеть /64 в IPv6** — первые 64 бита адреса. Провайдер выдаёт
  абоненту целую сеть /64: 18 квинтиллионов адресов. Считать такого
  клиента по полному адресу бессмысленно.
- **HEAD** — запрос «только заголовки»: сервер отвечает теми же
  заголовками, что на `GET`, но без тела. Инструменты разведки используют
  его, чтобы быстро узнать длину и тип ответа.
- **Sec-Purpose** — заголовок, который браузер ставит на запросы,
  сделанные заранее (предзагрузка), а не по действию человека.
- **Контекст запроса** (`context.Context`) — «карман» у запроса в Go,
  куда можно положить значение, чтобы оно доехало туда, где запрос
  обрабатывают дальше.

## Как это работает

```
запрос ─▶ Rewrite: адрес клиента (forwarded.Resolve)
            └─▶ lure.Prepare(in, out, клиент) ── out + клиент в контексте
                                                       │
                           ReverseProxy отправляет ◀───┘  (pr.Out после Rewrite)
                                                       │
ответ приложения (resp.Request = этот out) ─▶ lure.Modify
            ├─ clientOf(resp) — чей ответ
            ├─ lease(клиент, резерв): общий предел и доля клиента
            └─ HEAD? — те же заголовки, что получит GET, без чтения тела
```

## Разбор кода

### Доля клиента: `lease` и `set` в `lure/budget.go`

```go
func (b *memBudget) lease(client netip.Addr, n int64) *lease {
	b.mu.Lock()
	defer b.mu.Unlock()
	if b.used+n > editMemory || b.perClient[client]+n > clientMemory {
		return nil
	}
	if b.perClient == nil {
		b.perClient = make(map[netip.Addr]int64)
	}
	b.used += n
	b.perClient[client] += n
	return &lease{budget: b, client: client, n: n}
}
```

- `mu.Lock()` — две суммы (всего и по клиенту) проверяются и меняются
  вместе. На шаге 10б здесь было одно атомарное число без блокировки.
  С двумя числами атомарных операций мало: между проверкой одного
  и изменением другого вклинился бы соседний запрос.
- `b.perClient[client]` — чтение из карты по отсутствующему ключу в Go
  возвращает 0, поэтому новый клиент проверяется так же, как известный.
- `> editMemory || > clientMemory` — оба предела. Отказ — `nil`, ничего
  не занято.
- Блокировка короткая: несколько сложений на **правку тела**, то есть
  на страницу или `robots.txt`, а не на каждый запрос. Сколько она стоит
  под нагрузкой — покажет шаг 11.

```go
func (l *lease) set(n int64) {
	b := l.budget
	b.mu.Lock()
	defer b.mu.Unlock()
	d := n - l.n
	l.n = n
	b.used += d
	if b.perClient[l.client] += d; b.perClient[l.client] == 0 {
		delete(b.perClient, l.client)
	}
}
```

- `shrink(keep)` и `release()` — это `set(keep)` и `set(0)`. `d` — на сколько
  изменилось занятое правкой; на столько же меняются обе суммы.
- `l.n = n` — запоминается новое значение. Поэтому повторный `release`
  даёт `d = 0` и ничего не возвращает дважды (находка 1).
- Клиент с нулём удаляется из карты. Иначе карта росла бы с каждым новым
  адресом, и атакующий, перебирая адреса IPv6, раздул бы память сенсора.
  Теперь в ней не больше записей, чем ответов в пути.

### Кто клиент: `budgetKey`

```go
func budgetKey(a netip.Addr) netip.Addr {
	a = a.Unmap()
	if a.Is6() {
		p, _ := a.Prefix(64)
		return p.Addr()
	}
	return a
}
```

- `Unmap()` — `::ffff:192.0.2.1` (IPv4, записанный как IPv6) становится
  `192.0.2.1`. Иначе один и тот же клиент считался бы в двух долях.
- `Prefix(64)` — оставить первые 64 бита, остальные обнулить:
  `2001:db8::ffff:1:2:3` → `2001:db8::`. Все адреса абонента — одна доля.
- Нулевой адрес (клиент неизвестен) остаётся нулевым: все неизвестные
  клиенты делят одну долю. Это консервативно: неизвестных не бывает много,
  если прокси настроены правильно.

### Как адрес доходит до правки ответа: `Prepare` и `Rewrite`

```go
// proxy.go, Rewrite
client := o.Trust.Resolve(pr.In)
...
pr.Out = o.Lures.Prepare(pr.In, pr.Out, client.Addr)
```

```go
// lure.go
func (inj *Injector) Prepare(in, out *http.Request, client netip.Addr) *http.Request {
	...
	return withClient(out, client)
}

func withClient(out *http.Request, client netip.Addr) *http.Request {
	return out.WithContext(context.WithValue(out.Context(), clientKey{}, budgetKey(client)))
}
```

- Адрес клиента известен в `Rewrite` (там разбирается `X-Forwarded-For`
  от доверенных прокси), а память занимается в `Modify` — при ответе.
  Между ними — только запрос, который уходит приложению.
- `WithContext` возвращает **копию** запроса с новым контекстом. Поэтому
  `Prepare` возвращает запрос, а прокси кладёт его в `pr.Out`.
  `ReverseProxy` читает `pr.Out` после `Rewrite` и отправляет именно его.
  Это проверяет `TestLuresSeeClient`.
- `clientKey{}` — пустая структура как ключ. Ключ своего типа не совпадёт
  с ключом другого пакета, даже если у тех тоже «client».
- Ответ приложения хранит свой запрос в `resp.Request`, и `clientOf(resp)`
  достаёт адрес оттуда.
- Для `POST`, `PUT`, `DELETE` ответы не правятся, и `Prepare` возвращает
  запрос без нового контекста — без лишнего выделения памяти на каждый
  запрос.

### HEAD страницы: `headLikeGet` в `lure/html.go`

```go
case ok && resp.Request.Method == http.MethodHead:
	headLikeGet(resp, int64(len(p.HTMLFragment())))
case ok:
	inj.injectHTML(resp, p.HTMLFragment(), &e)
```

- Ответ на `HEAD` проходит те же проверки, что `GET` (`htmlEligible`):
  `200`, `text/html`, без сжатия, не файл на скачивание.
- `headLikeGet` — та же функция, что правит заголовки `GET` после вставки:
  длина плюс длина вставки, слабый `ETag`, без сводок содержимого. Одна
  функция на оба случая, чтобы заголовки не разошлись после будущей
  правки.
- Тело не читается — его у `HEAD` нет, и `<body>` не ищется. Поэтому
  у страницы без `<body>` `HEAD` покажет длину со вставкой, а `GET`
  отдаст страницу без неё. Это единственное оставшееся расхождение, и оно
  только у страниц, где наживки нет.

### HEAD robots.txt и новый разделитель

```go
if resp.Request.Method == http.MethodHead {
	if resp.ContentLength >= 0 && resp.ContentLength <= maxRobotsBytes {
		resp.ContentLength = robotsLength(resp.ContentLength, paths)
		resp.Header.Set("Content-Length", strconv.FormatInt(resp.ContentLength, 10))
		...
	}
	return
}
```

```go
func robotsLength(appLength int64, paths []string) int64 {
	n := appLength + int64(len(robotsGroup(paths)))
	if appLength > 0 {
		n += int64(len(robotsSeparator))
	}
	return n
}
```

- Чтобы узнать длину дополненного `robots.txt`, не видя файла, длина
  должна зависеть только от длины файла. На шаге 10а сенсор добавлял
  один или два перевода строки — смотря чем кончается файл. `HEAD`
  последнего байта не знает.
- Поэтому разделитель теперь всегда `"\n\n"`. Если файл кончался
  переводом строки, получается лишняя пустая строка. RFC 9309 это
  допускает.
- Длина неизвестна (`-1`) или больше предела — `HEAD` как есть, и `GET`
  в этом случае тоже уходит как есть (для большого файла).
- `404` у приложения: `GET` получает `robots.txt` сенсора, `HEAD` — те же
  код `200`, заголовки и длину, а тело `http.NoBody`.

### Sec-Purpose: `fetchFrom` в `event/event.go`

```go
fetchPurposes = map[string]bool{
	"prefetch": true, "prefetch;prerender": true, "prefetch;anonymous-client-ip": true,
}
...
Purpose: fetchValue(h.Get("Sec-Purpose"), fetchPurposes),
```

- Та же схема, что у `Sec-Fetch-*`: значение из белого списка
  записывается как есть, любое другое — `other`. Строка от клиента
  в событие не попадает: `prefetch; evil="<x>"` станет `other`.
- Касание не отменяется. Инструмент атакующего может прислать
  `Sec-Purpose: prefetch` сам. Решать, шум это или атака, будет
  классификация на этапе 4 — поле даёт ей данные.

## Находки

1. **Метрика скрыла двойной возврат памяти.** Мутация «повторный release
   возвращает дважды» выжила. Счётчик уходил в минус, а тесты смотрели
   на `EditMemory()`, которая для метрики показывает минус как 0. Тесты
   переведены на сырой счётчик (`memUsed`), мутация поймана.
2. **Проверка `POST` проходила бы при любом коде.** Новая проверка
   в тесте сначала попала на заглушку в режиме частичного обнаружения.
   В нём `Prepare` возвращает запрос сразу, и тест прошёл бы, даже если бы
   проверки метода не было. Тест исправлен и подтверждён мутацией.
3. **Старые тесты закрепляли старое поведение.** Два теста проверяли,
   что `HEAD` не правится. Это было верно для шага 10б и стало неверно
   теперь. Тесты изменены: вместо `HEAD` — методы, которые действительно
   не правятся (`PUT`, `POST`). Сам `HEAD` проверяют новые тесты.
4. **На стенде `HEAD` и `GET` расходились сильнее, чем в тестах.**
   У VulnBank нет `robots.txt`: `GET` получал `200` от сенсора, `HEAD` —
   `404` от приложения. Теперь оба `200`, длина 38.

## Граница доверия

- **Адрес клиента.** Берётся после разбора доверенных прокси (ADR-0022):
  `X-Forwarded-For` от недоверенного соединения не читается. Подделать
  адрес и занять чужую долю атакующий не может. Может только взять
  больше адресов — это и есть остаточный риск.
- **Заголовок `Sec-Purpose`** — строка от клиента, только сравнивается
  со списком.
- **Ответ приложения на `HEAD`.** `Content-Length` — число, которое прислало
  приложение; оно только проверяется на предел и складывается.
  Переполнения нет: предел 512 КиБ.

## Что может пойти не так

- **T3.** Атакующий с восемью и больше адресами всё ещё может занять
  бюджет. Для обычных страниц ему для этого нужно больше соединений,
  чем общий предел сенсора. Лимит соединений на адрес — этап 10.
- **Пользователи за одним NAT** делят долю: два одновременных разбора
  страниц на адрес. Лишние пропуски видны в метрике `memory`.
- **T5.** Страницы без сжатия — решение по замеру в шаге 11.
- **Ссылка — первый элемент `<body>`** — этап 8.

## Вопросы для самопроверки

1. Почему долю считают по адресу после разбора доверенных прокси,
   а не по адресу соединения?

   <details><summary>Ответ</summary>

   За CDN или балансировщиком все соединения приходят с нескольких
   адресов CDN. Доля по адресу соединения была бы общей на всех
   посетителей сайта, и один атакующий по-прежнему выключал бы наживки
   у всех. Адрес после разбора доверенных прокси — настоящий адрес
   посетителя. Подделать его атакующий не может: `X-Forwarded-For`
   читается только от прокси из `SENSOR_TRUSTED_PROXIES`.

   </details>

2. Почему у IPv6 доля считается по сети /64, а не по адресу?

   <details><summary>Ответ</summary>

   Абонент получает от провайдера целую сеть /64 — 2⁶⁴ адресов — и может
   отправлять запросы с любого из них. По полному адресу у одного
   атакующего было бы сколько угодно «клиентов», и доля ничего бы
   не ограничивала.

   </details>

3. Как адрес клиента попадает из `Rewrite`, где он известен, в `Modify`,
   где занимается память? Почему `Prepare` теперь возвращает запрос?

   <details><summary>Ответ</summary>

   `Prepare` кладёт адрес в контекст исходящего запроса. `WithContext`
   в Go создаёт копию запроса, а не меняет исходный, поэтому `Prepare`
   возвращает копию, а прокси записывает её в `pr.Out`. `ReverseProxy`
   отправляет приложению именно `pr.Out`, а ответ приложения ссылается
   на свой запрос в `resp.Request`. Из его контекста `Modify` и достаёт
   адрес.

   </details>

4. Чем ответ на `HEAD` выдавал сенсор и почему пришлось изменить формат
   дополненного `robots.txt`?

   <details><summary>Ответ</summary>

   `GET` страницы получал вставку, а `HEAD` — нет, поэтому длина и `ETag`
   расходились. У сайта без `robots.txt` `GET` получал `200` от сенсора,
   а `HEAD` — `404` от приложения. Сравнив два запроса, атакующий понял
   бы, что ответы кто-то правит, и стал бы осторожнее с «находками».
   Длину дополненного `robots.txt` на `HEAD` нужно знать без тела, а раньше
   она зависела от последнего байта файла. Теперь разделитель всегда
   одинаковый, и длина зависит только от длины файла.

   </details>

5. Почему касание с `Sec-Purpose: prefetch` записывается, а не отменяется?

   <details><summary>Ответ</summary>

   Заголовок может прислать не только браузер, но и инструмент атакующего.
   Код продукта публичен, так что правило «с этим заголовком касание
   не считается» стало бы известным способом обойти ловушку. Поле
   в событии даёт классификации на этапе 4 данные, а решение —
   шум или атака — она примет по совокупности признаков.

   </details>
