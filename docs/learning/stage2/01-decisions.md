# Этап 2, шаг 1. Решения этапа

> Снимок на момент шага: 2026-09-23. Решения — в ADR-0018 и ADR-0019,
> план этапа — в [roadmap.md](../../roadmap.md).

## Что и зачем

В этом шаге нет кода. Здесь записаны решения, от которых зависит, как будет
написан весь этап 2. Сделать это до кода нужно по простой причине:
решение «приманки настраиваются из веб-интерфейса» меняет устройство
сенсора уже сейчас, хотя сам интерфейс появится только на этапе 5.
Если писать приманки как код, а интерфейс добавить потом, приманки
пришлось бы переписывать.

Три решения шага:

1. Настройка сенсора и собственные правила — из веб-интерфейса, но
   с ограничениями (ADR-0018).
2. Вторая учебная цель — VulnBank, в изоляции (ADR-0019).
3. Технические решения этапа 2 — в [roadmap.md](../../roadmap.md).

## Понятия

- **Слой запуска (bootstrap)** — настройки, без которых сенсор не может
  начать работу: где слушать, куда проксировать, где control plane,
  чьей подписи верить.
- **Политика обнаружения** — что сенсор ищет: какие приманки включены,
  какие у них пути и тексты, какие собственные правила добавил администратор.
- **Наживка и ловушка.** Наживка — то, что атакующий видит (комментарий
  в HTML, строка в robots.txt, заголовок). Ловушка — место, где касание
  фиксируется (запрос на путь из наживки). Легитимный пользователь
  наживку не видит и в ловушку не приходит.
- **Режим наблюдения** — правило включено, но только записывает
  «сработало бы», не вмешиваясь в запрос.
- **SSRF** — уязвимость, при которой атакующий заставляет сервер сделать
  запрос по выбранному им адресу, в том числе во внутреннюю сеть,
  куда у самого атакующего доступа нет.

## Как это работает

### Два слоя конфигурации

```
 администратор                          тот, кто разворачивает
 в веб-интерфейсе                       (Helm, compose, переменные)
       │                                          │
       ▼                                          ▼
 ┌─────────────────┐   подпись вне    ┌────────────────────────┐
 │    политика     │── control plane ─▶        сенсор          │
 │ приманки,       │   (этап 3)       │  слой запуска:         │
 │ свои правила,   │                  │  куда проксировать,    │
 │ режим наблюдения│                  │  доверенные прокси,    │
 └─────────────────┘                  │  ключи проверки подписи│
                                      └────────────────────────┘
```

Граница между слоями проведена по одному вопросу: **что сможет сделать
тот, кто взломал control plane, если изменит этот параметр?**

| Параметр | Если его подменить | Где живёт |
|---|---|---|
| адрес защищаемого приложения | весь трафик клиента с паролями уходит на сервер атакующего | слой запуска |
| доверенные прокси | атакующий объявляет доверенным весь интернет и подделывает IP (T1) | слой запуска |
| ключ проверки подписи | подпись перестаёт что-либо значить | слой запуска |
| путь и текст приманки | обнаружение хуже, но трафик цел, а текст экранируется | политика |
| собственное правило | ложные срабатывания, но пути проверяются, а новое правило можно держать в режиме наблюдения | политика |

### Почему ключ подписи не в control plane

Сравним два варианта при одной атаке: control plane взломан.

| | Подписывает control plane | Подписывает администратор своим ключом |
|---|---|---|
| Атакующий выпускает политику | подписана, сенсоры применяют | без подписи администратора сенсоры отвергают |
| Что даёт подпись | только «выпущено control plane» | «одобрено человеком, у которого ключ» |

Подпись полезна, только если ключ находится **не там**, где угроза.
Какой именно будет механизм — аппаратный ключ или passkey администратора,
либо отдельная утилита — решим на этапе 3.

### Почему правила — данные, а не скрипты

Сенсор стоит в пути каждого запроса к приложению клиента. Скрипт в правиле —
это код, который исполняется на каждом запросе. Одна бесконечная петля
в правиле — и сенсор уходит в fail-open. Одна уязвимость в движке
скриптов — и атакующий исполняет код на сенсоре. Поэтому правило — это
заполненная форма из фиксированного набора полей, а не программа.

### Почему наживки только из шаблонов

Наживка вставляется в HTML **каждой** страницы сайта клиента. Если бы
в неё можно было вписать произвольный HTML, строка `<script>…</script>`
в политике означала бы хранимый XSS для всех пользователей сайта сразу.
Поэтому администратор задаёт только текст, а сенсор вставляет его
в заранее известное место шаблона и экранирует.

### Изоляция учебных целей

VulnBank и Juice Shop намеренно уязвимы. В VulnBank, например, Flask
запущен в режиме отладки — это исполнение кода в контейнере, — и есть
SSRF через загрузку картинки по URL. Значит, исходим из того, что
контейнер цели будет взломан, и ограничиваем, куда из него можно попасть.
План сетей (уточнится на шагах 3 и 4):

```
                 хост: 127.0.0.1
           ┌──────────┴───────────┐
           ▼                      ▼
   ┌──────────────── сеть edge ───────────────┐
   │  сенсор-juice            сенсор-vulnbank  │
   └─────┬──────────────────────────┬─────────┘
         │                          │
 ┌───────┴── demo-juice ──┐  ┌──────┴──── demo-vulnbank ──────┐
 │ (без интернета)        │  │ (без интернета)                │
 │ сенсор-juice           │  │ сенсор-vulnbank                │
 │ juice-shop             │  │ vulnbank    база vulnbank      │
 └────────────────────────┘  └────────────────────────────────┘
```

Из взломанной цели видно только её саму, её базу и вход сенсора.
Не видно: интернета, облачных метаданных, сети `backend` с нашими базой
и очередью, другой цели.

## Граница доверия

Этот шаг добавляет в модель новый источник данных — **политику**.
Она приходит от администратора, но:

- администратор может ошибиться (ловушка на `/login` сломает вход на сайт);
- сессию администратора могут украсть;
- control plane могут взломать.

Поэтому сенсор относится к политике как к полу-доверенному входу:
проверяет её сам, ограничивает, что она в принципе может выразить,
и при ошибке остаётся на последней валидной версии.

## Что может пойти не так

- **T15** — вредоносная или ошибочная политика. Меры: правила — данные,
  шаблоны с экранированием, проверка путей и размеров, RE2, режим
  наблюдения, сенсор — последний судья, аудит и откат.
- **T16** — взлом учебной цели и выход за её пределы. Меры: изолированные
  сети без интернета, свой Dockerfile без root и без доступа к Docker,
  отдельная база, только профили demo.
- **T6** уточнена: веб-интерфейс готовит политику, но не подписывает.

Остающийся риск: до этапа 6 алерт о переходе сенсора в fail-open
записывается, но никому не доставляется. Записан в технический долг.

## Как это проверено

Кода нет — проверка через ревью документов. На следующих шагах
каждое ограничение из ADR-0018 получит тест: например, политика
с `<script>` в тексте наживки должна отвергаться сенсором, а тест —
падать, если проверку убрать.

## Вопросы для самопроверки

1. Почему адрес защищаемого приложения нельзя менять из веб-интерфейса,
   хотя это было бы удобно?

   <details><summary>Ответ</summary>

   Потому что взломавший control plane или укравший сессию администратора
   поменял бы его на свой сервер, и весь трафик клиента — с паролями
   и cookie — пошёл бы атакующему. Параметры, которые определяют границы
   доверия, живут в слое запуска и меняются только при развёртывании.

   </details>

2. Control plane подписывает политику своим ключом. Что не так?

   <details><summary>Ответ</summary>

   Угроза T6 — как раз взлом control plane. Взломавший его получает
   и ключ, и может подписать любую политику. Подпись защищает, только если
   ключ хранится вне того места, откуда исходит угроза.

   </details>

3. Администратор хочет добавить правило «на любой путь, содержащий `admin`,
   отвечать фейковой страницей». Какие два механизма ADR-0018 здесь
   сработают и зачем?

   <details><summary>Ответ</summary>

   Проверка путей: слишком широкое правило перехватит настоящие страницы
   приложения (например, `/rest/admin/application-configuration`, который
   Juice Shop запрашивает при загрузке каждой страницы), и сенсор должен
   его отвергнуть или хотя бы явно предупредить. Режим наблюдения: даже
   допустимое правило сначала включается так, чтобы только записывать
   «сработало бы», — по реальному трафику видно, не ловит ли оно
   легитимных пользователей.

   </details>

4. Зачем прятать учебную цель в сеть без выхода в интернет, если она
   и так запущена только на вашей машине?

   <details><summary>Ответ</summary>

   Цель уязвима к SSRF и исполнению кода. Из неё можно обратиться
   к облачным метаданным (если стенд на облачной машине — это кража
   её учётных данных), к нашим базе и очереди, к сервисам вашей домашней
   или рабочей сети, скачать инструменты атакующего. Изоляция ограничивает
   ущерб от взлома самой цели, а не от доступа к ней.

   </details>

5. Почему скрытые поля форм перенесены на этап 8, хотя в VulnBank
   есть формы, на которых их можно проверить?

   <details><summary>Ответ</summary>

   Проверить есть на чём, но остаются две проблемы. Лишнее поле доходит
   до настоящего приложения и может сломать строгую проверку входных данных —
   тогда пострадают легитимные пользователи. А чтобы заметить подмену поля,
   сенсору пришлось бы читать тела всех POST-запросов, то есть больше
   данных атакующего в парсере и больше задержка. Cookie-приманка ловит
   тот же класс атак без этих проблем.

   </details>
