# Этап 2, шаг 7. Fail-open

> Снимок на момент шага: 2026-09-24. Решение — в
> [ADR-0024](../../adr/0024-fail-open.md). Текущее состояние —
> в [guide.md](../../guide.md), раздел «Сенсор».

## Что и зачем

С шага 8 на каждом запросе будет работать обнаружение: сравнение
с приманками, потом правила администратора. Это код, и он может упасть
на неожиданном вводе. Это работа, и под нагрузкой она может стать
медленной. Сенсор стоит в пути трафика: его сбой — сбой сайта клиента.

Шаг 7 ставит для обнаружения защитную оболочку — `Guard` — до того, как
появится само обнаружение. Приманки на шаге 8 встанут внутрь готовой
защиты.

Главный вопрос шага — не «как пропустить трафик при сбое», а «как
не дать атакующему этим воспользоваться». Если сбой обнаружения
выключает его для всех, атакующий найдёт сбой и выключит защиту.

## Понятия

- **Fail-open** — при собственном сбое пропускать трафик, а не блокировать.
- **Паника и `recover`** — аварийная остановка в Go и её перехват.
- **Гистерезис** — разные пороги входа и выхода, чтобы не переключаться
  туда-обратно.
- **Выборка** — проверять каждый N-й запрос, а не все.
- **Circuit breaker** — шаблон «при сбоях временно отключить»; у нас
  его вариант с выборкой вместо отключения.

Все — в [глоссарии](../../glossary.md).

## Как это работает

```
запрос ─► rejectConnect ─► сроки простоя ─► Guard ─► ReverseProxy ─► приложение
          (защита:           (защита:          │
           всегда)            всегда)          ├─ обычный режим: проверить каждый
                                               ├─ частичный режим: каждый 10-й
                                               │
                                               └─ Detector.Inspect(...)
                                                    ├─ ответил сам (ловушка) → стоп
                                                    ├─ не ответил → дальше в прокси
                                                    └─ паника → дальше в прокси
                                                               + detection.panic
```

Два сбоя — два разных ответа:

| Сбой | Что происходит | Общий режим |
|---|---|---|
| паника на запросе | этот запрос — в приложение без проверки; событие с адресом клиента | не меняется |
| проверки стали медленными | проверяется каждый 10-й запрос; событие critical | частичный, с гистерезисом |

## Разбор кода

### Где стоит Guard: `newHandler` в `proxy/proxy.go`

```go
return rejectConnect(o, withIOIdleDeadlines(o.Guard.Handler(rp), idle))
```

Читается изнутри наружу: `rp` (прокси) обёрнут в `Guard`, тот — в сроки
простоя, тот — в `rejectConnect`. Запрос проходит в обратном порядке:
сначала `rejectConnect`, последним — прокси.

Этот порядок и есть главное решение шага. Защита (`rejectConnect`, чистка
заголовков внутри `rp`) стоит **вне** `Guard`, поэтому никакой режим
fail-open её не выключает. Тест `TestFailOpenKeepsProtections` ставит
обнаружение, которое падает на каждом запросе, и проверяет: сайт
работает, `CONNECT` по-прежнему 405, `X-Real-IP` по-прежнему вычищен.
Если поменять порядок — поставить `Guard` снаружи, — тест падает.

### Паника: `inspect` в `failopen/guard.go`

```go
start := g.cfg.Now()
defer func() {
	p := recover()
	if p == nil {
		return
	}
```

`defer` выполняется при выходе из функции — и при обычном возврате,
и при панике. `recover()` внутри него возвращает значение паники или
`nil`, если паники не было. Паника перехвачена — дальше функция решает,
что с ней делать.

```go
	if err, ok := p.(error); ok && errors.Is(err, http.ErrAbortHandler) {
		panic(p)
	}
```

`http.ErrAbortHandler` — это не сбой, а способ, которым обработчик
намеренно обрывает соединение. Его пропускаем дальше: сервер Go знает,
что с ним делать.

```go
	handled, panicked = false, true
	g.onPanic(r, p)
}()

handled = g.cfg.Detector.Inspect(w, r)
```

После паники функция возвращает «не обработано, была паника», и запрос
идёт в прокси. `handled` и `panicked` — именованные результаты функции:
`defer` может менять их после паники, и именно эти значения получит
вызывающий.

Обратите внимание: при панике время проверки **не записывается** в окно
режима. Паники не влияют на общий режим — это решение, а не упущение.

### Что записывается о панике: `onPanic`

```go
ev := event.New(event.TypeDetectionPanic, event.SeverityHigh)
ev.Client = event.ClientFrom(g.cfg.Trust.Resolve(r))
ev.Request = event.RequestFrom(r)
ev.Data = map[string]string{"panic_type": fmt.Sprintf("%T", p)}
```

Паника на чужом вводе — это, возможно, кто-то ищет уязвимость в самом
сенсоре. Поэтому событие с адресом клиента и метаданными запроса (через
те же `ClientFrom` и `RequestFrom`, что и у других событий, — с маскированием
пути).

`%T` — тип значения паники (например, `runtime.boundsError`), а не само
значение. В значении могли бы оказаться данные запроса: паника
с сообщением «неожиданный путь /reset/токен» записала бы токен.

```go
now := g.cfg.Now().Unix()
last := g.lastPanicLog.Load()
if now-last < int64(panicLogInterval/time.Second) || !g.lastPanicLog.CompareAndSwap(last, now) {
	return
}
g.cfg.Logger.Error("паника в обнаружении: ...",
	slog.String("panic_type", fmt.Sprintf("%T", p)),
	slog.String("stack", string(debug.Stack())))
```

Стек — в лог, но не чаще раза в минуту. `CompareAndSwap` — атомарная
операция «запиши новое значение, только если там всё ещё старое»: из сотни
горутин, одновременно поймавших панику, в лог напишет ровно одна.
Стек — это имена функций и номера строк, без данных запроса. Без
ограничения частоты атакующий, нашедший вызывающий панику запрос,
заполнял бы диск логами.

### Когда пропустить нельзя: `Handler`

```go
tw := &trackedWriter{ResponseWriter: w}
origBody := r.Body
var tb *trackedBody
if r.Body != nil && r.Body != http.NoBody {
	tb = &trackedBody{ReadCloser: r.Body}
	r.Body = tb
}
```

На время проверки ответ и тело оборачиваются «следилками»: они
запоминают, начал ли `Detector` писать ответ и читал ли тело.

```go
handled, panicked := g.inspect(tw, r)
r.Body = origBody
```

Сразу после проверки — исходное тело обратно. Это важно для прозрачности:
если бы запрос без тела (`http.NoBody`) ушёл в прокси обёрнутым, прокси
решил бы, что тело есть, и отправил бы GET с пустым телом по частям.
Тест `TestBodyRestored`.

```go
if panicked && (tw.wrote.Load() || (tb != nil && tb.read.Load())) {
	g.Stats.Aborted.Add(1)
	panic(http.ErrAbortHandler)
}
next.ServeHTTP(w, r)
```

Два случая, когда пропустить запрос в приложение **нельзя**:

- `Detector` начал ответ и упал. Клиент уже получил начало ответа ловушки,
  а следом получил бы ответ приложения — два ответа в одном;
- `Detector` прочитал часть тела и упал. Приложение получило бы тело
  без начала: форму входа без логина, JSON без открывающей скобки.

Тогда соединение обрывается. Это единственный случай «fail-closed»
для одного запроса, и его можно избежать договором: сначала решить,
потом писать; тело не читать без необходимости. Договор записан
в комментарии к `Detector` для шага 8.

### Перегрузка: `record` в `failopen/mode.go`

```go
c.win.add(now, slow)

if c.degraded.Load() {
	return c.maybeRecover(now)
}
inspected, slowN := c.win.sum(now, enterWindow)
if inspected >= enterMinInspected && slowN*100 >= inspected*enterSlowPercent {
	c.degraded.Store(true)
	...
}
```

Окно — кольцо из 30 корзин по секунде. Каждая корзина хранит число
проверок и медленных за свою секунду. Память постоянная, сколько бы ни было
запросов.

Проверка входа: за последние 10 с не меньше 50 проверок и не меньше 10%
медленных. Сравнение — умножением, а не делением: `slow*100 >= inspected*10`
вместо `slow/inspected >= 0.1`. Так нет ни дробей, ни деления на ноль.

Минимум в 50 проверок нужен, чтобы тихой ночью два медленных запроса
из трёх не переключали режим.

### Выход и гистерезис: `maybeRecover`

```go
if !c.degraded.Load() || now.Sub(c.since) < minDegraded {
	return nil
}
inspected, slow := c.win.sum(now, exitWindow)
if inspected > 0 && slow*100 >= inspected*exitSlowPercent {
	return nil
}
c.degraded.Store(false)
```

Выход — при трёх условиях: прошло не меньше 30 с, за последние 30 с
медленных меньше 1%, либо проверок не было вовсе (нет трафика — нет
и нагрузки). Порог выхода в 10 раз строже порога входа. Если медленных
от 1% до 10%, режим не меняется ни в какую сторону — это и есть гистерезис.

`maybeRecover` вызывается и из `shouldInspect`, то есть на каждом запросе
в частичном режиме. Иначе при слабом трафике выход ждал бы, пока
наберутся проверки.

### Выборка: `shouldInspect`

```go
if !c.degraded.Load() {
	return true, nil
}
...
return c.sample.Add(1)%SampleEvery == 0, nil
```

В обычном режиме — сразу «проверять», без блокировки: `degraded`
атомарный, его чтение не ждёт чужих. В частичном — атомарный счётчик
запросов, проверяется каждый десятый. Не «ноль» — это важно: сканер,
перебирающий приманки, всё равно попадётся, а выборка заодно показывает,
прошла ли перегрузка.

### Приоритетная очередь: `Emit` и `run` в `event/recorder.go`

```go
q := r.queue
if isPriority(ev.Type) {
	q = r.prio
}
```

```go
func isPriority(t Type) bool {
	return strings.HasPrefix(string(t), "sensor.")
}
```

События о состоянии сенсора идут в свою очередь на 64 места. Решает тип,
а не важность. Тип — константа из кода, и события, которые вызывает
атакующий (`request.*`, `detection.*`, будущие касания приманок), туда
не попадут никогда. Иначе атакующий снова мог бы вытеснить событие
о fail-open своим потоком.

```go
select {
case ev := <-r.prio:
	r.write(ev)
	r.flushIfIdle()
	continue
default:
}
select {
case ev := <-r.prio:
case ev := <-r.queue:
case <-r.stop:
}
```

Почему два `select`. Когда готовы несколько веток, `select` выбирает
**случайную**. Один общий `select` не дал бы приоритета. Поэтому сначала
отдельная неблокирующая проверка приоритетной очереди, и только потом
общее ожидание.

### Паника в записи событий: `write`

```go
defer func() {
	if p := recover(); p != nil {
		r.Stats.DroppedWriteError.Add(1)
		r.sinkError(fmt.Errorf("паника при записи события: %T", p))
	}
}()
```

Горутина записи событий — не обработчик запроса. Её панику сервер Go
не перехватит, и упадёт весь процесс, а с ним и сайт клиента. До шага 7
так и было бы. Теперь паника на одном событии — это одно потерянное
и учтённое событие.

## Граница доверия

| Данные | Откуда | Что с ними делается |
|---|---|---|
| ввод, вызывающий панику в обнаружении | атакующий | запрос — в приложение; событие с адресом клиента; значение паники не записывается |
| число медленных проверок | атакующий может влиять нагрузкой | частичное обнаружение, а не полное отключение; выход с гистерезисом |
| поток событий об атаке | атакующий | не вытесняет события о состоянии сенсора: у них своя очередь |
| защита (CONNECT, заголовки, адрес приложения) | — | вне Guard; fail-open её не касается |

## Что может пойти не так

- **T3 — атакующий выключает обнаружение перегрузкой.** Частично: под
  перегрузкой проверяется каждый 10-й запрос. Остаётся принятый риск R1,
  теперь уточнённый — частичное обнаружение, а не отключённое.
  Каждый переход — событие critical.
- **T3 — атакующий нашёл запрос, вызывающий панику.** Он скрывает только
  этот запрос, и каждый такой запрос записан с его адресом. Общий режим
  не меняется.
- **T15 — ошибочная политика (шаг 8).** Падающее правило — fail-open
  для каждого запроса по отдельности. Медленное — частичный режим.
- **Падение процесса целиком** (нехватка памяти, фатальная ошибка среды Go)
  fail-open внутри процесса не покрывает. От этого защищают перезапуск
  контейнера и балансировщик, уводящий трафик с неготового сенсора
  (этап 10).
- **Блокировка в контроллере режима** при очень большом числе запросов
  и ядер может стать узким местом. Замер — на шаге 11.

## Как это проверено

- **Паника.** `TestPanicPassesRequestThrough` — 100 запросов с падающим
  обнаружением доходят до приложения с телом. 100 событий
  `detection.panic` с адресом клиента и замаскированным путём. Общий
  режим не изменился, стек в логе — один раз.
- **Когда пропустить нельзя.** `TestPanicAfterResponseStartedAborts`
  и `TestPanicAfterBodyReadAborts` — соединение оборвано, приложение
  не вызвано.
- **Прозрачность.** `TestBodyRestored` — после проверки у запроса исходное
  тело, `NoBody` остаётся `NoBody`.
- **Перегрузка.** `TestOverloadDegradesAndRecovers` — часы подменены,
  «медленная» проверка сдвигает их на 10 мс. 50 медленных — частичный
  режим, событие critical, строка ERROR. В режиме проверяется ровно 10
  из 100 запросов, приложение получает все 100. Проверки снова быстрые —
  режим снят с событием о восстановлении.
- **Гистерезис.** `TestHysteresis` — две минуты с 5% медленных режим
  не снимают. `TestNoEarlyRecovery` — 29 секунд мало. `TestEnterAtThreshold`,
  `TestEnterNeedsMinimumSample` — границы входа.
- **Защита не отключается.** `TestFailOpenKeepsProtections` — сквозной тест
  через настоящий сенсор.
- **Очередь событий.** `TestPriorityEventSurvivesFlood` — запись зависла,
  10 000 событий об атаке, а событие о fail-open записано.
  `TestWritePanicDoesNotCrash` — паника в записи одного события,
  остальные записаны.

Мутационная проверка — 12 поломок, каждую поймал тест:

| Поломка | Какой тест упал |
|---|---|
| не перехватывать панику | `TestPanicAfterBodyReadAborts` — паника дошла до теста |
| паника меняет общий режим | `TestPanicPassesRequestThrough` |
| пропускать в приложение после начатого ответа | `TestPanicAfterResponseStartedAborts` |
| пропускать в приложение после чтения тела | `TestPanicAfterBodyReadAborts` |
| не возвращать исходное тело | `TestBodyRestored` |
| переход не critical | `TestOverloadDegradesAndRecovers` |
| порог выхода равен порогу входа (без гистерезиса) | `TestHysteresis` |
| без минимального срока в режиме | `TestNoEarlyRecovery` |
| в частичном режиме не проверять ничего | `TestSampling`, `TestOverloadDegradesAndRecovers` |
| без приоритетной очереди | `TestPriorityEventSurvivesFlood`, `TestPriorityWrittenFirst` |
| паника в записи событий роняет процесс | `TestWritePanicDoesNotCrash` |
| обнаружение снаружи защиты | `TestFailOpenKeepsProtections` |

## Вопросы для самопроверки

1. Почему паника в обнаружении не переводит весь сенсор в fail-open,
   хотя перегрузка переводит? Что получил бы атакующий, если бы паники
   переключали режим?

   <details><summary>Ответ</summary>

   Паника зависит от ввода, а ввод выбирает атакующий. Найдя запрос,
   вызывающий панику, он повторял бы его и держал бы обнаружение
   выключенным для всех, а сам в это время касался бы приманок
   незамеченным. Сейчас паника выключает обнаружение только для самого
   «падающего» запроса, и тот записан с адресом отправителя. Перегрузка
   же — состояние всего сенсора, и снизить работу обнаружения — способ
   из неё выйти.

   </details>

2. Почему в частичном режиме проверяется каждый 10-й запрос, а не ни
   одного?

   <details><summary>Ответ</summary>

   Во-первых, обнаружение не пропадает: сканер делает десятки касаний
   приманок, и какие-то попадут в выборку. Полное отключение дало бы
   атакующему окно полной невидимости. Во-вторых, выборка непрерывно
   измеряет, быстры ли проверки, и по ней видно, что перегрузка прошла.
   При полном отключении пришлось бы включать проверку «на пробу» по таймеру.

   </details>

3. Что такое гистерезис и какую проблему он решает в сенсоре? Назовите
   оба порога.

   <details><summary>Ответ</summary>

   Разные пороги входа и выхода. Вход — 10% медленных проверок за 10 с,
   выход — меньше 1% за 30 с и не раньше чем через 30 с. Без этого при
   нагрузке около порога сенсор переключался бы туда-обратно на каждом
   всплеске: каждое переключение — событие critical и алерт, то есть
   шквал алертов и дёрганое поведение. Между 1% и 10% режим не меняется.

   </details>

4. Обнаружение начало отвечать ловушкой и упало посреди ответа. Почему
   сенсор обрывает соединение, а не пропускает запрос в приложение, как
   при обычной панике?

   <details><summary>Ответ</summary>

   Клиент уже получил начало ответа ловушки. Если отправить следом ответ
   приложения, он получит два ответа, склеенных в один. Вернуть уже
   отправленное нельзя, поэтому остаётся оборвать соединение. То же, если
   упавшее обнаружение прочитало часть тела: приложение получило бы тело
   без начала. Избежать этого можно договором для обнаружения: сначала
   решить, потом писать; не читать тело без необходимости.

   </details>

5. Почему событие о переходе в fail-open попадает в отдельную очередь
   по **типу** (`sensor.*`), а не по важности (`critical`)?

   <details><summary>Ответ</summary>

   Тип — константа из кода, и атакующий не может его выбрать. Касания
   приманок, в том числе самые важные, имеют свои типы и в очередь
   `sensor.*` не попадут никогда. Если бы очередь выбиралась по важности,
   атакующий мог бы заливать её событиями о «важных» касаниях и снова
   вытеснять событие о fail-open.

   </details>
