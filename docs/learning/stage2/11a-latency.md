# Этап 2, шаг 11а. Замер задержки сенсора

> Снимок на момент шага: 2026-09-29. Решение и цифры — в
> [ADR-0030](../../adr/0030-latency-budget.md). Как запустить —
> в [guide.md](../../guide.md), `make bench`.

## Что и зачем

Сенсор стоит в пути каждого запроса к сайту клиента. Если он заметно
замедляет сайт, его выключат — и защиты не будет вовсе. Поэтому с первого
дня у сенсора бюджет: **не больше +5 мс к p99** времени ответа приложения.
К концу этапа 2 сенсор проксирует, ищет ловушки, пишет события, правит
ответы. На этом шаге бюджет проверен замером. Замер нашёл одно место,
которое бюджет почти съедало, — правку большой страницы, — и она
исправлена.

## Понятия

- **Перцентиль (p50, p99)** — значение, быстрее которого прошла доля
  запросов. Бюджет записан через p99: среднее прячет редкие медленные
  ответы, а пользователи замечают именно их.
- **Открытая и закрытая модель нагрузки.** Закрытая: следующий запрос —
  после ответа. Открытая: запросы идут по расписанию, как настоящие
  посетители, которые не знают друг о друге.
- **Coordinated omission** — ошибка закрытой модели: медленный ответ
  задерживает отправку следующих, и они в замер не попадают.
- **Микробенчмарк** — замер одной функции: наносекунды и выделения памяти
  на вызов.
- **Профилирование** — на какие функции уходит время.
- **BREACH** — атака на сжатие ответов с секретом и отражённым вводом.

Все термины — в [глоссарии](../../glossary.md).

## Как это работает

```
генератор (расписание: rate запросов в секунду)
   │  задержка = конец ответа − момент, когда запрос ДОЛЖЕН был уйти
   ├──────────────▶ приложение-заглушка            «напрямую»
   └──▶ сенсор (run, demo.json) ──▶ приложение     «через сенсор»

цена сенсора = p99(через сенсор) − p99(напрямую), медиана трёх повторов
```

## Разбор кода

### Расписание запросов: `measure` в `cmd/sensor/latency_test.go`

```go
interval := time.Second / time.Duration(rate)
start := time.Now().Add(5 * time.Millisecond)
for i := range n {
	due := start.Add(time.Duration(i) * interval)
	if d := time.Until(due); d > 0 {
		time.Sleep(d)
	}
	wg.Add(1)
	go func() {
		...
		lat[i] = time.Since(due)
	}()
}
```

- `due` — момент, когда i-й запрос **должен** уйти: начало плюс i
  интервалов. Он не зависит от того, ответили ли на предыдущие.
- Каждый запрос — в своей горутине: генератор не ждёт ответа, прежде чем
  отправить следующий. Это и есть открытая модель.
- `time.Since(due)` — задержка от запланированного момента, а не от
  фактической отправки. Если генератор или сенсор отстали, отставание
  входит в задержку, а не прячется.
- `lat[i]` — у каждой горутины своя ячейка, поэтому блокировка не нужна.
  `wg.Wait()` ждёт всех, прежде чем читать срез.

### Честность сравнения

```go
for round := range *latRounds {
	for k := range targets {
		ti := (k + round) % len(targets)
		client := newClient()
		measure(ctx, client, targets[ti].base, sc, r, *latWarmup)
		res := measure(ctx, client, targets[ti].base, sc, r, *latDuration)
```

- Свой клиент на каждый замер: соединения, открытые для одной стороны,
  не достаются другой.
- Прогрев перед замером (`latWarmup`): первые запросы открывают
  соединения и греют кэши. Мерить их — мерить запуск, а не работу.
- `(k + round) % len(targets)` — в первом повторе первым идёт «напрямую»,
  во втором — «через сенсор». Второму достаётся прогретая машина.
- В отчёте — медиана трёх повторов: один всплеск (сборка мусора,
  соседний процесс) не решает исход.

### Проверки замера

```go
if sc.budget && extra > latencyBudget {
	t.Errorf("%s при %d/с: сенсор добавил %s к p99 — больше бюджета %s", ...)
}
...
if html != pagesSent {
	t.Errorf("наживка поставлена на %d страниц из %d", html, pagesSent)
}
```

- Превышение бюджета — ошибка теста, и `make bench` падает.
- Вторая проверка — чтобы бюджет не выполнялся «за счёт» наживок. Если
  бы под нагрузкой бюджет памяти кончался и наживки тихо пропускались,
  сенсор выглядел бы быстрее. Число страниц с наживкой сверяется с числом
  страниц через сенсор по `/metrics`.

### Новый предел: `maxHTMLHead` в `lure/html.go`

```go
const maxHTMLHead = 64 << 10
```

64 КиБ — сколько страницы токенизатор читает в поисках `<body>`. Было
256 КиБ, и на странице с большим `<head>` разбор занимал до 4,5 мс.

### Резерв по длине тела: `editReserve` в `lure/budget.go`

```go
func editReserve(contentLength, limit, perByte int64) int64 {
	n := limit
	if contentLength >= 0 && contentLength < limit {
		n = contentLength
	}
	return perByte*n + reserveBase
}
```

- `contentLength` — длина тела из ответа приложения. `-1` — длина
  неизвестна (chunked), и резерв считается как для тела на пределе.
- `perByte` — байт памяти на байт тела, по замеру с запасом: 8 для HTML
  (токенизатор копирует атрибуты), 6 для `robots.txt`.
- `reserveBase` — 16 КиБ на буфер токенизатора и мелочи.
- Страница Juice Shop (9,4 КБ) занимает при разборе около 90 КБ, а не
  2 МиБ, как на шаге 10б.

```go
func newEditBuffer(contentLength, limit int64) *bytes.Buffer {
	buf := &bytes.Buffer{}
	if contentLength >= 0 {
		buf.Grow(int(min(contentLength, limit)) + bytes.MinRead)
	}
	return buf
}
```

- Известна длина — буфер сразу нужного размера. Иначе он рос бы
  удвоением: 512 → 1024 → 2048… и выделил бы вдвое больше.
- `bytes.MinRead` (512 байт) — `ReadFrom` требует столько свободного
  места перед каждым чтением, в том числе последним, которое узнаёт
  о конце тела. Без запаса буфер вырос бы в последний момент.

Требование: худший резерв помещается в долю клиента (4 МиБ). Иначе тело
без `Content-Length` не правилось бы никогда. Проверяет
`TestWorstReserveFitsClientShare`.

## Находки

1. **Предел 256 КиБ почти съедал бюджет.** Токенизатор копирует атрибуты
   каждого тега: страница Juice Shop — 120 мкс, а 256 КиБ тегов —
   4,5 мс. Это ещё и дешёвый способ загрузить процессор сенсора. Предел
   снижен до 64 КиБ (худший случай — меньше 1 мс), резерв памяти
   пересчитан.
2. **Блокировка контроллера fail-open дешёвая.** 0,21 мкс под конкуренцией
   четырёх горутин. Долг шага 7 закрыт без переделки.
3. **Сжатие сенсором дешёвое, но небезопасное.** gzip из пула — 10 мкс
   на страницу. Но сенсор не знает, сжимало бы приложение страницу само,
   а приложения отключают сжатие страниц с секретами из-за BREACH.
   Сенсор не сжимает; сжимать — прокси перед ним.
4. **`robots.txt` под нагрузкой терял наживку.** Первый полный замер
   прошёл по бюджету, но показал 536 пропусков по памяти. Резерв на правку
   `robots.txt` был 4 МиБ — вся доля клиента. Одновременно у клиента
   дополнялся один `robots.txt`, остальные уходили как есть. Замер сверял
   только страницы. Исправлено: резерв по длине тела, замер сверяет
   и `robots.txt`.
5. **Исправление чуть не сломало `robots.txt` без длины.** При множителе
   8 худший резерв `robots.txt` (4,02 МиБ) не помещался в долю клиента
   (4 МиБ), и `robots.txt` без `Content-Length` не дополнялся бы никогда.
   Заметил при пересчёте, тесты этого не ловили. Добавлены
   `TestWorstReserveFitsClientShare` и случай без длины в
   `TestRobotsAppend`; множитель для `robots.txt` — 6 по замеру.
6. **Файл замера линтер не видел.** Файл с тегом `latency` собирается
   только с этим тегом, и линтер его пропускал. В `.golangci.yml`
   добавлен `build-tags: [latency]`.
7. **Мало замеров — p99 решает один всплеск.** Скачивание при 100 запросах
   в секунду за секунду — это 100 замеров, и p99 — второй по медленности.
   Короткий прогон упал на одном всплеске 18 мс, который бывал у обеих
   сторон. Теперь в каждом замере не меньше 1000 запросов.
8. **Точность таймеров в виртуальной машине** — около 0,9 мс базовой
   задержки у обеих сторон. Она одинакова и в разницу не входит, но
   абсолютные цифры — не время ответа приложения.

## Граница доверия

Шаг не добавляет кода, через который проходят данные от атакующего:
генератор и заглушка есть только в тестах. Изменён один предел в правке
HTML, и он строже прежнего: сенсор читает меньше данных приложения.

## Что может пойти не так

- **Цифры верны для этой машины.** На оборудовании клиента замер нужно
  повторить, `make bench`.
- **Генератор и сенсор делят процессоры.** Оценка поэтому завышена,
  а не занижена.
- **Страницы, где до `<body>` больше 64 КиБ, остаются без наживки.**
  Это видно в `html_no_body`.
- **Замер не в CI.** Если горячий путь изменится, а `make bench` не
  запустят, регресс пройдёт незамеченным. Микробенчмарки компилируются
  и проверяются линтером в CI, но не запускаются.

## Как это проверено

- `make bench` — задержка на шести сценариях при двух нагрузках
  и микробенчмарки: результаты — в ADR-0030.
- `TestEditReserves` — резерв не меньше замера для тел от 0 байт
  до предела, пяти форм HTML и `robots.txt`, с длиной и без неё.
- `TestWorstReserveFitsClientShare` — тело без длины помещается в долю
  клиента.
- Все тесты, фаззинг и мутации шагов 10а–10в — на изменённом пределе.

## Проверьте руками

```bash
make bench                                           # несколько минут
make bench BENCH_ARGS="-latency.rates=500 -latency.rounds=5"
cd sensor && go test -run '^$' -bench BenchmarkModify -benchmem ./internal/lure/
```

В конце вывода `make bench` — таблица «напрямую / через сенсор»

## Вопросы для самопроверки

1. Почему задержка считается от момента, когда запрос должен был уйти,
   а не от фактической отправки?

   <details><summary>Ответ</summary>

   Если сенсор замедлился, генератор с закрытой моделью отправил бы
   меньше запросов — ровно в тот момент, когда всё медленно. Медленные
   ответы спрятали бы сами себя, и p99 выглядел бы лучше правды
   (coordinated omission). Отсчёт от расписания включает в задержку
   и ожидание в очереди — то, что увидел бы настоящий посетитель.

   </details>

2. Зачем проверять, что наживка стоит на каждой странице через сенсор,
   в тесте про задержку?

   <details><summary>Ответ</summary>

   Под нагрузкой бюджет памяти правки тел может кончиться, и тогда
   страницы уходят без наживки — быстрее. Сенсор уложился бы в бюджет
   задержки за счёт того, что перестал работать. Проверка гарантирует,
   что замерена настоящая работа.

   </details>

3. Почему предел чтения страницы снижен с 256 до 64 КиБ, если память
   под правку и так ограничена бюджетом?

   <details><summary>Ответ</summary>

   Бюджет памяти ограничивает память, а не время. Токенизатор разбирает
   256 КиБ плотного `<head>` за 4,5 мс — почти весь бюджет задержки
   на один запрос, и это время процессора сенсора, которое атакующий
   может тратить, запрашивая такую страницу. При 64 КиБ худший случай —
   меньше 1 мс, а обычные страницы укладываются с запасом.

   </details>

4. gzip страницы стоит 10 мкс. Почему сенсор всё равно её не сжимает?

   <details><summary>Ответ</summary>

   Сенсор просит у приложения страницу без сжатия и не знает, сжало бы
   приложение её само. Некоторые приложения не сжимают страницы с токеном
   CSRF и отражённым вводом из-за атаки BREACH. Сенсор, включивший сжатие,
   открыл бы им эту атаку. Кроме того, writer gzip занимает около 800 КБ
   на всё время отправки медленному клиенту. Сжимать должен прокси перед
   сенсором — там оператор решает это сознательно.

   </details>

5. Почему замер не запускается в CI, и чем это грозит?

   <details><summary>Ответ</summary>

   Он идёт минуты, а результат зависит от машины и соседей: на общих
   раннерах тест то падал бы, то проходил, и ему перестали бы верить.
   Грозит тем, что регресс в горячем пути пройдёт незамеченным, если
   `make bench` не запустить. Поэтому его запускают перед выпуском
   и после изменений в горячем пути.

   </details>
