# Этап 2, шаг 6. События сенсора

> Снимок на момент шага: 2026-09-24. Решение — в
> [ADR-0023](../../adr/0023-sensor-events.md). Текущее состояние —
> в [guide.md](../../guide.md), раздел «Сенсор».

## Что и зачем

Продукт существует ради одного сигнала: «кто-то коснулся приманки». Этот
сигнал — событие, и до шага 6 сенсору некуда было его записать. Приманок
ещё нет (шаг 8), но путь события строится сейчас целиком: формат, буфер,
файл, счётчики. Настоящие события уже есть — запуск, остановка и попытки
`CONNECT`, то есть проверки «не открытый ли здесь прокси».

У записи событий четыре требования, и все про безопасность:

1. **Не ждать.** Запрос клиента не может задержаться из-за того, что диск
   занят. Сенсор стоит в пути трафика: его ожидание — это медленный сайт
   клиента.
2. **Не записать лишнего.** В событии не должно оказаться паролей, токенов,
   cookie, персональных данных сверх необходимого (T4).
3. **Не дать атакующему испортить журнал.** В событие попадает то, что
   выбрал атакующий: путь, User-Agent. Он не должен суметь дописать
   поддельное событие или выполнить что-то в терминале администратора (T19).
4. **Не дать заполнить диск.** Атакующий управляет числом событий (T3).

## Понятия

- **JSON Lines** — одна строка файла — один объект JSON.
- **Неблокирующая запись** — `select` с `default`: положить в канал, если
  есть место, иначе сразу сделать другое.
- **Вытеснение старого** — при полном буфере выбрасывается самое старое
  событие, а новое кладётся.
- **Маскирование** — замена части данных меткой до записи.
- **Ротация файла** — переименование в `.1` и новый файл по достижении
  предела; самый старый удаляется.
- **Метрика и Prometheus** — счётчики на `/metrics` в текстовом формате.
- **Управляющие последовательности** — невидимые символы, которые
  терминал выполняет.
- **Золотой тест** — сравнение результата с эталоном целиком.

Все — в [глоссарии](../../glossary.md).

## Как это работает

```
обработчик запроса              горутина записи              диск
      │                               │                        │
  event.New(...)                      │                        │
  Emit(ev) ──► [буфер 4096] ──────► json.Marshal ──► bufio ──► events.jsonl
      │         полон? вытеснить      │   один объект —          ротация 32 МиБ,
  сразу дальше  старое, учесть        │   одна строка            4 старых файла
      ▼                               │                        │
  ответ клиенту                  буфер пуст → сброс            │
                                                               │
  /metrics ◄── счётчики: принято, записано, потеряно по причинам
```

Обработчик запроса не касается диска вообще. Он кладёт событие в канал
и отвечает клиенту. Всё медленное — кодирование и запись — делает одна
отдельная горутина.

## Разбор кода

### Что берётся из запроса: `RequestFrom` в `event/event.go`

```go
func RequestFrom(r *http.Request) *Request {
	method, _ := Clean(r.Method, maxMethodBytes)
	path, truncated := MaskPath(r.URL.EscapedPath())
	ua, _ := Clean(r.Header.Get("User-Agent"), maxUserAgentBytes)
	return &Request{
		Method:        method,
		Path:          path,
		PathTruncated: truncated,
		HasQuery:      r.URL.RawQuery != "" || r.URL.ForceQuery,
		UserAgent:     ua,
	}
}
```

Главное здесь — чего в функции **нет**. Она читает из запроса ровно четыре
вещи. Остальное — тело, cookie, `Authorization`, прочие заголовки,
значения параметров — в событие попасть не может, потому что его никто
не читает. Проверять при ревью нужно именно этот список: новое поле
в `Request` — повод спросить «а это точно не персональные данные?».

- `r.Method` — атакующий может прислать метод из тысячи букв: Go принимает
  любой «токен». Отсюда предел в 32 байта.
- `r.URL.EscapedPath()` — путь в процентной кодировке, как его прислали:
  `%2e%2e` остаётся `%2e%2e`, а не превращается в `..`. Для анализа атаки
  важно, **как** атакующий записал путь. В этой форме только ASCII,
  поэтому с кодировкой проблем нет.
- `r.URL.RawQuery != ""` — из параметров записываем один бит: были ли они.
  В параметрах живут `?token=`, `?password=`, `?email=`.
- `User-Agent` — нужен для отпечатка клиента (ADR-0007), до 256 байт.

### Обрезка и UTF-8: `Clean`

```go
if len(s) > max {
	s = s[:max]
	truncated = true
}
s = strings.ToValidUTF8(s, "�")
if len(s) > max {
	cut := max
	for cut > 0 && !utf8.RuneStart(s[cut]) {
		cut--
	}
	s = s[:cut]
	truncated = true
}
```

1. Сначала отрезаем лишнее, чтобы не обрабатывать строку в десятки
   килобайт целиком.
2. `ToValidUTF8` меняет недопустимые последовательности байтов на `�`.
   Сервер Go пропускает в заголовках байты от 0x80, и атакующий может
   прислать мусор, который не является текстом.
3. Замена может **удлинить** строку: один байт `\xff` становится тремя
   байтами `�`. Поэтому режем ещё раз — по границе символа. `RuneStart`
   отвечает, начинается ли с этого байта символ. Если нет, отступаем
   назад, чтобы не разрезать букву пополам.

Экранирования здесь нет, и это намеренно. Его делает кодировщик JSON.
Двойное экранирование испортило бы данные для того, кто будет их
разбирать.

### Маскирование: `MaskPath` и `maskSegment` в `event/mask.go`

```go
if len(p) > maxPathBytes {
	p = p[:maxPathBytes]
	if i := strings.LastIndexByte(p, '/'); i >= 0 {
		p = p[:i+1]
	}
	...
}
```

Обрезка по пределу 1024 байта может прийтись на середину токена. Начало
токена короче порога маскирования и прошло бы как есть. Поэтому
обрезанный последний сегмент выбрасывается целиком — до последнего `/`.

```go
segments := strings.Split(p, "/")
for i, s := range segments {
	segments[i] = maskSegment(s)
}
```

Здесь `Split` допустим, в отличие от разбора `X-Forwarded-For` на шаге 5:
длина уже ограничена 1024 байтами.

```go
if i := strings.IndexByte(s, ';'); i >= 0 {
	return maskSegment(s[:i]) + ";" + maskParams
}
```

`/shop;jsessionid=0123ABCD` — так Tomcat передаёт идентификатор сессии.
Это классическая утечка сессии через журналы. Имя до `;` проверяем как
обычный сегмент, всё после — заменяем.

```go
switch {
case strings.Contains(s, "@") || strings.Contains(s, "%40"):
	return maskEmail
case isUUID(s):
	return maskUUID
case isJWT(s):
	return maskJWT
case isDigits(s):
	return maskNum
case len(s) >= minHexLen && isHex(s):
	return maskHex
case len(s) >= minTokenLen && isToken(s):
	return maskToken
}
```

Порядок важен: от точного к общему. UUID состоит из шестнадцатеричных
цифр и дефисов, и правило `{token}` его бы тоже поймало. Но `{uuid}`
точнее говорит, что было в пути. `%40` — это `@` в процентной записи:
без этой проверки адрес почты проходил бы, будучи записан иначе.

Пороги 16 и 20 символов подобраны так, чтобы обычные слова
(`facade` — это шестнадцатеричные буквы, `configuration-management` —
длинное, но без цифр) проходили, а токены — нет. Это эвристика
с известными ошибками в обе стороны; тест фиксирует границы: 16 символов
маскируются, 15 — нет.

### Буфер: `Emit` в `event/recorder.go`

```go
r.mu.RLock()
defer r.mu.RUnlock()
if r.stopped {
	r.Stats.DroppedStopped.Add(1)
	return
}
```

Блокировка на чтение — не ради ожидания. Остановка берёт её на запись
один раз, и после этого ни один `Emit` уже не положит событие в буфер.
Без неё событие, пришедшее в момент остановки, могло бы остаться в канале
после того, как горутина записи его уже дочитала: не записанным и
не учтённым.

```go
select {
case r.queue <- ev:
	r.Stats.Emitted.Add(1)
	return
default:
}
```

Неблокирующая запись: есть место — положили и вышли. Нет — идём дальше,
а не ждём.

```go
select {
case <-r.queue:
	r.Stats.DroppedQueueFull.Add(1)
default:
}
select {
case r.queue <- ev:
	r.Stats.Emitted.Add(1)
default:
	r.Stats.DroppedQueueFull.Add(1)
}
```

Буфер полон — вытесняем самое старое событие и кладём новое. Почему
старое, а не новое: буфер заполняется, только когда запись отстаёт,
и заполнить его может сам атакующий, касаясь приманок. Если бы терялись
новые события, он заполнил бы буфер и дальше действовал бы невидимо.
При вытеснении старых в буфере всегда самые свежие события.

Попыток ровно две, без цикла. Между ними освободившееся место может
занять другой обработчик — тогда теряется это событие. Цикл «пока
не получится» теоретически мог бы крутиться долго, а `Emit` не имеет
права задерживать запрос.

Эта часть исправлена в ходе шага. Сначала я написал «отбросить новое» —
так было в примере из `go-reading.md`. ADR-0004 же требует отбрасывать
старые. Расхождение нашлось при написании ADR-0023, и правильным
оказался ADR-0004. Тест `TestEmitNeverBlocks` теперь проверяет, что
последнее событие обязательно записано.

### Запись: `write` в `event/recorder.go`

```go
line, err := json.Marshal(ev)
...
line = append(line, '\n')
if err := r.sink.Write(line); err != nil {
```

`json.Marshal` — главная защита от T19. Он экранирует в строках перевод
строки (`\n`), возврат каретки, все управляющие символы (`\u001b` вместо
ESC), `<`, `>`, `&` и U+2028/U+2029. Поэтому внутри закодированного
события перевода строки быть не может, и наш `'\n'` — единственный
в строке. Атакующий не может вставить в User-Agent перевод строки
и «своё» событие.

Первый рубеж стоит ещё раньше — сервер Go. Запрос с ESC или переводом
строки в заголовке получает 400 до кода сенсора (проверено руками
и закреплено в `TestMalformedRequestsRejected`). Но полагаться только
на него нельзя: байты от 0x80 он пропускает, а в будущих приманках
данные придут и из тела запроса.

### Файл: `Write` и `rotate` в `event/file.go`

```go
f, err := os.OpenFile(s.path, os.O_WRONLY|os.O_CREATE|os.O_APPEND, filePerm)
```

`O_APPEND` — дописывать в конец: события прошлого запуска сохраняются.
`filePerm = 0o600` — читает только пользователь сенсора: в событиях
адреса клиентов.

```go
if s.size > 0 && s.size+int64(len(line)) > s.maxBytes {
	if err := s.rotate(); err != nil {
		return err
	}
}
```

Файл дорос до 32 МиБ — ротация. `rotate` переименовывает `.3` → `.4`,
`.2` → `.3`, …, текущий → `.1` и открывает новый. Переименование поверх
существующего файла заменяет его, поэтому `.4` при этом удаляется.
Итого не больше пяти файлов по 32 МиБ — 160 МиБ, сколько бы событий
ни было.

```go
if s.f == nil {
	if err := s.open(); err != nil {
		return err
	}
}
```

Если ротация не смогла открыть новый файл (например, пропал каталог),
следующая запись пробует снова. Сенсор не перестаёт писать навсегда
из-за временного сбоя, а пропущенные события учитываются как
`write_error`.

### Метрики: `metrics.Handler`

```go
labelRe = regexp.MustCompile(`^[a-z_][a-z0-9_]*="[a-z0-9_]+"$`)
```

Метка — например, `reason="queue_full"`. Регулярное выражение проверяет
её при запуске и не пропустит кавычку или перевод строки. Главное
правило другое, и оно не в коде, а в том, откуда метки берутся: только
константы. Метка из пути запроса дала бы атакующему создавать по новой
строке метрик на каждый запрос — это рост памяти без предела.

## Граница доверия

| Данные | Откуда | Что с ними делается |
|---|---|---|
| метод, путь, User-Agent | атакующий | ограничены по длине, UTF-8, путь маскируется; в файл — только как значения JSON |
| адрес из `CONNECT` | атакующий | ограничен 261 байтом, UTF-8 |
| тело, cookie, `Authorization`, параметры | атакующий | не читаются вовсе |
| число событий | атакующий | буфер фиксированного размера, вытеснение старых, ротация файла |
| адрес клиента | пакет `forwarded` (шаг 5) | как есть; неизвестный — поля нет |
| файл событий | сенсор | `0600`, каталог `0700`, читает только пользователь сенсора |
| `/metrics` | сенсор | только служебный слушатель, только числа и константы |

## Что может пойти не так

- **T3 — заполнение диска событиями.** Закрыто ротацией: не больше
  160 МиБ.
- **T3 — сенсор ждёт диск.** Закрыто: `Emit` не ждёт. Остаётся: при зависшем
  диске события теряются (вытесняются) — это принятый риск R2, и потери
  видны в `sensor_events_dropped_total`.
- **T4 — секреты в событиях.** Закрыто списком из четырёх полей
  и маскированием. Остаётся: маскирование — эвристика; короткий токен
  в пути пройдёт.
- **T19 — данные атакующего в журнале.** Закрыто двумя рубежами: сервер
  Go и JSON. Остаётся на этап 5: дашборд обязан выводить события как
  текст с экранированием.
- **Критичное событие утонет в шуме.** Ни «отбрасывать старое», ни
  «отбрасывать новое» не гарантирует, что событие о переходе в fail-open
  (шаг 7) переживёт поток касаний приманок. Записано в технический
  долг на шаг 7.
- **Сбой процесса.** Теряются события, ещё не сброшенные из буфера
  файла, — доли секунды при потоке. Расширение R2.

## Как это проверено

- **Формат.** `TestFormatV0` — золотой тест: событие с известными полями
  кодируется ровно в заданную строку.
- **Данные атакующего.** `TestNoLineInjection` — перевод строки, ESC,
  U+2028 и `<script>` в User-Agent дают одну строку с одним событием
  исходного типа. `TestEventSizeBounded` — самый неудобный запрос даёт
  событие не больше 4 КиБ. `TestRequestFromReadsOnlyMetadata` — токен
  в параметрах, тело, cookie, `Authorization` и токен в пути не попадают
  в событие.
- **Маскирование.** 26 случаев в `TestMaskPath`, включая границы порогов;
  `TestMaskPathTruncation` — начало токена не попадает в обрезанный путь.
  `FuzzMaskPath` — результат никогда не длиннее предела.
- **Буфер.** `TestEmitNeverBlocks` — при зависшей записи `Emit`
  не ждёт, последнее событие записано, «записано + потеряно» равно
  числу вызовов. `TestConcurrentEmitAndClose` — сотня горутин
  и одновременная остановка: без паники, без гонок, учёт точный.
  `TestCloseDoesNotHang` — зависший диск не вешает остановку.
- **Файл.** Дописывание после перезапуска, права `0600`, ротация
  с удалением старых, восстановление после пропажи каталога, отказ
  писать в каталог вместо файла.
- **Сенсор целиком.** `TestRunRecordsEventsAndMetrics` — настоящий сенсор:
  `CONNECT` даёт 405, событие и счётчик в `/metrics`; после остановки
  в файле ровно `sensor.started`, `request.connect_rejected`,
  `sensor.stopping`. `TestRunFailsWhenEventsFileUnavailable` — без файла
  сенсор не открывает слушатели.
- **Контейнер.** `make smoke` шлёт `CONNECT` в сенсор перед Juice Shop
  и ищет событие в файле внутри контейнера. Так проверяются права
  каталога в образе и том, а не только код.
- Всё — с детектором гонок (`go test -race`); тесты буфера прогнаны
  20 раз подряд.

Мутационная проверка — код намеренно ломался, каждый раз тест падал:

| Поломка | Какой тест упал |
|---|---|
| отбрасывать новое вместо старого | `TestEmitNeverBlocks` — последнее событие не записано |
| блокирующая запись в буфер | `TestEmitNeverBlocks` — «Emit ждёт зависшую запись» |
| не сбрасывать буфер файла при пустой очереди | `TestRecorderWithFile` — событие не видно в файле |
| файл событий с правами `0644` | `TestFileSinkPermissions` |
| оставлять обрезанный сегмент пути | `TestMaskPathTruncation` |
| не маскировать токены | `TestMaskPath` |
| не чинить UTF-8 | `TestClean` |
| не записывать `CONNECT` | `TestConnectRejected` |
| не считать отказы приложения | `TestUpstreamDownIsNeutral502` |

## Проверьте руками

В контейнере — событие о `CONNECT`:

```bash
make dev-demo
curl -s -o /dev/null -w '%{http_code}\n' -X CONNECT \
  --request-target 10.0.0.1:22 http://127.0.0.1:8080     # 405
make dev-events
```

Ожидается две строки — запуск и попытка туннеля к `10.0.0.1:22`:

```
{"v":0,...,"type":"sensor.started","severity":"info","data":{"version":"dev"}}
{"v":0,...,"type":"request.connect_rejected","severity":"low","client":{"ip":"172.19.0.1",...},"request":{"method":"CONNECT","user_agent":"curl/8.5.0"},"data":{"target":"10.0.0.1:22"}}
```

`172.19.0.1` — адрес шлюза сети Docker: с точки зрения контейнера
запрос пришёл оттуда.

Экранирование — `User-Agent` с U+2028, `<script>` и недопустимым байтом:

```bash
curl -s -o /dev/null -X CONNECT --request-target 10.0.0.1:22 \
  -A $'scanner <script>\xff' http://127.0.0.1:8080
make dev-events | tail -1
# "user_agent":"scanner <script>�"
```

А с ESC сервер Go ответит 400, и события не будет — первый рубеж:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X CONNECT \
  --request-target 10.0.0.1:22 -A $'x\x1b[31m' http://127.0.0.1:8080   # 400
make dev-down
```

Метрики — сенсор без Docker (нужен Go), приложения нет, поэтому запрос
получит 502:

```bash
make run-sensor                                   # в другом терминале:
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/   # 502
curl -s http://127.0.0.1:9090/metrics | grep -E 'upstream_unreachable|events_written'
# sensor_events_written_total 1
# sensor_upstream_errors_total{class="upstream_unreachable"} 1
ls -l .run/events.jsonl                           # -rw-------
```

## Вопросы для самопроверки

1. Почему при полном буфере сенсор выбрасывает самое старое событие,
   а не новое? Опишите, как атакующий воспользовался бы обратным
   решением.

   <details><summary>Ответ</summary>

   Буфер заполняется, когда запись отстаёт, и заполнить его может сам
   атакующий: он касается приманок, а каждое касание — событие. Если бы
   терялись новые события, атакующий сначала забил бы буфер шумом, а потом
   сделал бы главное — и это главное не попало бы в журнал. При вытеснении
   старых в буфере всегда самые свежие события, то есть его последние
   действия.

   </details>

2. Атакующий присылает `User-Agent: x\n{"type":"sensor.started"}`.
   Почему в файле событий не появится второе, поддельное событие? Назовите
   оба рубежа.

   <details><summary>Ответ</summary>

   Первый — сервер Go: перевод строки внутри заголовка недопустим, запрос
   получит 400 и до сенсора не дойдёт. Второй — `json.Marshal`: даже если
   такие данные придут иначе, кодировщик запишет перевод строки как `\n`
   внутри строки JSON. Настоящий перевод строки в файле — только тот,
   что сенсор ставит после каждого события. Одна строка — одно событие.

   </details>

3. Почему в событие не записываются параметры запроса, а только признак
   `has_query`? Чем путь отличается?

   <details><summary>Ответ</summary>

   В параметрах живут `?token=`, `?password=`, `?email=`, и отличить
   безопасный параметр от секретного по имени нельзя. Путь нужен, чтобы
   понять, что трогали, — поэтому он записывается, но с маскированием:
   токены, UUID, числа, почта заменяются метками. Это компромисс между
   пользой для расследования и минимизацией данных (ADR-0007).

   </details>

4. Файл событий не открывается при запуске — например, забыли создать
   каталог. Почему сенсор отказывается стартовать, хотя это делает сайт
   клиента недоступным?

   <details><summary>Ответ</summary>

   Это ошибка развёртывания, и она видна сразу — при первом запуске, а не
   через месяц. Сенсор, который пропускает трафик и молча ничего
   не записывает, создаёт ложное чувство защищённости: мониторинг зелёный,
   обнаружения нет. Та же логика, что с неверным адресом приложения:
   при запуске — громко, во время работы — fail-open.

   </details>

5. Почему метки метрик берутся только из констант? Что случилось бы,
   если бы метка была, например, путём запроса?

   <details><summary>Ответ</summary>

   Каждое новое значение метки — новая строка метрики в памяти сенсора
   и в хранилище Prometheus. Путь выбирает атакующий, и миллион запросов
   с разными путями дал бы миллион строк — рост памяти без предела,
   то есть отказ в обслуживании. Кроме того, путь в метрике — это данные
   атакующего в системе мониторинга, где их никто не экранирует.

   </details>
