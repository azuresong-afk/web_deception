# Этап 2, шаг 4. VulnBank — вторая учебная цель

> Снимок на момент шага: 2026-09-24. Решение — в
> [ADR-0019](../../adr/0019-test-targets.md). Как обновлять — в
> [deploy/demo/README.md](../../../deploy/demo/README.md).

## Что и зачем

Сенсор будет внедрять приманки в ответы приложения. Как это сработает,
зависит от того, как приложение устроено. Juice Shop — одностраничное
приложение: HTML почти пустой, страницы рисует JavaScript. VulnBank — наоборот:
сервер присылает готовые страницы с формами. Две цели разного устройства
проверяют сенсор на двух типичных для клиентов архитектурах.

Главная задача шага — не «запустить VulnBank», а запустить его так, чтобы
его уязвимости остались внутри контейнера. В нём отладчик Flask
(выполнение кода) и SSRF (запросы от имени сервера) — это по замыслу.

## Понятия

- **Отладчик Werkzeug** — консоль Python в браузере при `debug=True`.
  Выполнение любого кода на сервере.
- **SSRF** — атакующий заставляет сервер обратиться по выбранному адресу,
  в том числе туда, куда сам не дотянется.
- **Именованный контекст сборки** — дополнительный источник файлов для
  сборки образа, в нашем случае — git-репозиторий автора по SHA коммита.
- **Хеш коммита (SHA)** — отпечаток содержимого коммита. Ветку можно
  передвинуть на другой коммит, а коммит с этим SHA всегда один и тот же.

## Как это работает

```
compose: additional_contexts
   vulnbank-src = github.com/Commando-X/vuln-bank.git#4bb7cd5…  ← исходники по SHA
                                   │
deploy/demo/vulnbank/Dockerfile    ▼
   стадия сборки:  pip install --require-hashes --only-binary  ← зависимости с хешами
   рантайм:        COPY --from=vulnbank-src . /app              ← код, владелец root
                   USER 10001                                   ← не root
                                   │
compose: vulnbank                  ▼
   read_only, tmpfs для загрузок (16 МБ), сеть demo-vulnbank (internal)
   база vulnbank-db — своя, в памяти, в той же изолированной сети
                                   │
           127.0.0.1:8081 ──▶ sensor-vulnbank ──▶ vulnbank:5000
```

## Разбор кода

Go-кода в этом шаге нет. Разбираем конфигурацию: здесь граница «взломанная
учебная цель → всё остальное».

### Исходники по SHA: `deploy/compose/compose.yaml`

```yaml
build:
  context: ../demo/vulnbank
  additional_contexts:
    vulnbank-src: https://github.com/Commando-X/vuln-bank.git#4bb7cd5f46921959f034455e5615782481966177
```

- `context` — наш каталог: в нём только `requirements.txt` (остальное
  отсекает `.dockerignore`).
- `additional_contexts` — второй источник файлов: репозиторий автора.
  После `#` — полный SHA коммита. Если бы там стояло `#main`, каждая сборка
  брала бы то, что автор залил последним, и никто бы это не проверил.
- Это проверяет новое правило **C8** в `scripts/check_containers.py`:

```python
_PINNED_GIT_REF = re.compile(r"#[0-9a-f]{40}(:[^#]*)?$")
...
if _GIT_CONTEXT.match(ctx) and not _PINNED_GIT_REF.search(ctx):
    out.append(Violation(where, "C8", ...))
```

Читается так: если контекст — git-ссылка (`https://`, `git@`), то она
обязана заканчиваться на `#` и ровно 40 шестнадцатеричных знаков. Короткий
SHA из 7 знаков не подходит: он неоднозначен. Правило проверено подменой
SHA на `#main` — `make lint` падает.

### Зависимости с хешами: `deploy/demo/vulnbank/Dockerfile`

```dockerfile
RUN pip install --no-cache-dir --require-hashes --only-binary=:all: \
        --target /deps -r /tmp/requirements.txt
```

- `requirements.txt` собран из списка автора командой
  `make vulnbank-requirements`: у каждого пакета и каждой его зависимости —
  точная версия и хеши файлов.
- `--require-hashes` — файл с другим хешем не установится.
- `--only-binary=:all:` — только готовые колёса, без выполнения кода сборки.
- Сами версии старые и уязвимые — это учебная цель, и Dependabot их
  намеренно не обновляет.

### Исключение hadolint

```dockerfile
# hadolint ignore=DL3022
COPY --from=vulnbank-src . /app
```

Правило DL3022 проверяет, что `COPY --from` ссылается на стадию `FROM`,
и ловит опечатки. Именованных контекстов BuildKit hadolint не знает.
Опечатку здесь не пропустит сама сборка. Исключение — на одну строку,
с объяснением рядом, и вынесено владельцу на обсуждение: ослабление проверки
по правилам проекта не делается молча.

### Контейнер: `deploy/compose/compose.yaml`

```yaml
vulnbank:
  user: "10001:10001"
  read_only: true
  tmpfs:
    - /app/static/uploads:uid=10001,gid=10001,mode=0700,size=16m
  networks: [demo-vulnbank]
```

- Не root, корневая файловая система только для чтения. Код в `/app`
  принадлежит root — процесс не может его изменить (проверено: запись
  в `app.py` даёт `PermissionError`).
- Писать можно только в каталог загрузок — он в памяти и не больше 16 МБ.
  Загрузка файлов у VulnBank уязвима, но заполнить диск хоста она не сможет.
- Одна сеть, `demo-vulnbank`, с `internal: true` — без выхода наружу.

```yaml
vulnbank-db:
  environment:
    POSTGRES_HOST_AUTH_METHOD: trust
```

У учебной базы нет пароля. Это не небрежность: пароль, записанный
в публичный репозиторий, секретом не является, а база доступна только
самому VulnBank в изолированной сети.

## Граница доверия

Здесь граница не «интернет → сенсор», а «взломанная учебная цель → всё
остальное». Исходим из того, что VulnBank взломан (это легко — отладчик),
и проверяем, куда из него можно попасть:

| Куда | Результат |
|---|---|
| интернет | нет: `Temporary failure in name resolution` |
| облачные метаданные `169.254.169.254` | нет: `Network is unreachable` |
| база продукта `postgres`, `controlplane`, `nats` | имена не разрешаются |
| соседняя цель `juice-shop` | имя не разрешается |
| свой код `/app/app.py` | запись запрещена |
| порт на хосте | нет: `127.0.0.1:5000` не отвечает, только через сенсор |

## Что может пойти не так

- **T16 — выход за пределы цели.** Закрыто изоляцией выше; проверено руками.
- **Подмена исходников у автора.** Закрыто SHA коммита и правилом C8.
- **Остаётся:** обновлять VulnBank приходится вручную, с просмотром изменений
  автора (инструкция в `deploy/demo/README.md`).
- **Остаётся:** VulnBank не собирается в CI, поэтому поломку его сборки
  заметит только тот, кто запустит `make dev-vulnbank`.
- **Остаётся:** ответ VulnBank о регистрации возвращает `debug_data`
  с внутренними полями — это его уязвимость утечки информации, не наша.

## Как это проверено

- `scripts/test_check_containers.py`: тесты C8 — локальный контекст;
  git по полному SHA (с подкаталогом и без); git по ветке, тегу, короткому SHA,
  без ссылки; ssh-ссылка. И тест, что D6 не применяется к учебным целям,
  а D3 (не root) — применяется.
- C8 на настоящем compose: подмена SHA на `#main` — `make lint` падает.
- Руками: `make dev-vulnbank` — все сервисы healthy; через сенсор отдаются
  главная, страница входа, регистрация и вход по API; таблица изоляции выше.

make dev-vulnbank          # первый запуск дольше: образ собирается из исходников

## Вопросы для самопроверки

1. Почему исходники VulnBank закреплены по SHA коммита, а не по ветке `main`
   или тегу? Что проверяет правило C8?

   <details><summary>Ответ</summary>

   Ветку и тег автор может передвинуть на другой коммит — случайно или если
   его учётную запись взломают. Тогда следующая сборка возьмёт код, которого
   никто не видел. Коммит с данным SHA неизменен. C8 проверяет, что любая
   git-ссылка в сборке заканчивается полным SHA из 40 знаков; короткий SHA
   неоднозначен и тоже не принимается.

   </details>

2. VulnBank работает с отладчиком Flask — это выполнение кода. Почему
   мы его не выключили?

   <details><summary>Ответ</summary>

   Уязвимости внутри учебной цели — её смысл: на ней будут проверять, как
   сенсор видит атаки. Мы исходим из того, что цель взломана, и ограничиваем,
   куда из неё можно попасть: своя сеть без интернета, не видно ни продукта,
   ни соседней цели, код неизменяем, процесс не root.

   </details>

3. Зачем у учебной базы нет пароля, если правила проекта требуют секреты
   через переменные окружения или secret manager?

   <details><summary>Ответ</summary>

   Любой пароль, записанный в compose, лежит в публичном репозитории
   и секретом не является — это была бы видимость защиты. Реальная защита
   базы — сеть: к ней может подключиться только VulnBank. Правило о секретах
   относится к секретам продукта, а у учебной базы их нет.

   </details>

4. Почему для hadolint сделано исключение, а для D1 — нет, хотя обход
   `FROM vulnbank-src` убрал бы замечание hadolint?

   <details><summary>Ответ</summary>

   Замечание hadolint здесь ложное: он не знает именованных контекстов, а опечатку
   в имени не пропустит сама сборка. D1 же защищает от реального риска — образа
   без закрепления по digest. Обход ради одной проверки ослабил бы другую.
   Точечное исключение с объяснением честнее, и оно вынесено владельцу.

   </details>

5. Почему Dependabot обновляет базовый образ VulnBank, но не его зависимости
   и не минорную версию Python?

   <details><summary>Ответ</summary>

   Новый digest базового образа — это исправления уязвимостей в Debian: пусть
   приходят. Зависимости VulnBank старые по замыслу: обновить их — значит
   убрать уязвимости, ради которых цель и взята. Python 3.13 вместо 3.12 сломал
   бы установку (для psycopg2-binary 2.9.9 нет колёс под 3.13), а в CI образ
   не собирается, и поломку никто бы не заметил.

   </details>
