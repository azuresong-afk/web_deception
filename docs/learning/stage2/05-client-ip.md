# Этап 2, шаг 5. Адрес клиента и доверенные прокси

> Снимок на момент шага: 2026-09-24. Решение — в
> [ADR-0022](../../adr/0022-client-ip-trusted-proxies.md). Текущее состояние —
> в [guide.md](../../guide.md), раздел «Сенсор».

## Что и зачем

Сенсору нужно знать, кто прислал запрос: адрес клиента войдёт в каждое
событие (шаг 6), по нему строится профиль атакующего и реакция (этап 4).
Если перед сенсором стоит балансировщик, адрес TCP-соединения у всех
запросов один — адрес балансировщика. Настоящий адрес балансировщик
сообщает в `X-Forwarded-For`. Но тот же заголовок может прислать и сам
атакующий, с любым адресом внутри. Поверишь ему — атакующий спрячется
за чужим адресом или подставит адрес вашего партнёра, и блокировка
ударит по партнёру (угроза T1).

Шаг решает, кому верить, и делает это в одном месте кода.

Попутно найдена ошибка шага 3. Там написано, что Go сам удаляет все
присланные клиентом `X-Forwarded-*`. На деле он удаляет только
`X-Forwarded-For`, `-Host`, `-Proto` и `Forwarded`.
`X-Forwarded-Port: 443`, `X-Forwarded-Prefix: /evil`, `X-Forwarded-Ssl: on`
доходили до приложения от атакующего. Это проверено тестом на коде
шага 3 и исправлено здесь.

## Понятия

- **Доверенный прокси** — балансировщик или CDN перед сенсором, чьи адреса
  администратор перечислил в `SENSOR_TRUSTED_PROXIES`. По умолчанию список
  пуст: не доверять никому.
- **X-Forwarded-For** — цепочка адресов `клиент, прокси1, прокси2`: каждый
  прокси дописывает справа адрес того, кто к нему подключился.
- **Самый правый недоверенный адрес** — правило поиска клиента в этой
  цепочке: справа налево, пропуская свои прокси, до первого чужого.
- **Сеть и префикс (CIDR)** — `10.0.1.0/24`: адрес и число общих бит.
- **IPv4 в записи IPv6** — `::ffff:10.0.0.1`, тот же IPv4-адрес.

Все — в [глоссарии](../../glossary.md).

## Как это работает

Схема для запроса через балансировщик `10.0.0.1`, которому доверяем:

```
атакующий 203.0.113.7 шлёт:   X-Forwarded-For: 1.2.3.4       ← подделка
балансировщик 10.0.0.1 дописывает справа адрес атакующего:
                              X-Forwarded-For: 1.2.3.4, 203.0.113.7
сенсор видит соединение от 10.0.0.1 — доверенный, читаем заголовок
справа налево:
    203.0.113.7  — не наш прокси → это клиент, стоп
    1.2.3.4      — не читается вовсе
```

Почему справа: запись справа от доверенного прокси написал сам этот прокси,
значит, ей можно верить. Запись левее первого чужого адреса написал уже
не наш прокси — кто угодно.

Если бы атакующий подключился к сенсору напрямую, минуя балансировщик,
соединение пришло бы с 203.0.113.7 — адреса не из списка. Тогда заголовок
не читается вообще, клиент — адрес соединения.

Что получает приложение:

| Соединение | Заголовки о клиенте |
|---|---|
| не от доверенного прокси | все `X-Forwarded-*`, `Forwarded`, `X-Real-IP` и подобные удалены; `X-Forwarded-For`, `-Host`, `-Proto` сенсор ставит сам |
| от доверенного прокси | заголовки прокси как есть; `X-Forwarded-For` = `203.0.113.7, 10.0.0.1` — без подделки слева |
| любое | варианты с подчёркиванием (`X_Forwarded_For`) и `Forwarded` удалены |

## Разбор кода

Весь новый код — пакет `sensor/internal/forwarded`. Это единственное место,
где разрешено читать эти заголовки: правило Semgrep запрещает их чтение
в любом другом месте.

### Кто клиент: `Resolve` в `forwarded.go`

```go
peer, ok := parsePeer(req.RemoteAddr)
if !ok {
    return Client{}
}
```

`req.RemoteAddr` — адрес соединения вида `10.0.0.1:40000`. Его сообщает ядро,
атакующий подделать его не может. Если разобрать не удалось (для TCP такого
не бывает), возвращаем пустой результат: «клиент неизвестен», а не догадку.

```go
c := Client{Addr: peer, Peer: peer}
if !r.trusts(peer) {
    return c
}
```

Соединение не от нашего прокси — клиент и есть адрес соединения.
**Заголовок в этом случае даже не читается.** Это главное свойство шага:
пока администратор не перечислил свои прокси, `X-Forwarded-For` для сенсора
не существует.

```go
values := req.Header.Values(headerXFF)
```

`Values`, а не `Get`: `Get` вернул бы только первую строку заголовка.
Часть прокси добавляет свою запись не в конец существующей строки,
а новой строкой. Возьми мы первую строку — получили бы ту, что прислал
атакующий.

```go
for i := len(values) - 1; i >= 0; i-- {
    rest := values[i]
    for rest != "" {
        rest, field = cutLast(rest)
```

Два цикла: по строкам заголовка с последней и по элементам строки с правого.
`cutLast` отрезает всё после последней запятой. Почему не `strings.Split`:
заголовок может быть в десятки килобайт, и атакующий может положить слева
тысячи элементов. `Split` выделил бы память под каждый. Нам нужны обычно
один-два правых элемента, и до левых мы не доходим.

```go
        fields++
        if fields > maxFields {
            return c.broken(verified)
        }
```

Предел — 32 элемента, считая пустые. Считаем до разбора, так что число
итераций ограничено при любом содержимом. Дойти до этого предела можно,
только если все 32 адреса справа — наши прокси. Такого не бывает: это петля
между прокси или ошибка настройки.

```go
        field = strings.Trim(field, " \t")
        if field == "" {
            continue
        }
```

Пробелы и табуляция вокруг элемента разрешены синтаксисом списков HTTP.
Именно они, а не `strings.TrimSpace`, который снял бы и неразрывный пробел
` `. Такой пробел — не часть синтаксиса HTTP, запись с ним не разберётся,
и цепочка оборвётся. Пустые элементы (`a,,b`) HTTP велит пропускать.

```go
        addr, ok := parseHop(field)
        if !ok {
            return c.broken(verified)
        }
```

`parseHop` принимает IP, IP с портом и IPv6 в скобках. Всё остальное —
`unknown`, имя хоста, мусор — обрывает цепочку. Важно, **где** стоит мусор.
Слева от адреса клиента до него просто не доходим: `"<script>, 203.0.113.7"`
даст клиента `203.0.113.7`. Справа от клиента, в части, которую писали наши
прокси, мусор значит, что прокси настроен неправильно.

```go
func (c Client) broken(verified []netip.Addr) Client {
    c.Addr = netip.Addr{}
    c.ChainBroken = true
```

При обрыве адрес клиента — **нулевой**, а не «последний известный».
Последний известный — адрес нашего же балансировщика. Если бы реакция
этапа 4 заблокировала его, сайт перестал бы работать для всех. Нулевой адрес
вынуждает код, который им пользуется, обработать случай «клиент неизвестен».

```go
        verified = append(verified, addr)
        if !r.trusts(addr) {
            c.Addr = addr
            c.chain = reversed(verified)
            return c
        }
```

Первый адрес не из доверенных сетей — клиент. `chain` запоминает проверенную
часть цепочки: клиент и наши прокси после него. Её сенсор и передаст
приложению.

```go
if len(verified) > 0 {
    c.Addr = verified[len(verified)-1]
}
```

Все адреса оказались нашими — запрос начался внутри своей сети. Клиент —
самый левый адрес: его тоже записал наш прокси.

### Какой адрес считать адресом: `parseHop` и `normalize`

```go
if len(s) > maxHopLen {
    return netip.Addr{}, false
}
```

64 символа хватает на самый длинный IPv6 с портом в скобках. Более длинная
запись — точно не адрес, разбирать её незачем.

```go
addr, err := netip.ParseAddr(s)
if err != nil {
    ap, errPort := netip.ParseAddrPort(s)
```

Сначала «просто IP», затем «IP с портом». `ParseAddrPort` сам следит
за скобками: IPv6 с портом — только в скобках (`[2001:db8::1]:443`),
IPv4 в скобках — ошибка. Без скобок `2001:db8::7:443` — это не «адрес
и порт», а другой корректный IPv6-адрес. Поэтому скобки и обязательны.

```go
if addr.Zone() != "" {
    return netip.Addr{}, false
}
return normalize(addr), true
```

Зона IPv6 (`fe80::1%eth0`) имеет смысл только внутри одной машины.
`normalize` приводит `::ffff:10.0.0.1` к `10.0.0.1`. Без этого сеть
`10.0.0.0/8` не содержала бы такой адрес: прокси, который пишет IPv4
в форме IPv6, не опознался бы как доверенный.

### Что уходит приложению: `SetOutbound` в `outbound.go`

```go
for name := range out {
    norm := normalizeName(name)
    if !isForwardingHeader(norm) {
        continue
    }
```

Перебираем все заголовки исходящего запроса. `normalizeName` приводит имя
к нижнему регистру и заменяет `_` на `-`. `isForwardingHeader` — это
`forwarded`, всё с префиксом `x-forwarded-` и список `X-Real-IP` и подобных.
Префикс, а не список, закрывает ошибку шага 3 целиком: удалятся и
`X-Forwarded-Port`, и заголовок, о котором мы сегодня не знаем.

```go
    switch {
    case !c.ViaTrustedProxy,
        name != http.CanonicalHeaderKey(norm),
        norm == "forwarded",
        norm == "x-forwarded-for", norm == "x-forwarded-host", norm == "x-forwarded-proto":
        delete(out, name)
    }
```

Удаляем, если выполнено любое из условий:

- соединение не от доверенного прокси — удаляем всё;
- имя не в канонической записи. Сервер Go превращает `X_Forwarded_For`
  в `X_forwarded_for`. Для Go это отдельный заголовок, а PHP-FPM, CGI
  и часть WSGI-серверов переводят `-` в `_` и увидят там `X-Forwarded-For`.
  Атакующий спрятал бы подделку от сенсора и доставил приложению.
  Настоящие прокси подчёркиваний не пишут, поэтому удаляем всегда;
- `Forwarded` — сенсор его не поддерживает (ADR-0022, «Альтернативы»);
- три заголовка, которые сенсор выставит ниже сам.

От доверенного прокси остальные заголовки остаются: `X-Forwarded-Port`,
`X-Forwarded-Prefix`, `X-Real-IP` — это утверждения нашего прокси.

```go
if c.Peer.IsValid() {
    ...
    b.WriteString(c.Peer.String())
    out.Set(headerXFF, b.String())
}
```

`X-Forwarded-For` собирается из проверенной цепочки и адреса соединения.
Адреса записываются заново через `String()`, а не копируются из входящего
заголовка: `[2001:DB8:0::7]:443` станет `2001:db8::7`. До приложения доходят
только адреса, которые сенсор разобрал сам, без мусора и портов.

```go
if v := trustedValues(in, c, headerXFH); v != nil {
    out[headerXFH] = v
} else if in.Host != "" {
    out.Set(headerXFH, in.Host)
}
```

`X-Forwarded-Host` и `-Proto`: от доверенного прокси — его значение, иначе —
наше. `trustedValues` читает заголовок клиента, **только если** соединение
от доверенного прокси, и возвращает копию. Без копии исходящий и входящий
запросы делили бы одну память: правка одного незаметно меняла бы другой.

Почему значения прокси так важны: балансировщик снимает TLS и сообщает
`X-Forwarded-Proto: https`. Замени сенсор его на `http` по своему соединению —
приложение решит, что запрос пришёл по HTTP, и перенаправит на HTTPS.
Браузер придёт снова по HTTPS, и так по кругу.

### Проверка списка доверенных прокси: `parseTrustedPrefix` в `config.go`

```go
if parsed != parsed.Masked() {
    return p, fmt.Errorf("%q: адрес сети содержит биты узла; имелась в виду сеть %s или один адрес %s?", ...)
}
```

`10.0.0.1/8` Go разбирает без ошибки, но что имел в виду администратор:
сеть `10.0.0.0/8` (16 миллионов адресов) или один адрес `10.0.0.1`?
Не угадываем, отказываемся стартовать и называем оба варианта.

```go
if p.Addr().Is4In6() {
```

Сеть в записи `::ffff:…` не совпала бы ни с одним адресом, потому что
адреса сенсор приводит к IPv4. Доверенный прокси молча перестал бы быть
доверенным.

```go
if p.Bits() < minBits {
```

Сети шире `/8` (IPv4) и `/7` (IPv6) — отказ. Самые широкие настоящие
частные сети — `10.0.0.0/8` и `fc00::/7`, шире не бывает «сети своих
прокси». Это ловит классическую ошибку `0.0.0.0/0` («не работало —
разрешил всем»). Узкие, но чужие сети проверка не поймает. Это решение
администратора, и оно видно в логе при запуске (`trusted_proxies`).

## Граница доверия

| Данные | Откуда | Что с ними делается |
|---|---|---|
| адрес соединения | ядро | доверенный; по нему решается, читать ли заголовки |
| `X-Forwarded-For` от недоверенного соединения | атакующий | не читается, удаляется |
| `X-Forwarded-For` от доверенного прокси, правая часть | наш прокси | разбирается справа налево до первого чужого адреса |
| `X-Forwarded-For` левее адреса клиента | атакующий | не читается, приложению не передаётся |
| `X-Forwarded-*`, `X-Real-IP` и подобные | атакующий или наш прокси | передаются, только если соединение от доверенного прокси |
| варианты с `_` | атакующий | удаляются всегда |
| `SENSOR_TRUSTED_PROXIES` | администратор | строгая проверка при запуске; только слой запуска, не из веб-интерфейса |

## Что может пойти не так

- **T1 — подделка адреса клиента.** Закрыто правилом правого недоверенного
  адреса и пустым списком по умолчанию. Остаётся: администратор доверил
  всю внутреннюю сеть, и атакующий, закрепившийся в ней, подставляет адрес.
  Это видно в логе при запуске и описано в guide.
- **Доверенный прокси сам пропускает заголовки клиента.** Например,
  балансировщик передаёт присланный клиентом `X-Forwarded-Proto` без
  изменений. Сенсор его тоже передаст — так же было бы и без сенсора.
- **T18 — сенсор и приложение понимают заголовки по-разному.** Варианты
  с подчёркиванием удаляются. `X-Original-URL` и `X-Rewrite-URL`, которыми
  некоторые фреймворки переопределяют путь, — другой класс атак: записано
  в технический долг на шаг 8.
- **Ошибки в разборе.** Разбор — стандартный `net/netip`, свой код только
  режет строку по запятым. Фаззинг-тест проверяет: разбор не паникует,
  а найденный адрес всегда взят либо из соединения, либо из проверенной
  цепочки.

## Проверьте руками

Нужны Go и Python. Приложение — десять строк на Python, которые возвращают
в ответе полученные заголовки. Так видно ровно то, что получает приложение
за сенсором.

```bash
# Терминал 1 — «приложение», показывает полученные заголовки
python3 -c '
import http.server as h
class H(h.BaseHTTPRequestHandler):
    def do_GET(s):
        s.send_response(200); s.end_headers(); s.wfile.write(str(s.headers).encode())
h.HTTPServer(("127.0.0.1", 3000), H).serve_forever()'

# Терминал 2 — сенсор без доверенных прокси
cd sensor
SENSOR_UPSTREAM_URL=http://127.0.0.1:3000 SENSOR_LISTEN_ADDR=127.0.0.1:8080 go run ./cmd/sensor

# Терминал 3 — атакующий подставляет заголовки
curl -s http://127.0.0.1:8080/ -H 'X-Forwarded-For: 1.2.3.4' \
  -H 'X-Forwarded-Proto: https' -H 'X-Forwarded-Prefix: /evil' \
  -H 'X_Forwarded_For: 1.2.3.4' | grep -i forwarded
```

Ожидается — подделок нет, только значения сенсора:

```
X-Forwarded-For: 127.0.0.1
X-Forwarded-Host: 127.0.0.1:8080
X-Forwarded-Proto: http
```

Теперь притворимся балансировщиком: перезапустите сенсор
с `SENSOR_TRUSTED_PROXIES=127.0.0.1` и выполните:

```bash
curl -s http://127.0.0.1:8080/ -H 'X-Forwarded-For: 1.2.3.4, 203.0.113.7' \
  -H 'X-Forwarded-Proto: https' -H 'X-Forwarded-Prefix: /shop' \
  -H 'X_Forwarded_For: 1.2.3.4' | grep -i forwarded
```

Ожидается — `1.2.3.4` слева отброшен, значения «балансировщика» сохранены,
вариант с подчёркиванием удалён:

```
X-Forwarded-For: 203.0.113.7, 127.0.0.1
X-Forwarded-Host: 127.0.0.1:8080
X-Forwarded-Prefix: /shop
X-Forwarded-Proto: https
```

В логе сенсора при запуске — `"trusted_proxies":["127.0.0.1/32"]`.

И ошибка конфигурации:

```bash
SENSOR_UPSTREAM_URL=http://127.0.0.1:3000 SENSOR_TRUSTED_PROXIES=0.0.0.0/0 go run ./cmd/sensor
# ошибка конфигурации: SENSOR_TRUSTED_PROXIES: "0.0.0.0/0": сеть шире /8 ...
# exit status 2
```

## Вопросы для самопроверки

1. Атакующий подключается к сенсору напрямую, минуя балансировщик, и
   присылает `X-Forwarded-For: <адрес балансировщика>`. Какой адрес клиента
   запишет сенсор?

   <details><summary>Ответ</summary>

   Собственный адрес атакующего — адрес соединения. Соединение пришло
   не из доверенной сети, и `Resolve` возвращается до чтения заголовка.
   Подставить адрес доверенного прокси в заголовок бесполезно: доверие
   решается по соединению, которое подделать нельзя.

   </details>

2. Почему сенсор берёт самый правый недоверенный адрес, а не самый левый?
   Приведите цепочку, на которой они различаются.

   <details><summary>Ответ</summary>

   Каждый прокси дописывает адрес справа, поэтому правую часть написали
   наши прокси, а левую — кто угодно. Атакующий `203.0.113.7` присылает
   `X-Forwarded-For: 1.2.3.4`, балансировщик дописывает его адрес:
   `1.2.3.4, 203.0.113.7`. Самый левый — `1.2.3.4`, подделка. Правый
   недоверенный — `203.0.113.7`, настоящий адрес.

   </details>

3. Доверенный прокси прислал `X-Forwarded-For: 203.0.113.7, unknown`.
   Какой адрес клиента запишет сенсор и почему не `10.0.0.1` — адрес прокси?

   <details><summary>Ответ</summary>

   Никакой: адрес нулевой, `ChainBroken = true`. `unknown` стоит в части,
   которую писал наш прокси, значит, он настроен неправильно, и где
   настоящий клиент, сказать нельзя. Адрес прокси не подставляется
   намеренно: реакция по нему на этапе 4 заблокировала бы всех
   пользователей сразу.

   </details>

4. Зачем удалять `X_Forwarded_For` с подчёркиванием, если сенсор его
   не читает, а для Go это вообще другой заголовок?

   <details><summary>Ответ</summary>

   Потому что приложение может считать его тем же `X-Forwarded-For`:
   CGI, PHP-FPM и часть WSGI-серверов переводят `-` в `_` в именах
   заголовков. Атакующий спрятал бы подделку от сенсора и доставил её
   приложению. Это расхождение в разборе запроса (T18). Настоящие прокси
   подчёркиваний не пишут, поэтому удаляем всегда, даже от доверенных.

   </details>

5. Почему от доверенного прокси `X-Forwarded-Proto` передаётся как есть,
   а не выставляется сенсором по своему соединению, как для остальных?

   <details><summary>Ответ</summary>

   Балансировщик снимает TLS, и до сенсора запрос доходит по HTTP. Сенсор
   выставил бы `http`, и приложение, требующее HTTPS, перенаправило бы
   браузер на HTTPS. Браузер пришёл бы снова через тот же балансировщик —
   и так по кругу. Схему исходного запроса знает только балансировщик,
   и это его утверждение, которому мы доверяем.

   </details>
