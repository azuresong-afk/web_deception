# Этап 2, шаг 10а. Наживки в заголовке и robots.txt, цепочки

> Снимок на момент шага: 2026-09-24. Решение — в
> [ADR-0027](../../adr/0027-lures-header-robots.md). Текущее состояние —
> в [guide.md](../../guide.md), раздел «Сенсор».

## Что и зачем

До этого шага ловушки ловили тех, кто перебирает известные пути:
`/.env`, `/.git/config`. Целевой атакующий так не работает — он читает
сайт: заголовки ответов, `robots.txt`, HTML. Наживка — «случайная»
подсказка в ответе сайта: строка `Disallow: /admin-backup`, заголовок
`X-Debug-Trace: /internal/debug/trace`. Ловушка — путь, куда она ведёт.
Касание записывает, какая наживка привела, и по цепочке видно, как глубоко
атакующий изучил сайт.

Это первая **правка ответов приложения**, а не ответ вместо него. Всё, что
сенсор допишет, увидят все пользователи сайта. Поэтому шаг 10 разделён:
в 10а — заголовок и `robots.txt`, где правка простая; в 10б — правка HTML,
самое рискованное место этапа, со своим решением и фаззингом.

## Понятия

- **Наживка и ловушка** — наживку видят, ловушку трогают. См.
  [глоссарий](../../glossary.md).
- **robots.txt** — просьба к поисковым роботам не ходить по путям.
  Честные роботы её выполняют, сканеры читают как карту.
- **Цепочка «наживка → ловушка»** — поле `lure_id` в касании: откуда
  атакующий узнал путь.
- **Сжатие ответа** — сервер сжимает тело (gzip, Brotli), если клиент
  разрешил это заголовком `Accept-Encoding`. Сжатое тело не дополнить,
  не распаковав.
- **ETag** — «отпечаток» ответа для вопроса «изменилось ли?». После правки
  тела он неверен.
- **ModifyResponse** — функция, которую `httputil.ReverseProxy` вызывает
  с ответом приложения до отправки клиенту. Ошибка из неё — это `502`.
- **Переопределение метода** — `POST` с `X-HTTP-Method-Override: DELETE`,
  который фреймворк обрабатывает как `DELETE`.

## Как это работает

```
запрос ─▶ … ─▶ Guard/Detector ─▶ ReverseProxy.Rewrite ─▶ lure.Prepare ─▶ приложение
                                                                              │
клиент ◀─ … ◀─ ReverseProxy ◀─────────────────────── lure.Modify ◀────────────┘
                                                        ├─ заголовок X-Debug-Trace
                                                        └─ robots.txt: дописать или вместо 404
```

- **Prepare** — для `GET /robots.txt` просит у приложения ответ без сжатия
  (`Accept-Encoding: identity`) и без условий (`If-None-Match`, `Range`).
- **Modify** — ставит заголовок на каждый ответ приложения и дополняет
  `robots.txt`.
- **Detector** ставит тот же заголовок и на ответы ловушек.

Цепочки из учебного набора:

| Что прочитал атакующий | Куда пошёл | Касание |
|---|---|---|
| `robots.txt`: `Disallow: /admin-backup` (№4) | `GET /admin-backup` | medium, `lure_id: robots-admin` |
| заголовок `X-Debug-Trace` (№7) | `GET /internal/debug/trace` | medium, `lure_id: debug-header` |
| документация `/internal/api/v2/docs` (№6) | `POST /api/internal/v1/users/export` с JSON (№8) | high, `lure_id: api-docs` |

Наживка к самой документации — HTML-комментарий — появится в 10б.

## Разбор кода

### Имя заголовка-наживки: `validateLureHeader` в `policy/lure.go`

```go
case len(name) > maxLureHeaderLen || !lureHeaderRe.MatchString(name):
	add("%s.header: до %d символов, «X-» и слова из A-Z a-z 0-9 через дефис", ...)
...
for _, denied := range deniedLureHeaders {
	if strings.HasPrefix(lower, denied) {
		add("%s.header: %q понимают браузеры, прокси или приложения — не годится для наживки", ...)
```

- `lureHeaderRe` — `^X-[A-Za-z0-9]+(-[A-Za-z0-9]+)*$`. Ни пробела, ни `:`,
  ни перевода строки: политика не может дописать в ответ второй заголовок
  (`X-A\r\nSet-Cookie: ...` отвергается).
- `deniedLureHeaders` — начала имён, которые кто-то понимает. Главный
  пример — `X-Accel-Redirect`. Браузеры его игнорируют, но nginx **перед**
  сенсором, получив его в ответе, отдаст указанный внутренний файл.
  Наживка превратилась бы в чтение файлов сервера. `X-Robots-Tag` убрал бы
  сайт из поиска, `X-Frame-Options` — ослабил бы защиту страниц.
- Сравнение без учёта регистра: `x-accel-redirect` — тот же заголовок.

### Кто ведёт к ловушке: `refer` в `validateLures`

```go
refer := func(at, from, to string) {
	if prev, ok := referrer[to]; ok && prev != from {
		add("%s: к ловушке %q уже ведёт %q — ...", at, to, prev)
		return
	}
	referrer[to] = from
}
```

Одна ловушка — один источник. Если к `/admin-backup` вели бы и
`robots.txt`, и заголовок, касание не сказало бы, что прочитал атакующий.
`prev != from` — одна страница может упомянуть ловушку дважды, это
не конфликт (нашёл тест: сначала это отвергалось).

### Ссылки между ловушками: `{{trap:id}}`

```go
matches := trapRefRe.FindAllStringSubmatch(body, -1)
if strings.Count(body, trapRefPrefix) != len(matches) {
	add("%s: ссылка на ловушку записывается как {{trap:id}}, id из a-z 0-9 -", at)
}
size := len(body)
for _, m := range matches {
	...
	size += len(target.Path) - len(m[0])
	refer(at, t.ID, target.ID)
}
if size > maxBodyBytes {
	add("%s: после подстановки путей больше %d байт", at, maxBodyBytes)
}
```

- Каждое `{{trap:` обязано быть полной ссылкой: опечатка (`{{trap:API}}`)
  иначе осталась бы в ответе как есть.
- `size` считается **после** подстановки. Ссылка — 19 символов, путь —
  до 256. Тело в 64 КиБ из одних ссылок выросло бы в 13 раз, а 256 таких
  ловушек — сотни мегабайт памяти сенсора из одной политики (T15).
- Подстановка — в `compileLures`, один раз при разборе, а не на каждом
  запросе.

### Правка ответа: `Modify` в `lure/lure.go`

```go
orig := resp.Body
var consumed []byte
defer func() {
	if rec := recover(); rec != nil {
		inj.Stats.Skipped[SkipPanic].Add(1)
		if consumed != nil {
			resp.Body = readCloser{io.MultiReader(bytes.NewReader(consumed), orig), orig}
		}
		inj.cfg.OnPanic(resp.Request, rec, "lure")
	}
}()
```

- `Modify` вызывается из `ReverseProxy`, **вне** `failopen.Guard`. Поэтому
  своя защита: `recover` перехватывает панику.
- `consumed` — уже прочитанная часть тела. Если правка упала после чтения,
  тело собирается обратно: прочитанное, затем непрочитанное. Клиент
  получает ответ приложения как есть.
- `OnPanic` — это `Guard.RecordPanic`: те же счётчик, событие
  `detection.panic` (теперь со `stage: lure`) и стек в лог не чаще раза
  в минуту. Одно место на весь сенсор.
- `Modify` всегда возвращает `nil`: ошибка из `ModifyResponse` — это `502`,
  а сбой наживки не должен ломать сайт.

### Заголовок: `addHeaders`

```go
if resp.Header.Get(l.Header) != "" {
	inj.Stats.Skipped[SkipHeaderExists].Add(1)
	continue
}
resp.Header.Set(l.Header, l.Path())
```

Если у приложения уже есть заголовок с таким именем, сенсор его не трогает:
значение — дело приложения. Имя и путь проверены при разборе политики.

### robots.txt: `robots`

```go
switch resp.StatusCode {
case http.StatusOK:
case http.StatusNotFound:
	// свой robots.txt
default:
	inj.Stats.Skipped[SkipRobotsStatus].Add(1)
	return
}
```

- `200` — дописать. `404` — ответить своим: «файла нет» и «запрещены
  только ловушки» для роботов значат почти одно и то же.
- Всё остальное — как есть. `5xx` на `robots.txt` Google понимает как
  «сайт недоступен, не заходить никуда», и подмена изменила бы индексацию.

```go
data, err := io.ReadAll(io.LimitReader(orig, maxRobotsBytes+1))
*consumed = data
if err != nil || len(data) > maxRobotsBytes {
	resp.Body = readCloser{io.MultiReader(bytes.NewReader(data), errReader{err, orig}), orig}
	*consumed = nil
	return
}
```

- `LimitReader(…, 512 КиБ + 1)` — ответ приложения доверенный лишь
  частично; больше предела — отдаём как есть, не держа в памяти.
- `*consumed = data` — сразу после чтения, до любой другой работы: паника
  дальше не потеряет прочитанное. В первой версии прочитанное возвращалось
  из функции, и паника между чтением и возвратом теряла бы ответ — нашёл
  при чтении своего кода.
- `errReader{err, orig}` — обрыв тела у приложения доходит до клиента тем же
  обрывом. Без этого клиент получил бы обрезанный `robots.txt` с чистым
  концом, похожий на целый.

```go
if len(data) > 0 && data[len(data)-1] != '\n' {
	b.WriteByte('\n')
}
b.WriteByte('\n')
b.WriteString(robotsGroup(paths))
```

У Juice Shop последняя строка без перевода строки (`Disallow: /ftp`), и
без первой проверки получилось бы `Disallow: /ftpUser-agent: *`. Своя
группа `User-agent: *` — в конце: по RFC 9309 группы одного робота
объединяются.

### Заголовок на ответах сенсора: `addLureHeaders` в `decoy/decoy.go`

```go
func addLureHeaders(w http.ResponseWriter, p *policy.Compiled) {
	for _, l := range p.HeaderLures() {
		w.Header().Set(l.Header, l.Path())
	}
}
```

Вызывается перед ответом ловушки и отказом в preflight. Иначе у всех
ответов сайта был бы `X-Debug-Trace`, а у ответов ловушек — нет.

### Переопределение метода: `acceptsMethod` в `policy/policy.go`

```go
if slices.Contains(t.Methods, r.Method) {
	return true
}
if r.Method != http.MethodPost {
	return false
}
for _, h := range methodOverrideHeaders {
	if v := r.Header.Get(h); v != "" && slices.Contains(t.Methods, upperASCII(strings.TrimSpace(v))) {
		return true
	}
}
```

- Только у `POST`: так делают Express, Laravel, Rails.
- Значение от клиента только сравнивается со списком ловушки.
- В `Preflighted` такой заголовок — признак «непростого» запроса: браузер
  его не ставит, скрипт с чужого сайта добавит только после preflight.

## Находки

1. **Ответ ловушки без заголовка-наживки выдаёт ловушку.** На стенде все
   ответы Juice Shop несли `X-Debug-Trace`, а `/.env` от сенсора — нет.
   Сравнив заголовки, атакующий нашёл бы все ловушки. Исправлено:
   `addLureHeaders`.
2. **Juice Shop сжимает ответы Brotli.** Распаковщика Brotli в стандартной
   библиотеке Go нет. Поэтому за `robots.txt` сенсор просит ответ без
   сжатия. Для HTML в 10б понадобится то же решение.
3. **Тест с «липкой» ошибкой.** Мутация «обрыв тела теряет ошибку» выжила:
   тестовое тело повторяло ошибку при каждом чтении, и защита была
   не нужна. Настоящее тело может отдать ошибку один раз. Тест переписан,
   мутация поймана.
4. **Проверки в тестах.** Линтер `bodyclose` отметил 18 искусственных
   ответов, Semgrep — вывод ошибки чтения тела в `t.Fatalf`. Исправлено
   без подавления проверок: тесты описывают ответ приложения структурой,
   а собирает и закрывает его одна функция `run`.

## Граница доверия

- **Запрос клиента.** Путь и метод (`GET /robots.txt`) только сравниваются.
  `X-HTTP-Method-Override` только сравнивается со списком ловушки.
- **Ответ приложения** доверенный лишь частично. Тело `robots.txt`
  читается с пределом 512 КиБ, код ответа, `Content-Type`
  и `Content-Encoding` только сравниваются. Приложение, проигнорировавшее
  просьбу не сжимать, получит свой ответ обратно без изменений.
- **Политика** (T15). В ответ сайта попадают только проверенный путь
  ловушки и имя заголовка из безопасного набора. Опасные имена запрещены.

## Что может пойти не так

- **T15 — вредоносная политика.** Своего текста в ответы не вставить,
  опасные заголовки запрещены, тело ловушки ограничено после подстановки.
- **T5 — распознавание.** Заголовок-наживка теперь и на ответах ловушек.
  Остаются заголовки самого приложения (`Server`, `X-Recruiting`
  у Juice Shop), которых нет у ловушек, — этап 8.
- **T2 — межсайтовое срабатывание.** Путь из наживки открывается обычным
  `GET`, поэтому уверенность таких ловушек `medium`, а `sec_fetch` покажет
  межсайтовый запрос.
- **Поломка сайта.** Правка — fail-open. `5xx`, сжатые и большие
  `robots.txt` не трогаются. Заголовок не заменяет заголовок приложения.
- **T18 — сенсор и приложение понимают запрос по-разному.** Для
  переопределения метода закрыто.

## Вопросы для самопроверки

1. Почему за `robots.txt` сенсор просит у приложения ответ без сжатия
   и без условий (`If-None-Match`)? Что было бы иначе?

   <details><summary>Ответ</summary>

   Сжатое тело не дополнить, не распаковав. Juice Shop сжимает Brotli,
   а распаковщика Brotli в стандартной библиотеке Go нет. Ответ пришлось
   бы отдать без наживки. С условием приложение ответило бы `304` без
   тела, и у клиента (или CDN) осталась бы старая копия `robots.txt` —
   без наживок или с наживками прежней политики.

   </details>

2. Браузеры заголовок `X-Accel-Redirect` игнорируют. Почему он всё равно
   не может быть наживкой?

   <details><summary>Ответ</summary>

   Его понимает nginx. Если nginx стоит перед сенсором, то, получив
   `X-Accel-Redirect: /путь` в ответе, он отдаст клиенту внутренний файл
   по этому пути. Путь в наживке — это путь ловушки, но политика,
   подменённая при взломе control plane (T15), превратила бы наживку
   в чтение файлов сервера. Поэтому запрещены заголовки, которые понимает
   кто-то кроме атакующего.

   </details>

3. Почему `robots.txt` с ответом `404` сенсор заменяет своим, а ответ
   `503` оставляет как есть?

   <details><summary>Ответ</summary>

   Для поисковых роботов «файла нет» (`404`) значит «ходить можно везде».
   Наш `robots.txt` запрещает только пути ловушек, то есть смысл почти
   тот же. `5xx` на `robots.txt` Google понимает как «сайт недоступен,
   не заходить никуда». Заменив его на `200`, сенсор разрешил бы
   индексацию, которую приложение (временно) запретило.

   </details>

4. Зачем заголовок-наживку ставить и на ответы ловушек, которые даёт
   сам сенсор?

   <details><summary>Ответ</summary>

   Заголовок стоит на каждом ответе приложения. Если бы у ответов ловушек
   его не было, атакующий, сравнив заголовки, отличил бы ловушку
   от настоящего пути (T5). Проверив несколько путей из словаря, он бы
   нашёл все ловушки и дальше обходил их.

   </details>

5. В теле фейковой документации записано `{{trap:api-export}}`, а не путь.
   Что это даёт, и почему предел тела проверяется после подстановки путей?

   <details><summary>Ответ</summary>

   Сенсор подставит путь ловушки `api-export` сам. Если путь в политике
   изменят, документация не разойдётся с ловушкой. Кроме того, ссылка
   записывает цепочку: касание метода получает `lure_id: api-docs`.
   Предел — после подстановки, потому что ссылка короче пути: тело
   из тысяч ссылок в 64 КиБ выросло бы в десятки раз, и одна политика
   заняла бы сотни мегабайт памяти сенсора (T15).

   </details>
