# Этап 2, шаг 2. Control plane на distroless

> Снимок на момент шага: 2026-09-24. Решение — в
> [ADR-0020](../../adr/0020-controlplane-distroless.md). Текущее состояние —
> в [guide.md](../../guide.md), раздел «Control plane».

## Что и зачем

Образ control plane был построен на урезанном Debian: 87 пакетов, среди них
`sh`, `bash`, `apt`, `perl`. Для работы приложения всё это не нужно,
а после взлома пригодится атакующему. К тому же Trivy каждую неделю показывал
44 уязвимости HIGH без исправлений в этих ненужных пакетах. Такой отчёт
быстро перестают читать.

Шаг переводит control plane на distroless — образ, где есть только Python
и библиотеки, без которых он не запустится. Заодно control plane переходит
с Python 3.12 на 3.13: другой версии Python в distroless нет.

## Понятия

- **Distroless** — образ без дистрибутива вокруг программы: нет shell,
  менеджера пакетов, утилит.
- **Многостадийная сборка** — в Dockerfile несколько `FROM`. Первая стадия
  (сборка) содержит всё нужное для установки. Вторая (рантайм) начинается
  с чистого минимального образа и забирает из первой только результат.
  Инструменты сборки в итоговый образ не попадают.
- **Минорная и патч-версия.** В `3.13.5` минорная версия — `3.13`,
  патч — `5`. Внутри минорной версии совпадают формат байткода
  и двоичный интерфейс (ABI), поэтому пакеты, установленные на 3.13.15,
  работают на 3.13.5.
- **Код выхода 127** — так shell и Docker сообщают, что запускаемой
  программы нет.

## Как это работает

```
 стадия сборки: python:3.13-slim              стадия рантайма: distroless/python3
 ┌───────────────────────────────┐          ┌─────────────────────────────────┐
 │ pip ставит uv (хеши проверены)│          │ /usr/bin/python3 (Debian 3.13)  │
 │ uv ставит зависимости         │          │ glibc, OpenSSL, zlib …          │
 │   строго по uv.lock → /app/deps ├── COPY ─▶ /app/deps   (владелец root)      │
 │ компилирует наш код → /app/src │── COPY ─▶ /app/src    (владелец root)      │
 │ (здесь есть shell, apt, pip)  │          │ процесс от пользователя 65532   │
 └───────────────────────────────┘          │ нет sh, bash, apt, pip, perl    │
         в итоговый образ не попадает        └─────────────────────────────────┘
```

## Разбор кода

### Dockerfile: стадия сборки

Файл `deploy/docker/controlplane.Dockerfile`.

```dockerfile
FROM python:3.13-slim-trixie@sha256:8d9d… AS build
```

Базовый образ сборки — официальный Python той же минорной версии, что
и в рантайме. `@sha256:…` — digest: образ закреплён по содержимому,
а не по имени, и подменить его нельзя. `AS build` — имя стадии, чтобы
потом забрать из неё файлы.

```dockerfile
RUN uv export --frozen --no-dev --no-emit-project --format requirements-txt \
        --output-file /tmp/requirements.txt \
 && uv pip install --no-deps --require-hashes --only-binary :all: \
        --compile-bytecode --target /app/deps -r /tmp/requirements.txt
```

Построчно:

- `uv export --frozen` — выписать список пакетов из `uv.lock`, ничего
  не пересчитывая. В списке у каждого пакета хеш файла.
- `--no-dev` — без pytest, mypy, ruff: в продакшене они не нужны.
- `--no-emit-project` — без самого control plane: его код копируется отдельно.
- `uv pip install --no-deps` — ставить ровно то, что в списке, и не искать
  зависимости самостоятельно.
- `--require-hashes` — если хеш скачанного файла не совпал со списком,
  установка падает. Это защита от подмены пакета на PyPI или по дороге.
- `--only-binary :all:` — только готовые колёса. Сборка из исходников
  исполняет код пакета во время установки.
- `--compile-bytecode` — сразу создать `.pyc`: в рантайме файловая система
  только для чтения.
- `--target /app/deps` — в обычный каталог, а не в виртуальное окружение.
  Виртуальное окружение помнит путь к Python сборки (`/usr/local/bin`),
  а в рантайме Python лежит в `/usr/bin`.

### Dockerfile: стадия рантайма

```dockerfile
FROM gcr.io/distroless/python3-debian13:nonroot@sha256:8ee2…
COPY --from=build /app/deps /app/deps
COPY --from=build /app/src /app/src
```

Новый `FROM` начинает образ с нуля. Из стадии сборки берутся только два
каталога. Всё остальное — pip, uv, shell, apt сборочного образа — остаётся
в стадии сборки и в итоговый образ не попадает. Файлы копируются
с владельцем root, а процесс работает от 65532. Поэтому приложение не может
изменить собственный код, даже если его взломали.

```dockerfile
ENV PYTHONPATH="/app/src:/app/deps" \
    PYTHONSAFEPATH=1 \
```

- `PYTHONPATH` — где Python ищет модули: наш код и зависимости.
- `PYTHONSAFEPATH=1` — не искать модули в текущем каталоге. Без этого
  файл `json.py`, оказавшийся в рабочем каталоге, был бы импортирован
  вместо стандартного модуля `json`.

```dockerfile
USER 65532:65532
HEALTHCHECK … CMD ["/usr/bin/python3", "-m", "webdeception_cp.healthcheck"]
ENTRYPOINT ["/usr/bin/python3", "-m", "webdeception_cp"]
```

Форма со скобками `["…"]` запускает программу напрямую. Строковая форма
(`CMD python3 -m …`) запускала бы её через `/bin/sh -c`, а shell в образе
нет. Поэтому ещё на этапе 1 проверку здоровья сделали модулем Python,
а не вызовом `curl`.

### Правило D6: Dockerfile продукта обязан быть distroless

Файл `scripts/check_containers.py`, функция `check_dockerfile`.

```python
stages: dict[str, str] = {}
...
if instruction == "FROM":
    image, alias = _parse_from(args)
    final_base = stages.get(image.lower(), image)
    ...
    if alias:
        stages[alias.lower()] = final_base
```

Скрипт идёт по инструкциям Dockerfile сверху вниз. На каждом `FROM` он
запоминает, от какого образа строится стадия. Если стадия строится
от другой стадии (`FROM base`), скрипт подставляет образ, с которого
началась та. После последнего `FROM` в `final_base` — настоящая основа
итогового образа.

```python
if final_base and not final_base.startswith(_DISTROLESS_PREFIX):
    out.append(Violation(where, "D6", ...))
```

Если основа не начинается с `gcr.io/distroless/`, это нарушение. Второе
нарушение — отладочный вариант distroless (тег `debug`): формально это
distroless, но в нём есть busybox с shell в `/busybox/sh`. Эту дыру нашли
при ревью собственного изменения — первая версия правила её пропускала.

### Проверка собранного образа: make check-images

Правило D6 читает Dockerfile, но не видит, что на самом деле оказалось
в образе. Вторая проверка запускает сам образ:

```make
docker run --rm --network none --entrypoint "$$prog" "$$img" >/dev/null 2>&1; \
rc=$$?; \
if [ "$$rc" -ne 127 ]; then … exit 1; fi
```

Для каждой программы из списка (`/bin/sh`, `/bin/bash`, `/usr/bin/perl`, …)
Docker пытается запустить её как точку входа. Код 127 — программы нет,
это успех проверки. Код 0 — программа есть и выполнилась, это провал.
Код 125 — нет самого образа, это тоже провал: проверять было нечего.
`--network none` — у проверочного контейнера нет сети.

## Граница доверия

Шаг не меняет обработку данных из запросов. Он работает с другой
границей — «атакующий, уже выполняющий код в контейнере control plane».
Изменение уменьшает то, что атакующему доступно за этой границей:
нет shell для готовых эксплойтов, нет менеджера пакетов для установки
своих инструментов, код приложения недоступен на запись.

Честная оговорка: интерпретатор Python остаётся, и полезная нагрузка,
написанная на Python, без shell обойдётся. Distroless поднимает цену
атаки, но не делает её невозможной.

## Что может пойти не так

- **Уязвимости самого Python.** Раньше Python в образе был собран
  из исходников, и Trivy его не видел. Теперь это пакет Debian, и сканер
  показывает 12 уязвимостей без исправлений: в разборе XML, HTML-парсере,
  tarfile, ncurses, libuuid. Control plane ничего из этого не использует.
  Если начнёт — риск R5 нужно пересмотреть.
- **Отставание патч-версий.** В Debian Python 3.13.5, а у upstream уже 3.13.15.
  Исправления безопасности Debian переносит, но не все и не сразу.
- **Отладка.** Зайти в контейнер через `sh` нельзя. Доступны логи,
  проверка здоровья и `docker debug` локально.

## Как это проверено

- `scripts/test_check_containers.py`: четыре новых теста D6 — финальная
  стадия не distroless; distroless только в сборочной стадии; финальная
  стадия от именованной стадии (хороший и плохой варианты); отладочный
  вариант `:debug`. На старом Dockerfile из `main` правило D6 срабатывает.
- `make check-images` проверена в обе стороны: на образах продукта проходит,
  на `python:3.13-slim`, на отладочном distroless и на несуществующем
  образе падает.
- Все 67 тестов control plane проходят на Python 3.13, покрытие 97%.
- Весь стек поднят с новым образом: control plane healthy, `/readyz`
  отвечает `ready`, процесс работает от 65532.
- Trivy: 44 → 22 записи HIGH, ни одной с доступным исправлением.

## Вопросы для самопроверки

1. Почему в Dockerfile две стадии, и что случилось бы, если оставить одну?

   <details><summary>Ответ</summary>

   Для установки зависимостей нужны pip, uv, сеть и полноценный образ Python.
   В одной стадии всё это осталось бы в итоговом образе. Вторая стадия
   начинается с чистого distroless и забирает из первой только два каталога
   с результатом. Инструменты сборки в продакшен не попадают.

   </details>

2. Trivy показывал 44 уязвимости, теперь 22. Можно ли сказать, что образ
   стал вдвое безопаснее?

   <details><summary>Ответ</summary>

   Нет, и сравнение даже несправедливо к новому образу. В старом Trivy не
   видел интерпретатор Python, собранный из исходников, поэтому его
   уязвимости в отчёт не попадали вовсе. Новый отчёт короче и полнее
   одновременно. К тому же количество — плохая мера: важно, достижима ли
   уязвимость из нашего кода. Все оставшиеся лежат в модулях, которыми
   control plane не пользуется.

   </details>

3. Зачем нужна `make check-images`, если правило D6 уже проверяет Dockerfile?

   <details><summary>Ответ</summary>

   D6 проверяет намерение: «финальная стадия построена на distroless».
   `check-images` проверяет результат: в собранном образе действительно
   нельзя запустить shell. Это ловит, например, `COPY --from=build /bin/sh /bin/sh`
   или базовый образ, в котором shell лежит не там, где его ждёт правило.
   Правило, которое читает только конфигурацию, не видит того, что
   получилось на самом деле.

   </details>

4. Почему `ENTRYPOINT ["/usr/bin/python3", "-m", "webdeception_cp"]`,
   а не `ENTRYPOINT python3 -m webdeception_cp`?

   <details><summary>Ответ</summary>

   Строковая форма означает «запусти через `/bin/sh -c`», а shell в образе нет —
   контейнер не стартовал бы. Форма со скобками запускает программу напрямую.
   Плюс: при строковой форме сигнал остановки получал бы shell, а не наш
   процесс, и корректная остановка не работала бы.

   </details>

5. Атакующий получил выполнение кода в control plane. Что из его обычного
   арсенала теперь не сработает, а что сработает?

   <details><summary>Ответ</summary>

   Не сработают: эксплойты, вызывающие `/bin/sh`, установка утилит через
   `apt` или `pip`, обратное соединение через `bash` или `perl`, скачивание
   через `curl` и `wget`, подмена кода приложения (файлы принадлежат root).
   Сработает: всё, что можно написать на самом Python, — у него есть
   сокеты, файлы, HTTP. Поэтому distroless — один из слоёв, а не вся защита:
   дальше работают отсутствие capabilities, файловая система только для
   чтения и изолированная сеть backend.

   </details>
