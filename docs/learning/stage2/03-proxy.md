# Этап 2, шаг 3. Сенсор проксирует трафик

> Снимок на момент шага: 2026-09-24. Решение — в
> [ADR-0021](../../adr/0021-proxy-transparency.md). Текущее состояние —
> в [guide.md](../../guide.md), раздел «Сенсор».

## Что и зачем

До этого шага сенсор умел только отвечать на `/healthz`. Теперь он встаёт
между интернетом и приложением: каждый запрос к Juice Shop проходит через
него. Приманок ещё нет — сенсор прозрачен. Но с этой минуты граница
«интернет → сенсор» из модели угроз становится настоящей: каждый байт,
который сюда приходит, прислал потенциальный атакующий.

У шага две цели, которые тянут в разные стороны:

- **не мешать**: приложение и его пользователи не должны замечать сенсор;
- **не стать дырой**: сенсор не должен превратиться в открытый прокси,
  в точку отказа или в прослойку, которая понимает запрос иначе, чем
  приложение.

## Понятия

- **Reverse proxy** — сервер, который принимает запрос вместо приложения
  и пересылает его приложению. В отличие от обычного прокси, клиент
  не выбирает, куда пойдёт запрос: это решает прокси.
- **Открытый прокси** — прокси, который соединяется с любым адресом по
  просьбе клиента. Для сенсора это путь во внутреннюю сеть клиента (T17).
- **Hop-by-hop заголовки** — заголовки одного соединения (`Connection`,
  `Keep-Alive`, `Proxy-Authorization`), которые нельзя передавать дальше.
- **Request smuggling** — атака, когда прокси и приложение по-разному видят
  границу запроса (T18).
- **Срок (deadline)** — момент, после которого операция с сетью
  завершится ошибкой. Его можно сдвигать перед каждой операцией.
- **Семафор** — счётчик свободных мест; здесь — для предела соединений.

## Как это работает

```
клиент ──TCP──▶ LimitListener ──▶ http.Server ──▶ rejectConnect ──▶ withIOIdleDeadlines
                (предел           (таймаут          (CONNECT → 405)   (срок перед каждым
                 соединений)       заголовков,                         чтением и записью)
                                   предел размера)                          │
                                                                            ▼
                                                                    httputil.ReverseProxy
                                                                     │ Rewrite: куда и
                                                                     │ с какими заголовками
                                                                     ▼
                                                              http.Transport ──TCP──▶ приложение
                                                              (таймауты, без
                                                               HTTP_PROXY)
```

Проверки выстроены слоями, и порядок важен: предел соединений — до того,
как сервер начнёт тратить память на чтение запроса; отказ `CONNECT` — до
того, как запрос попадёт в прокси.

## Разбор кода

### Адрес приложения: `config.parseUpstream`

Файл `sensor/internal/config/config.go`. Это вход от администратора, а не
от атакующего, но ошибка в нём — трафик клиента, ушедший не туда.

```go
v := strings.TrimSpace(getenv("SENSOR_UPSTREAM_URL"))
if v == "" {
    return nil, fmt.Errorf("SENSOR_UPSTREAM_URL: не задан адрес ...")
}
```

- `strings.TrimSpace` — убрать пробелы по краям: частый результат
  копирования в `.env`.
- Значения по умолчанию нет. Любое угаданное значение — это чужой трафик,
  отправленный наугад.

```go
if u.User != nil {
    // В сообщение адрес целиком не выводим: в нём пароль.
    return nil, fmt.Errorf("логин и пароль в адресе приложения не поддерживаются")
}
```

- `u.User` — часть `логин:пароль@` в адресе. Отвергаем, и в текст ошибки
  **не** включаем исходную строку: ошибка уйдёт в лог контейнера.
  Это проверяет тест `TestUpstreamPasswordNotInError`.

```go
return &url.URL{Scheme: u.Scheme, Host: u.Host}, nil
```

- Возвращаем новый адрес только из схемы и хоста. Даже если в разборе
  что-то пропустили, лишние поля до прокси физически не дойдут.

### Куда и что уходит: `Rewrite` в `proxy.newHandler`

Файл `sensor/internal/proxy/proxy.go`. Главное место шага.

```go
Rewrite: func(pr *httputil.ProxyRequest) {
```

`pr.In` — запрос, как его прислал клиент. `pr.Out` — копия, которая уйдёт
приложению. К моменту вызова ReverseProxy уже удалил из `pr.Out`
hop-by-hop заголовки и все `X-Forwarded-*` и `Forwarded` от клиента.

```go
    pr.SetURL(upstream)
```

Схема, хост и порт исходящего запроса — из `upstream`, то есть из
конфигурации. Не из `pr.In.Host`, не из `pr.In.URL.Host`. Именно эта
строка делает сенсор не открытым прокси. Тест `TestUpstreamOnlyFromConfig`
присылает чужой `Host` и абсолютный адрес `GET http://внутренний-сервис/`
и проверяет, что «внутренний сервис» не получил ни одного запроса.
Если заменить эту строку на адрес из `Host`, тест падает — это проверено.

```go
    pr.Out.Host = pr.In.Host
```

`SetURL` заменил заголовок `Host` на адрес приложения. Возвращаем исходный:
приложение строит по нему ссылки. Это не опасно: `Host` — просто заголовок,
соединение уже решено строкой выше.

```go
    for _, h := range clientIPHeaders {
        pr.Out.Header.Del(h)
    }
```

ReverseProxy удаляет только `X-Forwarded-*` и `Forwarded`. А `X-Real-IP`,
`True-Client-IP` и подобные прошли бы к приложению. Если приложение
настроено «доверять X-Real-IP от прокси», атакующий подставил бы любой IP —
и, например, попал бы в чужой список разрешённых адресов. Эту дыру нашли
при написании шага, её закрывает тест `TestClientIPHeadersReplaced`.

```go
    pr.SetXForwarded()
```

Выставить `X-Forwarded-For` по адресу TCP-соединения — его атакующий
подделать не может. Плюс `X-Forwarded-Host` и `X-Forwarded-Proto`.

### Что клиент узнает при сбое: `errorHandler`

```go
status, reason := classify(err)
...
slog.String("error_type", fmt.Sprintf("%T", err)),
...
respond.Plain(w, status, http.StatusText(status))
```

- `classify` превращает ошибку в код (502, 504) и короткую причину.
- `%T` — тип ошибки (например, `*net.OpError`), а не её текст. Текст
  в лог не пишется: в ошибках транспорта бывают куски ответа приложения,
  а в других ошибках — адрес запроса с параметрами, где лежат токены.
  Тест `TestUpstreamDownIsNeutral502` шлёт запрос с `?token=SECRET-TOKEN-123`
  и проверяет, что этой строки нет ни в ответе, ни в логе.
- Клиенту — только `Bad Gateway`: ни адреса приложения, ни причины.

### Молчащий клиент: `withIOIdleDeadlines`

Файл `sensor/internal/proxy/deadline.go`.

```go
func (r *idleReader) Read(p []byte) (int, error) {
    _ = r.rc.SetReadDeadline(time.Now().Add(r.idle))
    n, err := r.body.Read(p)
```

- Перед **каждым** чтением тела запроса срок сдвигается на `idle` (60 с)
  вперёд. Пока клиент шлёт данные, срок уезжает; замолчал на минуту —
  следующее чтение завершится ошибкой.
- Почему не общий `ReadTimeout`: он ограничил бы всю загрузку, и большой
  файл на медленном канале не загрузился бы никогда. Нам нужно не «быстро»,
  а «без пауз».

```go
    var netErr net.Error
    if err != nil && errors.As(err, &netErr) && netErr.Timeout() {
        r.timedOut.Store(true)
    }
```

- Запоминаем, что оборвал клиент, а не приложение. Иначе ответ был бы
  504 «приложение не ответило», и в логе оказалась бы ложная причина.
  С этим флагом клиент получает 408.

```go
defer func() {
    _ = rc.SetReadDeadline(time.Time{})
    _ = rc.SetWriteDeadline(time.Time{})
}()
```

- После обработки сроки снимаются: соединение keep-alive переживает запрос.
  Честная заметка: сервер Go 1.27 делает это и сам, но документация этого
  не обещает. Сначала я написал тест как «регрессионный на найденную
  ошибку». Проверка с намеренно сломанным кодом показала, что ошибки
  в этой версии Go нет, и комментарий пришлось исправить. Хороший пример
  того, зачем проверять тест, ломая код.

### Предел соединений: `LimitListener`

Файл `sensor/internal/proxy/limit.go`.

```go
select {
case l.slots <- struct{}{}:
    return true
default:
}
```

- `slots` — канал ёмкостью `SENSOR_MAX_CONNS`. Положить в него значение —
  занять место. `default` делает попытку неблокирующей: если места есть,
  берём сразу.

```go
if l.onSaturated != nil {
    l.onSaturated()
}
select {
case l.slots <- struct{}{}:
    return true
case <-l.done:
    return false
}
```

- Мест нет — сообщаем (в лог, не чаще раза в минуту) и ждём. Ждём одного
  из двух: освободилось место или слушатель закрыли. Без второго варианта
  остановка сенсора под нагрузкой зависла бы на этом месте навсегда.

```go
func (c *limitConn) Close() error {
    err := c.Conn.Close()
    c.releaseOnce.Do(c.release)
    return err
}
```

- Место освобождается при закрытии соединения — ровно один раз.
  `sync.Once` защищает от двойного `Close`, иначе оно освободило бы
  чужое место, и предел перестал бы работать.

## Граница доверия

| Данные | Откуда | Что с ними делает сенсор |
|---|---|---|
| путь, параметры | атакующий | передаёт как есть; параметры с `;`, которые Go не разобрал, удаляет |
| `Host`, абсолютный адрес в строке запроса | атакующий | не влияют на то, куда открывается соединение |
| `X-Forwarded-For`, `X-Real-IP` и подобные | атакующий | удаляются; `X-Forwarded-For` выставляется заново |
| `Content-Length`, `Transfer-Encoding` | атакующий | разбираются сервером Go; приложению — пересобранный запрос |
| тело запроса | атакующий | передаётся потоком; паузы дольше минуты обрывают запрос |
| скорость, число соединений | атакующий | таймауты и предел соединений |
| `SENSOR_UPSTREAM_URL` | администратор | строгая проверка; логин и пароль запрещены |
| ответ приложения | частично доверенный | передаётся как есть; заголовки ограничены 1 МиБ |

## Что может пойти не так

- **T17 — открытый прокси.** Закрыто: адрес только из конфигурации,
  `CONNECT` — 405, прокси из окружения не используется.
- **T18 — разный разбор запроса.** Закрыто разбором запроса сервером Go
  и пересборкой запроса. Остаётся: приложение может иначе разбирать путь
  (`..`, `%2e`) — сенсор его не нормализует, это решение прозрачности.
  При сравнении с путями приманок (шаг 8) нормализация понадобится.
- **Остаётся:** клиентский слушатель без TLS — его завершает балансировщик.
  Из-за этого сенсор не видит отпечаток TLS-клиента (JA4), нужный профилю
  атакующего на этапе 4. Записано в долг.
- **Остаётся:** о насыщении соединений пока только строка в логе, метрика
  появится на шаге 6.

## Как это проверено

- 24 теста в пакете `proxy`, покрытие пакета 96%, всего сенсора 92%. Главные:
  `TestUpstreamOnlyFromConfig`, `TestConnectRejected`,
  `TestClientIPHeadersReplaced`, `TestAmbiguousFramingIsNormalized`,
  `TestMalformedRequestsRejected`, `TestUpstreamDownIsNeutral502`,
  `TestSlowBodyIsCutOff`, `TestLimitListenerWaitsAtLimit`.
- Каждый из четырёх ключевых тестов безопасности проверен ломанием кода:
  убрали удаление заголовков, пропустили `CONNECT`, взяли адрес из `Host`,
  не сняли срок — тест краснеет. В одном случае проверка показала, что тест
  не ловит то, что обещает: его пришлось переписать.
- Поведение Go на спорных запросах сначала проверено опытом, а не взято
  из памяти, и уже потом записано в тесты.
- `make smoke`: весь стек с Juice Shop за сенсором, запрос через сенсор
  возвращает страницу Juice Shop.
- Руками: WebSocket Juice Shop через сенсор (ответ 101); из контейнера
  Juice Shop нет выхода в интернет и имя `postgres` не разрешается.

## Вопросы для самопроверки

1. Атакующий шлёт через сенсор `GET http://169.254.169.254/latest/meta-data/`.
   Куда уйдёт запрос и какая строка кода за это отвечает?

   <details><summary>Ответ</summary>

   В приложение из `SENSOR_UPSTREAM_URL` — Juice Shop. За это отвечает
   `pr.SetURL(upstream)` в `Rewrite`: адрес соединения берётся из
   конфигурации, а не из строки запроса или `Host`. Приложение получит
   путь `/latest/meta-data/` и, скорее всего, ответит 404. До облачных
   метаданных запрос не дойдёт.

   </details>

2. ReverseProxy и так удаляет `X-Forwarded-For` от клиента. Зачем мы
   отдельно удаляем `X-Real-IP` и `True-Client-IP`?

   <details><summary>Ответ</summary>

   ReverseProxy удаляет только `X-Forwarded-*` и `Forwarded`. Остальные
   заголовки с «настоящим IP» он пропускает. Приложение за прокси часто
   настраивают доверять такому заголовку — и тогда атакующий, подставив его,
   выдал бы себя за любой адрес: обошёл бы список разрешённых IP или подставил
   чужой адрес в логи и блокировки (T1).

   </details>

3. Почему у клиентского слушателя нет `ReadTimeout`, хотя у служебного
   он есть? Чем его заменили?

   <details><summary>Ответ</summary>

   `ReadTimeout` ограничивает весь запрос целиком, и легитимная загрузка
   большого файла на медленном канале оборвалась бы. Служебному слушателю
   длинные запросы не нужны, клиентскому — нужны. Заменили сроками простоя:
   перед каждым чтением тела срок сдвигается на минуту. Долго можно,
   молчать нельзя.

   </details>

4. Приложение упало. Что увидит клиент, что попадёт в лог — и чего
   намеренно не попадёт?

   <details><summary>Ответ</summary>

   Клиент — `502 Bad Gateway` и больше ничего. В лог — предупреждение
   с причиной «не удалось соединиться с приложением», типом ошибки и кодом.
   Не попадут: текст ошибки, адрес запроса и параметры (там бывают токены),
   адрес приложения в ответе клиенту.

   </details>

5. Предел соединений — 1024. Пришло 1025-е соединение. Что с ним будет
   и почему не отказ?

   <details><summary>Ответ</summary>

   Оно не отвергается, а ждёт в очереди ядра, пока освободится место.
   В лог раз в минуту пишется предупреждение. Отказ был бы честнее при
   атаке, но при кратком всплеске легитимные клиенты получили бы ошибку
   вместо задержки. Главное, что даёт предел: сенсор не падает по памяти,
   а падение сенсора уронило бы сайт клиента целиком.

   </details>
