# Этап 2, шаг 10б. Наживки в HTML: комментарий и скрытая ссылка

> Снимок на момент шага: 2026-09-25. Решение — в
> [ADR-0028](../../adr/0028-html-lures.md). Текущее состояние —
> в [guide.md](../../guide.md), раздел «Сенсор».

## Что и зачем

Атакующий, который изучает сайт, открывает исходный код страниц. Там он
ищет комментарии разработчиков и ссылки, которых нет в меню. Сканеры
и пауки (Burp, ZAP) делают то же автоматически: обходят все ссылки
страницы. Поэтому на шаге две новые наживки, обе сразу после `<body>`:

- **комментарий** — `<!-- TODO: API v2 documentation moved to /internal/api/v2/docs (internal only) -->`
  ведёт к фейковой документации (№6);
- **скрытая ссылка** — `<a href="/account/legacy-login" hidden ...></a>`
  ведёт к «старому входу» (№5).

Это самая рискованная правка в сенсоре. Страницу видит каждый посетитель,
а в ней могут быть данные, которые сохранил атакующий. Вставка не в том
месте ломает сайт клиента на всех страницах. Чужой текст во вставке —
это XSS. Поэтому шаг вынесен в отдельный PR: свой ADR, фаззинг,
мутационное тестирование.

## Понятия

- **Токенизатор HTML** — первая ступень разбора HTML. Делит поток байтов
  на токены: стартовый тег, закрывающий тег, текст, комментарий. Знает,
  где `<body>` — не тег: внутри `<script>`, комментария, атрибута.
  См. [глоссарий](../../glossary.md).
- **Режим совместимости (quirks mode)** — старый режим отображения
  страниц. Его включает любой текст перед `<!doctype html>`.
- **Слабый ETag** — `W/"v1"`: «по смыслу то же», а не «побайтно то же».
- **Бюджет памяти правки тел** — общий предел памяти, которую сенсор
  тратит на чтение и правку тел ответов.
- **go.sum и sum.golang.org** — хеши зависимостей в репозитории
  и публичный журнал хешей всех модулей Go.
- **Зависимость** — чужой код, который собирается в наш бинарник.
  До этого шага сенсор обходился стандартной библиотекой Go.

## Как это работает

```
запрос ─▶ … ─▶ ReverseProxy.Rewrite ─▶ lure.Prepare ─▶ приложение
                                        │
          переход по странице? ─────────┘ да: Accept-Encoding: identity

клиент ◀─ ReverseProxy ◀── lure.Modify ◀── ответ приложения
                              │
                              ├─ GET 200 text/html без сжатия?  нет → как есть
                              ├─ бюджет памяти есть?            нет → как есть (memory)
                              ├─ токенизатор ищет <body> в первых 256 КиБ
                              │     не нашёл → как есть (html_no_body)
                              └─ прочитанное[:место] + вставка + прочитанное[место:] + остаток
```

- **Prepare.** Для перехода по странице (`Sec-Fetch-Dest: document`)
  сенсор просит у приложения ответ без сжатия. Сжатую страницу не
  дополнить, а распаковщика Brotli в стандартной библиотеке Go нет.
- **Modify.** Проверяет, что ответ — страница. Читает начало страницы
  через токенизатор до `<body>` и собирает тело из трёх кусков
  и непрочитанного остатка. Байты страницы не меняются, кроме вставки.
- **Вставка собрана заранее.** Фрагмент (`<a ...></a><!-- ... -->`)
  собирается один раз, при разборе политики. На запросе ничего не
  форматируется.

Цепочки учебного набора теперь полные:

| Что прочитал атакующий | Куда пошёл | Касание |
|---|---|---|
| скрытая ссылка (№5) | `GET /account/legacy-login` | medium, `lure_id: legacy-link` |
| комментарий (№6) | `GET /internal/api/v2/docs` | medium, `lure_id: docs-comment` |
| документация (№6) | `POST /api/internal/v1/users/export` с JSON (№8) | high, `lure_id: api-docs` |

## Разбор кода

### Текст комментария: `validateLureText` в `policy/lure.go`

```go
lureTextRe = regexp.MustCompile(`^[A-Za-z0-9 .,:;/()_?=+-]*$`)

func validateLureText(at, text string, add func(string, ...any)) {
	rest := strings.Replace(text, lurePathPlaceholder, "", 1)
	switch {
	case strings.Count(text, lurePathPlaceholder) != 1:
		add("%s.text: обязателен и содержит {path} ровно один раз", at)
	case len(text) > maxLureTextLen:
		add("%s.text: не длиннее %d байт", at, maxLureTextLen)
	case !lureTextRe.MatchString(rest):
		add("%s.text: только латиница, цифры, пробел и . , : ; / ( ) _ ? = + -", at)
	case strings.Contains(rest, "--") || strings.Contains(text, "-"+lurePathPlaceholder) ||
		strings.Contains(text, lurePathPlaceholder+"-"):
		add("%s.text: без двойного дефиса и дефиса вплотную к {path}", at)
	}
}
```

Здесь текст наживки впервые приходит из политики, а не из шаблона.
Поэтому проверка строже, чем кажется нужным.

- `rest` — текст без `{path}`. Фигурные скобки не входят в разрешённый
  набор, поэтому регулярное выражение проверяет текст без
  заполнителя.
- `Count(...) != 1` — путь ловушки обязателен ровно один раз: наживка
  без пути ни к чему не ведёт.
- `lureTextRe` — белый список. Нет `<` и `>`: ими не открыть новый тег
  и не закрыть комментарий (`-->`). Нет `!`: комментарий закрывает и
  `--!>`. Нет `&`: ссылки на символы (`&gt;`) внутри комментария
  не раскрываются, но и незачем. Нет кириллицы — это не ограничение
  безопасности, а цена простоты: проверять весь Unicode на опасные
  символы (невидимые, меняющие направление текста) дороже, чем
  не пускать его.
- `--` запрещено отдельно: в комментарии это ошибка разбора HTML.
  Дефис вплотную к `{path}` — тоже: путь ловушки может заканчиваться
  на `-`, и после подстановки получилось бы `--`.
- Проверка пути ловушки — рядом, в `validateLures`: у ловушки комментария
  в пути нет `--`. Символов `<`, `>` и `"` в путях нет вовсе (ADR-0025).

### Сборка вставки: `compileLures`

```go
case LureHTMLComment:
	c.htmlFragment += "<!-- " + strings.Replace(l.Text, lurePathPlaceholder, target.Path, 1) + " -->"
case LureHTMLLink:
	c.htmlFragment += `<a href="` + html.EscapeString(target.Path) +
		`" hidden aria-hidden="true" tabindex="-1" rel="nofollow"></a>`
```

- Вставка собирается один раз, при разборе политики, в порядке наживок.
  `HTMLFragment()` возвращает готовую строку.
- Пробел после `<!--` и перед `-->` нужен: `<!-->` и `<!--->` браузер
  понимает как пустой комментарий, и текст после них оказался бы
  на странице.
- `html.EscapeString` — из стандартной библиотеки (`html`, не `x/net`).
  В пути ловушки допустим `&`, а в атрибуте `&` начинает ссылку
  на символ: `href="/a&copy"` браузер прочитал бы как `/a©`. Экранирование
  даёт `&amp;copy`, и браузер получает исходный путь.
- Атрибуты ссылки — в ADR-0028. Коротко: не видна, не в фокусе
  клавиатуры, не читается программами экранного доступа, поисковикам —
  «не ходить».

### Какой запрос — страница: `isHTMLPage`

```go
func isHTMLPage(r *http.Request) bool {
	if r.Method != http.MethodGet {
		return false
	}
	if dest := r.Header.Get("Sec-Fetch-Dest"); dest != "" {
		return dest == "document" || dest == "iframe" || dest == "frame"
	}
	return strings.Contains(r.Header.Get("Accept"), "text/html")
}
```

- Решает одно: просить ли у приложения страницу без сжатия. Ошибка
  здесь стоит трафика или наживки, но не безопасности: клиент может
  прислать что угодно, и худшее, что он получит, — страницу без сжатия.
- `Sec-Fetch-Dest` ставит браузер, скрипт страницы его изменить не может.
  `document` — переход по ссылке или адресной строке, `iframe`
  и `frame` — страница во фрейме. `fetch` из скрипта даёт `empty`:
  такому запросу сжатие не отключаем, даже если в `Accept` есть
  `text/html`.
- Без `Sec-Fetch-*` (старый браузер, curl, сканер) — смотрим `Accept`.
  Сканер, который просит `text/html`, как раз тот, кому наживка нужна.

### Какой ответ правится: `htmlEligible`

```go
if resp.Request == nil || resp.Request.Method != http.MethodGet || resp.StatusCode != http.StatusOK {
	return false, -1
}
mediaType, params, _ := strings.Cut(resp.Header.Get("Content-Type"), ";")
if !strings.EqualFold(strings.TrimSpace(mediaType), "text/html") {
	return false, -1
}
if ce := resp.Header.Get("Content-Encoding"); ce != "" && !strings.EqualFold(ce, "identity") {
	return false, SkipHTMLEncoded
}
charset := strings.ToLower(params)
if strings.Contains(charset, "utf-16") || strings.Contains(charset, "utf-32") ||
	strings.HasPrefix(strings.ToLower(strings.TrimSpace(resp.Header.Get("Content-Disposition"))), "attachment") ||
	resp.Header.Get("Content-Range") != "" {
	return false, SkipHTMLNotPage
}
return true, 0
```

Ответ приложения доверенный лишь частично, но заголовки здесь только
сравниваются.

- Только `GET` и `200`. `HEAD` без тела, у `404` и `500` своя страница,
  которую сенсору незачем трогать.
- `strings.Cut(..., ";")` отделяет тип от параметров: `text/html;
  charset=utf-8` → `text/html` и ` charset=utf-8`. `EqualFold` —
  регистр не важен (`Text/HTML`). `application/xhtml+xml` не правится:
  там другие правила разбора (XML), и токенизатор HTML5 для них не годится.
- Сжатый ответ — как есть, с причиной `html_encoded`. Это значит, что
  приложение не выполнило просьбу `identity`, или сенсор не просил
  (запрос не похож на переход по странице).
- UTF-16 и UTF-32: вставка — байты ASCII, в двухбайтовой кодировке
  они стали бы мусором. Страница в UTF-16 без `charset` в заголовке,
  но с меткой порядка байтов, тоже безопасна: `<body>` там записан
  с нулевыми байтами, токенизатор его не найдёт.
- `attachment` — файл на скачивание, `Content-Range` — кусок файла.
  Это не страница, которую откроет браузер, а изменённый кусок
  испортил бы файл.
- Второй результат — причина для метрики. `-1` — «не страница, считать
  не нужно»: иначе счётчик рос бы на каждой картинке.

### Где `<body>`: `bodyInsertOffset` в `lure/html.go`

Это главное место шага.

```go
func bodyInsertOffset(body io.Reader, consumed *bytes.Buffer) (offset int, err error) {
	z := html.NewTokenizer(io.TeeReader(io.LimitReader(body, maxHTMLHead), consumed))
	pos := 0
	for {
		tt := z.Next()
		if tt == html.ErrorToken {
			if e := z.Err(); !errors.Is(e, io.EOF) {
				err = e
			}
			return -1, err
		}
		pos += len(z.Raw())
		if tt == html.StartTagToken || tt == html.SelfClosingTagToken {
			name, _ := z.TagName()
			if atom.Lookup(name) == atom.Body {
				return pos, nil
			}
		}
	}
}
```

Построчно, от внутреннего вызова к внешнему:

- `io.LimitReader(body, maxHTMLHead)` — не больше 256 КиБ. Дальше
  токенизатор получит «конец данных», даже если страница длиннее.
- `io.TeeReader(..., consumed)` — всё, что токенизатор прочитал, заодно
  копируется в `consumed`. Это «тройник» на трубе: токенизатор разбирает,
  а байты не пропадают, и потом их можно отдать клиенту как есть.
- `html.NewTokenizer` — токенизатор HTML5 из `golang.org/x/net/html`.
- `z.Next()` — следующий токен и его вид. `ErrorToken` — конец данных
  или ошибка чтения. `io.EOF` — нормальный конец: `<body>` не нашёлся
  (`-1, nil`). Любая другая ошибка — обрыв страницы у приложения
  (`-1, err`), её нужно донести до клиента.
- `z.Raw()` — исходные байты токена, **как они были в странице**,
  а не нормализованные. Сумма длин всех токенов до `<body>` включительно —
  точное смещение конца тега в прочитанных байтах. Поэтому вставка
  встаёт ровно после `>` тега, а сам тег и всё вокруг остаётся байт
  в байт.
- `StartTagToken` или `SelfClosingTagToken` — `<body>` и `<body/>`.
  Второй браузер понимает так же, как первый.
- `z.TagName()` — имя тега в нижнем регистре (`<BODY>` → `body`).
  `atom.Lookup(name) == atom.Body` — сравнение с заранее известным
  именем без создания строки.

Что токенизатор делает за нас. Строка `<body>` здесь **не тег**:

```html
<script>var s = "<body>";</script>          <!-- текст скрипта -->
<!-- <body> -->                              <!-- комментарий -->
<title>Где <body>?</title>                   <!-- текст заголовка -->
<meta content="<body>">                      <!-- значение атрибута -->
<textarea><body></textarea>                  <!-- текст поля -->
<noscript><body></noscript>                  <!-- для браузера с JS — текст -->
```

Поиск строки `<body` нашёл бы первое же из этих мест. Вставка внутри
`<script>` сломала бы JavaScript страницы, а внутри атрибута — вышла бы
из него.

### Вставка: `injectHTML`

```go
if e.mem = inj.mem.lease(htmlReserve); e.mem == nil {
	inj.Stats.Skipped[SkipMemory].Add(1)
	return
}
orig := resp.Body
buf := &bytes.Buffer{}
e.consumed = buf
offset, err := bodyInsertOffset(orig, buf)
read := buf.Bytes()
e.mem.shrink(int64(buf.Cap()))
if offset < 0 {
	if err == nil {
		inj.Stats.Skipped[SkipHTMLNoBody].Add(1)
	}
	resp.Body = heldBody{io.MultiReader(bytes.NewReader(read), errReader{err, orig}), orig, e.mem}
	e.consumed = nil
	return
}
resp.Body = heldBody{io.MultiReader(bytes.NewReader(read[:offset]), strings.NewReader(fragment),
	bytes.NewReader(read[offset:]), orig), orig, e.mem}
e.consumed = nil
```

- `lease(htmlReserve)` — сначала память из бюджета, потом чтение
  (следующий раздел).
- `e.consumed = buf` — **до** чтения. `e` живёт в `Modify`, и её `recover`
  видит буфер, даже если паника случится посреди чтения, внутри
  токенизатора. Тогда страница соберётся из прочитанного и остатка.
  В первой версии буфер отдавался после чтения, и такая паника потеряла бы
  прочитанное — клиент получил бы страницу без начала (находка 1).
- `shrink(buf.Cap())` — токенизатор закончил, его буфер больше не нужен.
  За ответом остаётся только прочитанное.
- `offset < 0` — тега нет. Тело — прочитанное, потом остаток. `errReader`
  при обрыве сначала отдаёт ту же ошибку, что пришла от приложения:
  клиент увидит обрыв, а не обрезанную страницу, похожую на целую.
- `io.MultiReader` читает куски по очереди: начало страницы до конца
  `<body>`, вставку, остаток прочитанного, непрочитанное. Страница
  не копируется: куски — срезы одного буфера. Раньше начало копировалось
  в новый массив, теперь нет — меньше памяти на медленного клиента.
- `heldBody` — тело, которое при закрытии вернёт память в бюджет
  и закроет соединение с приложением.

Дальше — заголовки: `Content-Length` плюс длина вставки (иначе клиент
получил бы страницу, обрезанную по старой длине — это поймала мутация,
находка 2), сильный `ETag` → слабый, сводки содержимого удаляются.

### Бюджет памяти: `lure/budget.go`

```go
func (b *memBudget) lease(n int64) *lease {
	if b.used.Add(n) > editMemory {
		b.used.Add(-n)
		return nil
	}
	l := &lease{budget: b}
	l.n.Store(n)
	return l
}

func (l *lease) shrink(keep int64) {
	l.budget.used.Add(keep - l.n.Swap(keep))
}

func (l *lease) release() {
	l.budget.used.Add(-l.n.Swap(0))
}

func (b heldBody) Close() error {
	b.mem.release()
	return b.Closer.Close()
}
```

Зачем. Прочитанное начало страницы ждёт в памяти, пока клиент его
не заберёт. Медленный клиент держит его долго (сроки простоя не
закрывают соединение, пока клиент хоть понемногу читает). Страница без
`<body>` — до 256 КиБ на соединение, соединений — до 1024, лимит
контейнера — 128 МиБ. Предел «256 КиБ на ответ» сумму не ограничивает
(находка 6).

- `used` — одно атомарное число на весь сенсор. `Add` возвращает новое
  значение. Если оно больше 32 МиБ — вернуть занятое и отказать.
  Две правки у самого предела могут обе отказаться: каждая видит вклад
  другой. Это лишний пропуск наживки, а не выход за предел.
- Резерв на разбор — 2 МиБ для HTML, 4 МиБ для `robots.txt`. Это
  замер худшего случая с запасом: около 1,7 и 3,2 МиБ. Тест
  `TestEditReserves` сверяет резерв с замером, поэтому если код начнёт
  тратить больше, тест упадёт.
- `shrink` — после разбора оставить за правкой ровно то, что ждёт
  отправки. `Swap` меняет значение и возвращает старое одной операцией.
- `release` — вернуть всё. `Swap(0)` делает повторный вызов безвредным:
  тело могут закрыть дважды, а при панике память возвращает ещё
  и `Modify`.
- `heldBody.Close` — прокси закрывает тело, когда ответ отправлен или
  клиент ушёл. Тогда память и возвращается. Это проверяет сквозной тест:
  после ответа метрика `sensor_lures_memory_bytes` возвращается к 0.

## Находки

1. **Паника внутри токенизатора потеряла бы начало страницы.** Буфер
   прочитанного становился виден `recover` только после чтения.
   Исправлено: буфер заводится до чтения. Тест `TestInjectHTMLPanic`
   паникует посреди чтения и проверяет, что страница пришла целиком.
2. **Мутация «длина не обновлена» выжила.** Тест проверял поле
   `ContentLength`, а прокси отдаёт клиенту заголовок `Content-Length`.
   Тест дополнен, мутация поймана.
3. **Проверка снимка коммита врала.** Перед коммитом тесты прогоняются
   на снимке индекса — ровно на том, что уйдёт в коммит. Вывод шёл через
   `| tail`, а код возврата конвейера — это код `tail`, то есть всегда 0.
   Коммит с тестом без файла политики прошёл бы «проверку». Коммиты
   пересобраны, проверка теперь сохраняет код возврата `go test`.
4. **Сборка образа без сети модулей.** С первой зависимостью образ
   сенсора скачивает модуль при сборке. В Dockerfile — отдельный слой
   `go mod download` по `go.sum`.
5. **Juice Shop в браузере не затихает.** Проверка в Chromium ждала
   «сеть без запросов» и не дожидалась: приложение держит открытые
   соединения. Проверка ждёт загрузки документа и появления ссылки
   в DOM.
6. **Память без общего предела (T3).** Найдено при подготовке этого
   разбора: 256 КиБ на ответ — предел для одного ответа, но не для
   тысячи. То же было у `robots.txt` из шага 10а. Добавлен бюджет.
7. **Детектор гонок меняет выделение памяти.** Под `-race` замер
   памяти вдвое больше: инструментирование само выделяет память. Замер
   имеет смысл только в обычной сборке, как в образе. Тест
   `TestEditReserves` собирается без `-race`, и `make test-go` запускает
   его отдельно. Проверку не пропускаем, а запускаем в тех условиях,
   где она верна.

## Граница доверия

- **Запрос клиента.** `Sec-Fetch-Dest` и `Accept` только сравниваются
  и решают одно: просить ли страницу без сжатия.
- **Ответ приложения** доверенный лишь частично: в странице может быть
  то, что сохранил атакующий.
  - Заголовки только сравниваются.
  - Тело читается не больше чем на 256 КиБ и в рамках бюджета.
  - Из страницы во вставку не попадает ничего: вставка собрана заранее.
  - Байты страницы не разбираются нашим кодом, их делит на токены
    `x/net/html`. Наш код только складывает длины токенов.
- **Политика** (T15). Во вставку из неё попадают путь ловушки
  (проверен ADR-0025, экранирован в атрибуте) и текст комментария
  (белый список символов, без `--`).
- **Зависимость** (T12). `golang.org/x/net` — чужой код в нашем бинарнике.
  Почему ему можно доверять — в ADR-0028.

## Что может пойти не так

- **T15 — сломанная страница или XSS.** Место ищет токенизатор, байты
  страницы не меняются, во вставке нет чужих данных. Остаточное:
  токенизатор не строит дерево, и внутри `<template>` или CDATA в SVG
  наживка станет неактивной или текстом.
- **T3 — память и время.** 256 КиБ на ответ, 32 МиБ на все правки.
  Остаточное: занятый бюджет выключает наживки у всех, но не сайт.
- **T5 — распознавание.** Страница при переходе без сжатия, а для
  скрипта — сжатая. `HEAD` и `GET` различаются по длине.
- **T2 — чужие касания.** Путь ссылки открывается обычным `GET`,
  ловушка — `medium`. Поисковики и предзагрузка браузера могут пройти
  по ссылке — шум для этапа 4.
- **Совместимость.** Ссылка — первый элемент `<body>`: стили
  `body > div:first-child` её увидят. Проверять на копии сайта.

## Вопросы для самопроверки

1. Почему `<body>` ищет токенизатор, а не `strings.Index(page, "<body")`?
   Приведите страницу, на которой поиск строки сломал бы сайт.

   <details><summary>Ответ</summary>

   Строка `<body>` бывает не тегом: в тексте скрипта, в комментарии,
   в заголовке, в значении атрибута. Например,
   `<head><script>var s = "<body>";</script></head><body>`: поиск строки
   найдёт первое вхождение — внутри скрипта, — и вставка окажется
   в JavaScript. Скрипт перестанет разбираться, и сайт не заработает
   на всех страницах. Токенизатор делит страницу по правилам HTML5, как
   браузер, и знает, что внутри `<script>` до `</script>` тегов нет.

   </details>

2. Почему наживки вставляются сразу после `<body>`, а не в самое начало
   ответа и не перед `</body>`?

   <details><summary>Ответ</summary>

   Текст перед `<!doctype html>` включает режим совместимости, и вёрстка
   сайта поплывёт. Ссылку внутри `<head>` браузер сочтёт началом тела
   раньше настоящего `<body>`. Перед `</body>` — пришлось бы читать
   страницу целиком (память, задержка), а `</body>` часто нет вовсе.
   Сразу после `<body>` комментарий и ссылка точно в теле документа,
   а читать нужно только начало страницы.

   </details>

3. Текст комментария берётся из политики. Как гарантируется, что
   взломанный control plane не вставит через него `<script>` на все
   страницы клиента?

   <details><summary>Ответ</summary>

   Текст проверяется белым списком: латиница, цифры, пробел и
   `. , : ; / ( ) _ ? = + -`. Без `<` не открыть тег. Комментарий
   закрывают только `-->` и `--!>`, а `>`, `!` и `--` запрещены. Путь
   ловушки из своего набора символов, без `<`, `>`, и для комментария —
   без `--`. Внутри комментария браузер ничего не исполняет, а выйти
   из комментария этим текстом нельзя. Ту же политику проверяет сам
   сенсор при загрузке, а не только control plane.

   </details>

4. У каждого ответа уже есть предел — 256 КиБ. Зачем понадобился ещё
   общий бюджет памяти, и что происходит, когда он кончается?

   <details><summary>Ответ</summary>

   Предел на ответ не ограничивает сумму. Прочитанное держится в памяти,
   пока клиент его не заберёт, а медленный клиент забирает долго.
   Тысяча медленных соединений на странице без `<body>` — это сотни
   мегабайт при лимите контейнера 128 МиБ. Сенсор упал бы, а падение
   процесса fail-open не покрывает — сайт встал бы. Бюджет — 32 МиБ
   на все правки тел. Когда он кончается, ответ уходит без наживки,
   причина `memory` — в метрике. Страдают наживки, а не сайт: доступность
   важнее.

   </details>

5. Почему буфер прочитанного заводится **до** чтения страницы, а не
   возвращается из функции после?

   <details><summary>Ответ</summary>

   Потому что паника может случиться посреди чтения — внутри токенизатора,
   на странице, которой он не ожидал. Тогда функция не вернётся, и то,
   что она прочитала, пропало бы вместе с ней. Клиент получил бы страницу
   без начала. Буфер, заведённый до чтения, лежит в `Modify`, и её
   `recover` собирает страницу из прочитанного и непрочитанного. Это
   проверяет `TestInjectHTMLPanic` и мутация «буфер виден только после
   чтения».

   </details>
