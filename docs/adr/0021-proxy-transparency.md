# ADR-0021. Проксирование: прозрачность, таймауты, пределы

Статус: принято, частично заменено [ADR-0022](0022-client-ip-trusted-proxies.md)
(заголовки с адресом клиента). Дата: 2026-09-24.

## Контекст

С этого шага сенсор стоит в пути трафика: каждый запрос к приложению
клиента проходит через него. Отсюда два противоречащих требования:

- **Прозрачность.** Приложение и его пользователи не должны замечать
  сенсор. Любое изменение запроса или ответа — это риск сломать сайт
  клиента, а изменение, которое видно снаружи, выдаёт продукт (угроза T5).
- **Защита.** Сенсор принимает враждебный вход из интернета. Он не должен
  стать ни открытым прокси во внутреннюю сеть, ни местом, где атакующий
  исчерпает память или соединения, ни прослойкой, которая понимает запрос
  иначе, чем приложение.

Решение — прозрачность по умолчанию и короткий перечень осознанных
изменений, у каждого из которых есть причина в модели угроз.

## Решение

### Основа

`httputil.ReverseProxy` из стандартной библиотеки Go в режиме `Rewrite`.
Своя реализация прокси — это разбор HTTP вручную, то есть ровно то место,
где рождаются уязвимости request smuggling. Режим `Rewrite`, а не устаревший
`Director`: до вызова `Rewrite` ReverseProxy сам удаляет служебные заголовки
соединения и присланные клиентом `X-Forwarded-*` и `Forwarded`.

### Что проходит без изменений

- Метод, путь (без нормализации: `..`, `%2e%2e`, `//` доходят до приложения
  как есть), параметры, тело, заголовки запроса.
- Заголовок `Host` — исходный, а не адрес приложения: по нему приложение
  строит ссылки и перенаправления.
- Код, заголовки и тело ответа, включая `Server` и `Set-Cookie` приложения.
  Сенсор не добавляет своих заголовков (`Via` и подобных).
- Сжатие: сенсор не распаковывает ответы и не добавляет `Accept-Encoding`.
- WebSocket и другие `Upgrade`.

### Что сенсор меняет — и почему

| Изменение | Причина |
|---|---|
| Адрес приложения только из `SENSOR_UPSTREAM_URL`, никогда из `Host` или строки запроса | иначе сенсор — открытый прокси во внутреннюю сеть (T17) |
| `CONNECT` отвергается с 405 | запрос на туннель к произвольному адресу (T17) |
| Удаляются присланные клиентом `X-Forwarded-*`, `Forwarded`, `X-Real-IP`, `True-Client-IP`, `CF-Connecting-IP`, `X-Client-IP`, `X-Cluster-Client-IP` | приложение, доверяющее им «от прокси», поверило бы подставленному IP (T1) |
| `X-Forwarded-For` = адрес TCP-соединения, плюс `X-Forwarded-Host` и `X-Forwarded-Proto` | приложение узнаёт настоящий адрес клиента; доверие цепочке своих прокси — шаг 5 |
| Удаляются hop-by-hop заголовки, включая `Proxy-Authorization` | они относятся к соединению с сенсором; учётные данные для прокси не должны достаться приложению |
| Параметры, которые Go не может разобрать (с `;`), удаляются | иначе сенсор и приложение видели бы разные параметры, и приманку можно было бы обойти, спрятав параметр от сенсора |
| Запрос с неоднозначной длиной тела (`Content-Length` вместе с `Transfer-Encoding`) пересобирается с одним способом указать длину; противоречивые запросы отвергаются самим сервером Go (400, 501) | request smuggling: приложение не может увидеть границу запроса иначе, чем сенсор (T18) |

### Таймауты и пределы

Клиент → сенсор:

| Что | Значение | Зачем |
|---|---|---|
| заголовки запроса | 10 с | Slowloris |
| размер заголовков | 64 КиБ (+4 КиБ запаса самого Go) | память; 431 сверх предела |
| пауза посреди тела запроса или при чтении ответа | 60 с | медленное тело и медленное чтение; как `client_body_timeout` и `send_timeout` в nginx |
| keep-alive между запросами | 120 с | не держать молчащие соединения |
| одновременных соединений | `SENSOR_MAX_CONNS`, по умолчанию 1024 | сверх предела соединения ждут в очереди ядра, а не отвергаются |

`ReadTimeout` и `WriteTimeout` сервера не заданы намеренно: они ограничивают
длительность запроса целиком и рвали бы легитимные длинные загрузки
и скачивания. Их роль выполняют сроки простоя: не «запрос длится не дольше N»,
а «клиент не может замолчать дольше N».

Сенсор → приложение:

| Что | Значение | Зачем |
|---|---|---|
| соединение | 5 с | быстрый 502, если приложения нет |
| заголовки ответа | 60 с | как `proxy_read_timeout` в nginx; не рвать запросы, нормальные для приложения |
| размер заголовков ответа | 1 МиБ | ответ приложения доверенный лишь частично |
| запас соединений | 256 | без него под нагрузкой — новое соединение на каждый запрос и лишние миллисекунды к p99 |
| прокси из `HTTP_PROXY` | не используется | трафик клиента не должен уйти через машину из переменной окружения |

Таймауты — константы, а не настройки: это защита от класса атак,
и возможность выставить её в ноль — возможность её отключить.

### Ошибки

Приложение не ответило — нейтральный `502 Bad Gateway` или `504 Gateway
Timeout`, клиент замолчал посреди тела — `408`. В ответе только код и его
название. В лог — класс ошибки и её тип, но не текст: в ошибках транспорта
бывают фрагменты ответа приложения, а в ошибках клиента HTTP — полный адрес
запроса с параметрами.

### Предел соединений — своя реализация

Около сорока строк вместо `golang.org/x/net/netutil.LimitListener`: ради них
не стоит добавлять модуль с зависимостями. Предупреждение о насыщении —
не чаще раза в минуту, чтобы атака на соединения не стала атакой на лог.

## Альтернативы

- **nginx или Envoy перед приложением, сенсор сбоку.** Зрелый прокси,
  но приманки требуют менять ответы и отвечать вместо приложения, а это
  логика внутри прокси — модули на C, Lua или Wasm, которые пришлось бы
  писать и поддерживать вместо Go (ADR-0001).
- **Нормализовать путь перед отправкой приложению.** Защитило бы
  приложения с ошибками разбора путей, но изменило бы поведение сайта
  и сделало сенсор непрозрачным. Нормализация понадобится для сравнения
  с путями приманок (шаг 8) — но только для сравнения, а в приложение
  уходит исходный путь.
- **`ReadTimeout` и `WriteTimeout` вместо сроков простоя.** Проще,
  но ломает длинные загрузки и потоковые ответы.
- **Отвергать соединения сверх предела вместо ожидания.** Честнее
  сообщает о перегрузке, но при кратком всплеске легитимные клиенты
  получили бы ошибки вместо небольшой задержки.
- **Передавать приложению исходные параметры с `;`.** Максимальная
  прозрачность, но сенсор и приложение понимали бы запрос по-разному.

## Последствия

- Сенсор без адреса приложения не стартует (код 2). В compose он поднимается
  вместе с учебной целью в профиле demo; `make dev` — только control plane,
  PostgreSQL и NATS.
- Путь в адресе приложения (`http://app/api`) пока не поддерживается.
- Клиентский слушатель — HTTP без TLS. В боевом развёртывании TLS
  завершается на балансировщике перед сенсором. Отпечаток TLS-клиента (JA4),
  нужный профилю атакующего на этапе 4, без завершения TLS на сенсоре
  недоступен — записано в технический долг.
- Приложения, разбирающие параметры через `;`, за сенсором этих параметров
  не получат. Для современных приложений это не встречается; если
  понадобится — отдельное решение.

## Исправление от 2026-09-24

В разделах «Основа» и «Что сенсор меняет» ошибочно сказано, что
ReverseProxy удаляет все присланные клиентом `X-Forwarded-*`. Он удаляет
только `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`
и `Forwarded`; `X-Forwarded-Port`, `X-Forwarded-Prefix`, `X-Forwarded-Ssl`
и другие доходили до приложения от клиента. Найдено и исправлено на шаге 5:
[ADR-0022](0022-client-ip-trusted-proxies.md), где описано и то, какие
заголовки о клиенте теперь уходят приложению.
