# ADR-0023. События сенсора: формат v0, буфер, файл, метрики

Статус: принято. Дата: 2026-09-24. Уточняет [ADR-0004](0004-events-nats.md)
(буфер событий) и [ADR-0007](0007-data-minimization.md) (что записывается).

## Контекст

С шага 8 сенсор будет выставлять приманки, и каждое касание — событие.
Ради событий продукт и существует. До появления очереди NATS (этап 3)
событиям нужно куда-то попадать, а правила проекта ставят условия:

- **Сенсор никогда не ждёт.** Запись события не может задержать запрос
  клиента, даже если диск завис (CLAUDE.md).
- **Только метаданные.** Тела, заголовки авторизации, cookie, токены
  и пароли не записываются (CLAUDE.md, ADR-0007, угроза T4).
- **В событие попадают данные атакующего.** Путь, User-Agent, адрес
  из `CONNECT` выбирает атакующий. Они не должны портить файл событий,
  подделывать соседние события и исполняться там, где их потом читают.
- **Атакующий управляет числом событий.** Касаясь приманок без остановки,
  он может заполнить диск хоста (угроза T3).

## Решение

### Формат v0

Одна строка — одно событие JSON (формат JSON Lines):

```json
{"v":0,"id":"DWGKZ2UHWY7VAG4JRA2WOMNLXG","ts":"2026-09-24T17:22:11.644Z",
 "type":"request.connect_rejected","severity":"low",
 "client":{"ip":"203.0.113.7","peer":"10.0.0.1","via_trusted_proxy":true},
 "request":{"method":"CONNECT","user_agent":"curl/8.5.0"},
 "data":{"target":"10.0.0.1:22"}}
```

| Поле | Что это |
|---|---|
| `v` | версия формата; 0 — формат ещё меняется, обязательство совместимости — с версии 1 на этапе 3 |
| `id` | 128 случайных бит (`crypto/rand.Text`): на этапе 3 одно событие, отправленное дважды, не посчитается двумя |
| `ts` | время в UTC |
| `type` | тип: `sensor.started`, `sensor.stopping`, `request.connect_rejected`; касания приманок — с шага 8 |
| `severity` | `info`, `low`, `medium`, `high`, `critical` |
| `client` | адрес клиента по ADR-0022; нет `ip` — адрес неизвестен (цепочка оборвана) |
| `request` | метод, путь с маскированием, факт наличия параметров, User-Agent |
| `data` | поля, свои для типа; ключи — константы из кода |

Формат закреплён «золотым» тестом: событие с известными полями обязано
кодироваться ровно в заданную строку. Изменение формата видно в ревью.

### Что берётся из запроса

Ровно четыре вещи: метод, путь, `User-Agent` и факт наличия параметров.
Значения параметров, тело, cookie, `Authorization` и остальные заголовки
в событие не попадают.

- **Путь** — в процентной кодировке, как прислан, с маскированием (ниже),
  не длиннее 1024 байт. Обрезка идёт по границе сегмента: обрезанный
  сегмент выбрасывается целиком, потому что начало токена — тоже часть
  токена.
- **User-Agent** — до 256 байт, нужен для отпечатка клиента (ADR-0007).
- **Метод** — до 32 байт; **адрес `CONNECT`** — до 261 (host:port).
- Все строки от клиента приводятся к корректному UTF-8.

### Маскирование пути

Каждый сегмент пути проверяется правилами, более точное — раньше:

| Сегмент | Метка | Пример |
|---|---|---|
| содержит `@` или `%40` | `{email}` | `/users/john@example.com` |
| UUID | `{uuid}` | `/files/550e8400-e29b-…` |
| начинается с `eyJ` и содержит точку | `{jwt}` | `/auth/eyJhbGciOi….….` |
| только цифры | `{num}` | `/api/users/12345` |
| от 16 шестнадцатеричных символов | `{hex}` | `/reset/9f8a7c6e5d4b3a2f` |
| от 20 символов токена, есть буква и цифра | `{token}` | `/magic/aZ3kQ9pL2mX7vB1nR8tY` |
| параметры после `;` | `;{params}` | `/shop;jsessionid=…` |

Это эвристика. Она не поймает короткий токен и замаскирует длинный
осмысленный сегмент с цифрами. Правила выбраны так, чтобы ошибаться
в сторону маскирования: лишняя метка стоит меньше, чем записанный
действующий токен сброса пароля.

### Данные атакующего в файле (угроза T19)

Первый рубеж — сервер Go: запрос с управляющим символом (ESC, перевод
строки) в заголовке или строке запроса получает 400 ещё до кода сенсора
(проверено руками). Но байты от 0x80 он пропускает — в них U+2028
и недопустимый UTF-8, — а позже данные атакующего придут и не из
заголовков (тела запросов к приманкам). Поэтому второй рубеж не зависит
от первого.

Строки от клиента записываются только как значения JSON, и кодировщик
Go экранирует в них перевод строки, возврат каретки, все управляющие
символы (включая ESC терминала), `<`, `>`, `&` и символы U+2028/U+2029.
Поэтому:

- одна строка файла — ровно одно событие; «дописать своё событие»,
  вставив перевод строки в User-Agent, нельзя;
- `cat events.jsonl` в терминале не выполнит управляющую
  последовательность из пути атакующего;
- размер события ограничен при любом запросе (проверено тестом: не больше
  4 КиБ).

Вывод событий в дашборде (этап 5) — только как текст с экранированием,
по правилу CLAUDE.md.

### Буфер: никогда не ждать

`Emit` кладёт событие в канал ёмкостью 4096 без ожидания (`select`
с `default`). Отдельная горутина пишет события в файл.

Если буфер полон, **вытесняется самое старое событие**, как требует
ADR-0004. Атакующий может сам заполнить буфер, касаясь приманок; если бы
терялись новые события, его следующие действия не записались бы вовсе.
Попыток две, без цикла: если освободившееся место занял другой
обработчик, теряется это событие.

Учёт точный: после остановки каждое событие, переданное в `Emit`, либо
записано, либо ровно в одном счётчике потерь: `queue_full`, `write_error`,
`stopped`. Для этого остановка один раз берёт блокировку на запись:
после неё `Emit` не кладёт событий в буфер, и горутина записи дочитывает
всё, что там есть. `Emit` держит ту же блокировку на чтение на время
нескольких неблокирующих операций. Ждать он может только эти
микросекунды и только в момент остановки.

Буфер файла сбрасывается, когда очередь опустела. При редких событиях
каждое сразу видно в файле, при потоке они пишутся пачками. `fsync` —
только при остановке: он ждёт диск.

### Файл

- Путь — `SENSOR_EVENTS_FILE`, по умолчанию `/var/lib/sensor/events.jsonl`.
  В образе каталог принадлежит пользователю сенсора, права `0700`,
  файл — `0600`: в событиях адреса клиентов.
- Дописывание в конец: после перезапуска события прошлого запуска
  сохраняются.
- **Ротация по размеру**: 32 МиБ, 4 старых файла
  (`events.jsonl.1` … `.4`). Верхняя граница на диске — 160 МиБ, сколько бы
  событий ни порождал атакующий.
- Если ротация не смогла открыть новый файл, следующая запись пробует
  снова. События между попытками учитываются как `write_error`.
- **Файл не открылся при запуске — сенсор не стартует.** Сенсор, который
  пропускает трафик и молча ничего не записывает, создаёт ложное чувство
  защищённости. Это ошибка развёртывания, и видна она сразу.

### Метрики

`/metrics` на служебном слушателе, текстовый формат Prometheus, написан
вручную (решение этапа 2: без `client_golang`):

| Метрика | Что показывает |
|---|---|
| `sensor_events_emitted_total` | события, принятые в буфер |
| `sensor_events_written_total` | события, записанные в файл |
| `sensor_events_dropped_total{reason}` | потерянные: `queue_full`, `write_error`, `stopped` |
| `sensor_events_sink_errors_total` | ошибки записи и сброса файла |
| `sensor_events_queue_length`, `_capacity` | заполнение буфера |
| `sensor_connect_rejected_total` | отвергнутые `CONNECT` |
| `sensor_client_chain_broken_total` | неразобранный `X-Forwarded-For` от доверенного прокси (ADR-0022) |
| `sensor_connections_saturated_total` | ожидания из-за предела соединений (долг шага 3) |
| `sensor_upstream_errors_total{class}` | запросы без ответа приложения по классу причины |

Имена и метки — только константы из кода, проверяются при запуске.
Метка из данных запроса позволила бы атакующему создавать новые строки
метрик без предела.

## Альтернативы

- **События в stdout, а сбор — драйвером логов Docker.** Ротация уже
  есть у Docker. Но события смешались бы с логами, у которых другой
  круг читателей, а в событиях персональные данные. И запись в stdout
  может заблокироваться, если драйвер логов не успевает.
- **Отбрасывать новое событие, а не старое.** Проще: одна операция
  вместо двух. Но это отдаёт атакующему возможность «ослепить» сенсор,
  заполнив буфер, — см. выше.
- **Запись с таймаутом вместо отбрасывания.** Нарушает «никогда
  не ждать»: даже 10 мс на событие при потоке касаний — задержка
  запросов клиента.
- **Отдельная приоритетная очередь для критичных событий** (переход
  в fail-open). Ни одна из политик выше не гарантирует, что критичное
  событие переживёт поток шума. Вернёмся к этому на шаге 7, когда такие
  события появятся.
- **Регулярные выражения для маскирования.** RE2 безопасен от ReDoS, но
  простые циклы по символам понятнее при ревью и быстрее.
- **Хеш пути вместо маскирования.** Защищает любые секреты, но делает
  событие бесполезным для человека: по хешу не понять, что трогали.
- **Библиотека `client_golang` для метрик.** Стандарт отрасли, но десяток
  модулей зависимостей ради десятка счётчиков.
- **Стартовать без файла событий, с предупреждением.** Сохраняет трафик
  при ошибке развёртывания, но делает её незаметной.

## Последствия

- При сбое процесса теряются события, которые ещё не сброшены из буфера
  файла, — доли секунды при потоке. Расширение принятого риска R2.
- События пишутся локально на каждом сенсоре. Сбор с нескольких
  сенсоров — этап 3 (NATS). Останется ли файл рядом с NATS, решим там же.
- В событии пока нет идентификатора сенсора и хеша сессии (ADR-0007).
  Идентификатор появится вместе с mTLS на этапе 3, хеш сессии —
  с приманками, которым он нужен.
- `/metrics` раскрывает, замечены ли действия атакующего. Служебный
  слушатель по умолчанию доступен только с localhost, при другой
  настройке — предупреждение в логе.
- В compose у каждого экземпляра сенсора свой том: два процесса,
  ротирующие один файл, испортили бы его.
