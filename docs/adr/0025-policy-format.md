# ADR-0025. Политика обнаружения: формат v1, проверка, загрузка, ловушки на путях

Статус: принято. Дата: 2026-09-24. Реализует этап 2 из
[ADR-0018](0018-policy-as-data.md) (политика как данные, до этапа 3 —
локальный файл).

## Контекст

ADR-0018 решил, что приманки — это данные, которые интерпретирует сенсор,
а не код под каждую приманку. На этапе 5 политику будут редактировать
в веб-интерфейсе, на этапе 3 — раздавать с control plane, который может
быть взломан (угроза T15). Сейчас нужно:

- определить формат так, чтобы он пережил и веб-интерфейс, и раздачу;
- проверять политику в сенсоре строго: всё, что пропустила проверка,
  попадёт в ответы сайту клиента;
- не дать ошибке в политике ни уронить сенсор, ни молча выключить ловушки;
- поставить первые ловушки — учебные приманки №1–3 из roadmap.

## Решение

### Формат v1

```json
{
  "schema_version": 1,
  "version": "demo-1",
  "traps": [
    {
      "id": "env-file",
      "description": "фейковый .env",
      "path": "/.env",
      "mode": "enforce",
      "confidence": "low",
      "response": {"status": 200, "content_type": "text/plain", "body": "APP_ENV=production\n..."}
    }
  ]
}
```

| Поле | Правило |
|---|---|
| `schema_version` | ровно 1; другую версию сенсор не принимает — незнакомое поле могло бы менять смысл правила |
| `version` | метка от администратора, до 64 символов `A-Za-z0-9._:-`; попадает в события касаний |
| `traps` | до 256 |
| `id` | до 64 символов `a-z0-9-`, уникален; по нему в событии видно, что трогали |
| `description` | необязательно, до 256 байт |
| `path` | точный путь, до 256 байт, в нормализованном виде, не `/`, без `;`, `%`, `?`; уникален |
| `mode` | `observe` — только записать; `enforce` — записать и ответить вместо приложения |
| `confidence` | `low`, `medium`, `high`, `very_high` |
| `response.status` | 200, 401, 403, 404, 500 — без перенаправлений |
| `response.content_type` | `text/plain`, `application/json`, `application/octet-stream` — без HTML |
| `response.body` | до 64 КиБ, UTF-8; для `application/json` — корректный JSON |

Весь документ — до 1 МиБ. Все пределы — константы.

### Строгий разбор

Разбор — `encoding/json/v2` из стандартной библиотеки Go 1.27, с запретом
неизвестных полей. Отвергаются:

- повторяющийся ключ (`"mode"` дважды) — прежний `encoding/json` молча
  взял бы последнее значение, и администратор видел бы в файле одно,
  а сенсор применял бы другое;
- имя в другом регистре (`"Path"`) — прежний пакет принял бы его как `path`;
- неизвестное поле (`"regex"`) — опечатка в имени поля не должна давать
  правило, которое выглядит настроенным, а работает по умолчанию;
- недопустимый UTF-8 и данные после документа.

Проверка перечисляет все найденные ошибки (до 20) с местом — например,
`traps[2].path: ловушка на «/» перехватила бы главную страницу`.
Администратору удобнее исправить всё за раз.

Любая ошибка — политика не принимается целиком. Половина политики хуже,
чем прежняя целиком.

### Что не может сделать даже принятая политика (T15)

- **Перехватить главную страницу** — ловушка на `/` запрещена. Пути только
  точные, без префиксов и шаблонов: ловушка не накроет раздел сайта.
- **Внедрить скрипт на сайт клиента** — ответ ловушки не бывает HTML.
  Заголовки `X-Content-Type-Options: nosniff` и `Content-Type` ставит
  сенсор, а не политика, поэтому браузер не угадает HTML в тексте ловушки.
  Наживки внутри HTML-страниц — шаг 10, только через шаблоны с экранированием.
- **Сделать открытый редирект** — коды 3xx запрещены.
- **Отравить кэш** — ответ ловушки всегда `Cache-Control: no-store`. CDN
  перед сенсором не закэширует его, и каждое касание дойдёт до сенсора.
- **Исчерпать память и время** — пределы размеров, сравнение пути —
  поиск в карте.

Остаётся: ловушка на **существующем** пути приложения (`/login`)
перехватит его. Сенсор не знает, какие пути есть у приложения. Защита —
режим наблюдения: новое правило сначала ставится в `observe`, и по событиям
видно, трогают ли этот путь обычные пользователи.

### Сравнение пути: нормализация

Путь запроса (`r.URL.Path` — процентная запись уже раскодирована сервером
Go) перед сравнением нормализуется:

| Запись атакующего | После нормализации |
|---|---|
| `//.env`, `/./.env`, `/static/../.env`, `/.env/` | `/.env` (`path.Clean`) |
| `/.env;jsessionid=1` | `/.env` (параметры сегмента, как их понимает Tomcat) |
| `\.env` | `/.env` (разделитель пути IIS) |
| `/.env%00.png` | `/.env` (часть серверов обрезает строку на нулевом байте) |
| `/%2eenv` | `/.env` (раскодировал сервер Go) |

Регистр сохраняется: ловушка — точный путь.

Нормализация — только для сравнения. В приложение уходит исходный путь,
как решено в ADR-0021. Путь ловушки в политике обязан быть записан
в нормализованном виде: ненормализованная запись никогда бы не совпала
и выглядела бы как работающая ловушка.

### Касание

`decoy.Detector` встаёт внутрь `failopen.Guard` (ADR-0024). Касание:

1. событие `decoy.touch`: адрес клиента, метаданные запроса (ADR-0023),
   `decoy_id`, `mode`, `confidence`, `policy_version`. Важность — из
   уверенности; `very_high` → `high`: `critical` оставлен для событий
   о состоянии сенсора;
2. в режиме `enforce` — ответ ловушки (`respond.Trap`), запрос дальше
   не идёт; в режиме `observe` — запрос идёт в приложение.

Касание записывается при любом методе запроса. Тело запроса не читается.
Жёсткой реакции нет: ответ фейковым файлом — не блокировка, поэтому
правило о накопленном скоринге для аутентифицированных пользователей
не нарушается.

Политика в `Detector` заменяется целиком одной атомарной операцией
(`atomic.Pointer`). Запрос видит либо старую политику, либо новую, но
никогда половину той и другой.

### Загрузка и последняя валидная версия

| Когда | Файл верен | Файл неверен |
|---|---|---|
| запуск | применить, сохранить копию | взять копию последней валидной; нет копии или она неверна — без ловушек |
| `SIGHUP` | применить, сохранить копию | оставить текущую |

- **Ошибка в политике не мешает запуску.** Политика — не граница доверия,
  как адрес приложения, и сайт клиента не должен лежать из-за опечатки.
  Каждый исход — событие (`sensor.policy_loaded` с источником `file` или
  `last_valid`, `sensor.policy_rejected` с текстом ошибки и версией,
  которая осталась) и строка в логе.
- **Копию последней валидной ведёт сам сенсор** (`SENSOR_POLICY_CACHE_FILE`,
  по умолчанию `/var/lib/sensor/policy.last-valid.json`, права `0600`).
  Запись атомарная: временный файл в том же каталоге, `fsync`,
  переименование. Копия проверяется при чтении так же строго, как файл
  администратора: её мог испортить сбой диска или кто-то чужой.
- **Перезагрузка — по `SIGHUP`** (`make policy-reload`). Обработчик ставится
  в самом начале запуска: по умолчанию Go при `SIGHUP` завершает процесс,
  и без обработчика команда «перечитай политику» роняла бы сенсор.
- События о политике — в приоритетной очереди (`sensor.*`, ADR-0024).

### Файл политики в контейнере

В compose каталог `deploy/policy` монтируется только для чтения. Именно
каталог, а не отдельный файл. Редакторы и `sed -i` сохраняют файл через
замену на новый. Смонтированный по отдельности файл Docker привязывает
к старому, и после правки сенсор по `SIGHUP` перечитывал бы прежнюю
политику. Найдено при проверке руками.

## Альтернативы

- **Прежний `encoding/json` с `DisallowUnknownFields`.** Привычнее, но
  повторяющиеся ключи и имена в другом регистре проходят молча.
- **YAML или TOML.** Удобнее руками, но на этапе 5 политику пишет
  веб-интерфейс, а у YAML неочевидные правила типов (строка `no` — это
  `false`). JSON выбран в ADR-0018.
- **Префиксы и регулярные выражения в путях.** Гибче, но ловушка
  на префиксе может накрыть раздел настоящего сайта. Понадобятся —
  отдельным решением, с RE2 и ограничением длины (ADR-0018).
- **Отказ стартовать при неверной политике.** Так сделано для слоя запуска,
  но там ошибка — это граница доверия. Здесь это была бы недоступность
  сайта из-за опечатки в тексте фейкового файла.
- **Встроенная политика по умолчанию в бинарнике.** Удобно, но делает
  учебные приманки частью каждого боевого сенсора: их знает любой, кто
  читал репозиторий (T5, ADR-0011). Без `SENSOR_POLICY_FILE` сенсор
  работает без ловушек и пишет об этом в лог.
- **Слежение за файлом (inotify) или опрос по таймеру вместо `SIGHUP`.**
  Слежение требует зависимости или платформенного кода, опрос — лишней
  работы и задержки. На этапе 3 политика будет приходить по сети,
  и способ обновления всё равно поменяется.
- **HTTP-эндпоинт «перезагрузить» на служебном порту.** Ещё одна точка,
  через которую можно менять поведение сенсора.
- **Машиночитаемая JSON Schema в `schemas/` сейчас.** ADR-0018 требует
  её для сверки сенсора и control plane. Сейчас второго читателя нет,
  и файл схемы, который никто не проверяет, разошёлся бы с кодом.
  Появится на этапе 3 вместе с проверкой с обеих сторон; до этого
  источник истины — проверка в Go и этот ADR.

## Последствия

- Учебные ловушки — в `deploy/policy/demo.json`. Они публичны
  (ADR-0011): до этапа 8 сенсор не для боевого применения.
- Ответ ловушки отличается от ответов приложения заголовками. Например,
  нет `Server`, который ставит сервер приложения. Внимательный атакующий
  может это заметить (T5). Подстройка ответов под приложение — вместе
  с наживками (шаг 10) и динамическими приманками (этап 8).
- Сенсор сравнивает путь из строки запроса. Если приложение берёт путь
  из заголовка (`X-Original-URL`, `X-Rewrite-URL` — так умеют IIS
  и некоторые фреймворки), сенсор и приложение видят разные пути.
  Для ловушек на несуществующих путях это не важно, для правил,
  которые что-то запрещают, — важно. Решение (удалять заголовки или
  считать их признаком атаки) — на шаге 9, вместе с условиями
  на заголовки в политике.
- Изменение политики на сенсоре фиксируется событием, но не журналом
  аудита с автором: автора сенсор не знает. Журнал аудита — в control
  plane на этапах 3 и 5.
- Формат будет расширяться: шаг 9 добавит условия на заголовки и методы,
  шаг 10 — наживки в ответах. Новые поля — либо необязательные в версии 1,
  либо версия 2; старый сенсор новое поле отвергнет, а не проигнорирует.
