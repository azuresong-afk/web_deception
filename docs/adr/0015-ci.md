# ADR-0015. CI в GitHub Actions

Статус: принято. Дата: 2026-09-22.

## Контекст
CI запускает код из каждого pull request с правами на наш репозиторий.
Это граница доверия «CI/CD → артефакты» из модели угроз и угроза T12 —
подмена зависимости или action. Скомпрометированный CI опаснее
скомпрометированного разработчика: он работает автоматически, на каждый
PR, и его вывод принимают на веру.

От CI нужно три вещи: те же проверки, что у разработчика локально;
скорость, чтобы монорепозиторий не превратился в ожидание (ADR-0008);
и собственная безопасность.

## Решение

**Workflow вызывает только make.** Что проверять, записано в Makefile;
workflow решает лишь где и когда. Одинаковые команды локально и в CI.

**Триггеры: `pull_request` и `push` в main.** Никогда `pull_request_target`:
он исполняет код из PR в контексте основного репозитория — с его секретами
и токеном на запись.

**`GITHUB_TOKEN` только на чтение** (`permissions: contents: read`)
на уровне всего workflow.

**Каждый action закреплён полным SHA коммита**, тег — комментарием рядом.
Используются только действия GitHub (`actions/*`). Инструменты ставятся
из закреплённых источников, а не сторонними setup-действиями: uv — через
pip с контрольными суммами из `deploy/docker/requirements-build.txt`,
инструменты Go — через модули в `tools/` с контрольными суммами в go.sum.

**`persist-credentials: false`** — токен не остаётся в `.git/config`
после checkout, и следующие шаги задания не могут его прочитать.

**Данные событий — только через переменные окружения.** Подстановка
`${{ }}` вставляет значение в текст скрипта до запуска; для заголовка PR
или имени ветки это готовая инъекция команд.

**Образ раннера зафиксирован** (`ubuntu-24.04`, а не `ubuntu-latest`) —
по той же причине, по которой запрещён тег latest у образов.

**Задания выбираются по изменённым путям** своим скриптом
`scripts/ci_changes.py`, который при любой неопределённости запускает всё.
Итоговое задание `ci-ok` — единственная проверка, которую нужно сделать
обязательной в защите ветки (шаг 7).

**У каждого инструмента Go свой модуль** в `tools/<инструмент>/` с директивой
`tool`. В общем модуле Go выбирает для общей зависимости максимальную
из нужных версий, и один инструмент ломает другой — это произошло
на практике: golangci-lint притянул YAML-библиотеку, с которой actionlint
не компилировался.

**Таймаут у каждого задания и отмена устаревших прогонов** при новом push.

**actionlint** проверяет сами workflow в `make lint` — перенесён с шага 6
на шаг 5, потому что workflow появились сейчас.

## Альтернативы
- **Фильтр `paths:` на уровне workflow.** Встроенный и простой, но пропущенный
  так workflow не сообщает о себе вовсе, и обязательная проверка в защите
  ветки ждёт его вечно. PR с правкой документации нельзя было бы слить.
- **`dorny/paths-filter` для выбора заданий.** Популярен, но это сторонний
  код, исполняемый в нашем CI с доступом к токену. Наш скрипт — 60 строк
  стандартной библиотеки с тестами.
- **`golangci/golangci-lint-action`.** Официальный путь, но версия линтера
  в CI и у разработчика расходятся, если не следить вручную. Модуль
  инструментов даёт одну версию везде и контрольные суммы.
- **`astral-sh/setup-uv`.** Ещё один сторонний action, когда закреплённый
  по хешам uv у нас уже есть.
- **Один модуль для всех инструментов Go.** Проще, но приводит к конфликтам
  версий зависимостей — см. выше.

## Последствия
- Добавление нового action требует найти SHA коммита и убедиться, что это
  коммит, а не объект тега. Без Dependabot (шаг 6) закреплённые SHA устареют.
- Кеш модулей Go, созданный прогоном в main, читается прогонами PR. Писать
  в кеш main может только код, уже слитый в main, поэтому отравление кеша
  через PR из форка невозможно — но это нужно помнить при любых изменениях
  настройки кеша.
- Для `make lint` локально нужны Go и docker CLI; на раннерах они есть.
- Задание `containers` поднимает весь стек и проверяет готовность — это самое
  медленное задание, и оно запускается только при изменении кода или
  конфигурации контейнеров.
