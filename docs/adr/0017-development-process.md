# ADR-0017. Процесс разработки: git-хуки, формат коммитов, защита ветки

Статус: принято. Дата: 2026-09-22.

## Контекст
К концу этапа 1 у проекта есть полноценный CI (ADR-0015, ADR-0016), но он
носит рекомендательный характер: ничто технически не мешает влить в `main`
изменение с красным CI или отправить коммит напрямую, минуя PR. Нужно:

- сделать CI условием слияния, а не советом;
- ловить самое дорогое — секрет в коммите — раньше, чем коммит покинет
  машину разработчика;
- сделать историю изменений машинно-читаемой, чтобы из неё собирались
  changelog и номер версии.

## Решение

**Git-хуки из каталога `.githooks/`**, включаются командой `make hooks`
(`git config core.hooksPath .githooks`):

- `pre-commit` — gitleaks по индексированным изменениям и проверка
  форматирования изменённых файлов Go и Python. Проверяется содержимое
  индекса, а не файла на диске: в коммит уходит индекс.
- `commit-msg` — формат сообщения.

Поведение при отсутствии инструмента выбрано по цене ошибки: проверка
секретов **блокирует** коммит (утёкший секрет не вернуть), проверки
форматирования **пропускаются** с предупреждением (их повторит CI,
исправление — одна команда).

**Conventional Commits** для всех коммитов. Проверяется скриптом
`scripts/check_commit_msg.py` — в хуке и в задании CI `commits` для всех
коммитов PR, кроме слияний.

**Правила ветки `main` — ruleset в `.github/rulesets/main.json`**,
импортируемый владельцем в настройках: слияние только через PR,
обязательные `ci-ok` и `CodeQL` с привязкой к публикующему приложению,
ветка PR должна быть актуальной относительно `main`, запрет force push
и удаления, закрытые обсуждения, без исключений для кого-либо. Файл
проверен по OpenAPI-схеме API GitHub.

## Альтернативы
- **Фреймворк pre-commit.** Стандарт де-факто, но хуки скачиваются из
  сторонних репозиториев по тегу (`rev: v4.5.0`) — то есть по изменяемой
  ссылке, как action по тегу, запрещённый в CLAUDE.md. Плюс ещё одна
  зависимость на Python. Наши хуки — два коротких shell-скрипта, которые
  вызывают уже закреплённые инструменты.
- **husky, lefthook.** Требуют Node.js или отдельный бинарник ради того,
  что git умеет сам.
- **Классическая защита ветки (branch protection).** Работает, но rulesets
  экспортируются в JSON и импортируются обратно — правила можно хранить
  в репозитории и ревьюить как код.
- **Одно обязательное одобрение.** Невозможно при одном человеке в проекте:
  GitHub не даёт автору одобрить свой PR. Включается, когда появится второй.
- **Обязательная подпись коммитов.** Сильная мера против подмены автора,
  но требует настройки ключей у каждого участника и в среде ассистента.
  Отложено.
- **Проверка формата коммитов через сторонний action** (commitlint). Node.js
  и сторонний код в CI ради регулярного выражения.

## Последствия
- `make hooks` нужно выполнить один раз в каждом клоне. Git сознательно
  не устанавливает хуки из репозитория сам.
- Хуки обходятся `git commit --no-verify`. Граница — CI и ruleset, хуки —
  ранняя обратная связь.
- Ruleset не применяется автоматически и не сверяется с файлом: для чтения
  правил нужен токен администратора. Расхождение возможно, если правила
  изменят в интерфейсе, не изменив файл.
- **Ассистент действует от учётной записи владельца.** Правила ветки
  не отличают слияние, которое сделал владелец, от слияния, которое сделал
  ассистент по его поручению. Это принятый риск R6 в модели угроз.
  Снижается выдачей ассистенту отдельной учётной записи или GitHub App
  с правом только на ветки и PR.
- Строгое правило актуальности ветки означает лишнее нажатие «Update branch»,
  когда `main` ушла вперёд. Цена — проверяется ровно тот код, который
  окажется в `main` после слияния.
