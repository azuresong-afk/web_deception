# ADR-0026. Ловушки, которые нельзя вызвать с чужого сайта

Статус: принято. Дата: 2026-09-24. Расширяет формат политики
[ADR-0025](0025-policy-format.md) необязательными полями версии 1.
Закрывает долг шага 5 о заголовках, переопределяющих путь.

## Контекст

Угроза T2 из модели угроз — межсайтовое срабатывание. Атакующий размещает
на своём сайте страницу, которая заставляет браузер посетителя запросить
ловушку на сайте клиента: `<img src="https://shop.example/.env">`, форма
с автоотправкой, `fetch`. Браузер отправит запрос с адреса посетителя
и с его cookie. Для сенсора это касание ловушки пользователем, который
ничего не делал. На этапе 4 по касаниям будет реакция, и тогда такая
страница станет способом заблокировать чужой адрес или заморозить чужой
аккаунт.

Меры, записанные в модели угроз:

- учитывать `Sec-Fetch-Site`;
- ловушкам высокой уверенности требовать CORS preflight (нестандартный
  заголовок или JSON);
- для аутентифицированных пользователей — реакция только по накопленному
  скорингу (этап 4).

Учебные приманки №8 (метод «внутреннего» API) и №9 (cookie со «служебным»
значением) из roadmap — шаг 9.

Отдельный долг из шага 5: заголовки `X-Original-URL` и `X-Rewrite-URL`
проходили от клиента к приложению.

## Решение

### Что браузер может отправить с чужого сайта

Спецификация Fetch делит запросы на «простые» и остальные. Простой запрос —
метод `GET`, `HEAD` или `POST`, и `Content-Type` один из трёх, которые умеет
отправить HTML-форма: `application/x-www-form-urlencoded`,
`multipart/form-data`, `text/plain`. Такой запрос чужая страница отправляет
сразу, с cookie пользователя (кроме cookie с `SameSite`).

Любой другой запрос браузер с чужого сайта сначала согласует
предварительным запросом `OPTIONS` (preflight). Сам запрос уйдёт, только если
сервер ответит заголовками `Access-Control-Allow-*`, разрешающими этот сайт.

Значит, «непростой» запрос, дошедший до ловушки, отправлен либо со страницы
самого сайта, либо не из браузера — инструментом атакующего.

### Условия ловушки на пути

Два необязательных поля:

| Поле | Смысл |
|---|---|
| `methods` | при каких методах запрос к пути — касание: `GET`, `HEAD`, `POST`, `PUT`, `DELETE`, `PATCH`. Без поля — при любом. `OPTIONS` нельзя: preflight браузер отправляет сам, с любого сайта |
| `preflight_only` | касание, только если браузер не отправил бы такой запрос с чужого сайта без preflight |

Проверка `preflight_only` (`policy.Preflighted`) **консервативна**: «да»
только тогда, когда браузер точно потребовал бы preflight. Метод не
`GET`/`HEAD`/`POST` — да. Иначе решает `Content-Type`: длиннее 128 байт,
с запрещённым байтом или с типом не из трёх «простых» — да. Тип сравнивается
так, чтобы никогда не назвать «непростым» то, что браузер считает простым:
часть до `;`, без пробелов по краям, нижний регистр — только для латиницы.
Нестандартные заголовки не учитываются: браузер сам добавляет заголовки,
которых нет в списке «простых», и надёжно отличить их нельзя. Ошибка
в сторону «нет» — пропущенное касание; в сторону «да» — ложное касание
пользователя. Поэтому только первое.

**Уверенность `high` и `very_high` — только с `preflight_only: true`.**
Это правило модели угроз, и его проверяет сенсор при разборе политики,
а не интерфейс: даже подменённая политика не сделает ловушку высокой
уверенности, которую может вызвать чужая страница.

### Сенсор сам отвечает на preflight к таким ловушкам

Приложение может одобрять CORS для любого сайта на любом пути. Так делает
Juice Shop: на preflight отвечает `Access-Control-Allow-Origin: *`. Тогда
браузер получил бы одобрение и отправил бы «непростой» запрос с чужой
страницы, и защита `preflight_only` не работала бы.

Поэтому на preflight (`OPTIONS` с `Access-Control-Request-Method`) к ловушке
с `preflight_only` в режиме `enforce` отвечает сенсор: `204` без единого
заголовка `Access-Control-Allow-*`. Preflight — не касание. Проверено
в Chromium: `fetch` с JSON с чужого сайта заблокирован браузером, а без
ответа сенсора Juice Shop бы его одобрил.

В режиме `observe` preflight уходит в приложение: наблюдение не меняет
ответов приложения. Касание в этом режиме может оказаться межсайтовым —
это видно по `sec_fetch` в событии, а реакции на касания в режиме
наблюдения нет по смыслу режима.

### Cookie-ловушка

Новая конструкция политики — `cookie_traps`:

```json
"cookie_traps": [
  {"id": "role-cookie", "name": "account_role", "value": "customer", "confidence": "high"}
]
```

- **Наживка.** К ответу приложения на переход по странице (`GET`,
  `Sec-Fetch-Mode: navigate`, а без него — `Accept` с `text/html`) сенсор
  добавляет `Set-Cookie: account_role=customer; Path=/; HttpOnly;
  SameSite=Strict`. При HTTPS — ещё `Secure`; о HTTPS сенсор судит по своему
  соединению или по `X-Forwarded-Proto` доверенного прокси. Если у браузера
  cookie уже есть — не добавляет. К ответам на картинки, скрипты и запросы
  API — тоже нет: CDN может не кэшировать ответ с `Set-Cookie`.
- **Ловушка.** Запрос, в котором эта cookie есть, но значение другое, —
  касание: cookie изменили вручную. Запрос при этом идёт в приложение:
  ответ вместо приложения выдал бы ловушку.
- **Почему её нельзя вызвать с чужого сайта.** `SameSite=Strict` — браузер
  не отправит cookie ни с каким межсайтовым запросом. `HttpOnly` — скрипт
  на странице её не перезапишет.
- **Значение не записывается никуда**, даже изменённое. В событии — только
  `decoy_id` и `decoy_kind: cookie`. Cookie — запрещённые к записи данные
  (CLAUDE.md), и в изменённом значении может оказаться что угодно.
- **Атрибуты — от сенсора, не из политики.** Имя начинается с буквы или
  цифры: это исключает префиксы `__Host-` и `__Secure-`, которые браузер
  принимает только с `Secure`. Имя и значение — только из
  `A-Z a-z 0-9 _ . -`, до 64 символов; `;` и кавычки невозможны, поэтому
  политика не допишет в `Set-Cookie` свой `Domain`. Не больше 8 cookie-ловушек.

**Одно событие на клиента в минуту.** Касание cookie-ловушки — состояние
браузера, а не действие: изменённая cookie уходит с каждым запросом.
Проверка в Chromium показала 30 событий `high` на одно открытие страницы
Juice Shop. Поэтому событием записывается первое касание от клиента за
минуту, а все касания считает `sensor_cookie_touches_total`. Таблица
«клиент → время» ограничена 4096 записями; переполнение очищает её, и тогда
событий становится больше, но пропущенных не бывает. Клиент без адреса
(оборванная цепочка прокси) не прореживается. Ловушки на путях
не прореживаются: каждое их касание — отдельный запрос.

### `Sec-Fetch-*` в событиях

Во всех событиях о запросе — поле `sec_fetch`: `site`, `mode`, `dest`,
`user`. Эти заголовки ставит браузер, скрипт их изменить не может.
`site: cross-site` у касания ловушки без `preflight_only` — признак, что его
могла вызвать чужая страница. Этап 4 учтёт это в классификации.
Инструмент атакующего может прислать любые значения, поэтому это
свидетельство, а не доказательство. Записываются только значения из
спецификации, остальное — `other`.

### Заголовки, переопределяющие путь

`X-Original-URL` и `X-Rewrite-URL` сенсор передаёт приложению только
от доверенного прокси, как `X-Forwarded-*`, а вариант с подчёркиванием
удаляет всегда. IIS, Symfony, Laminas берут из них путь запроса, и от
клиента это известный обход: «`GET /` + `X-Original-URL: /admin`» — прокси
и сенсор видят `/`, приложение обрабатывает `/admin`.

Признаком атаки их не считаем: событий на них нет. Продукт — не WAF, и
сигнатуры атак в обычных запросах — это шум, от которого ловушки как раз
избавляют.

### Что отложено

- **Цепочки «наживка → ловушка»** — на шаг 10. Связь нужна между наживкой
  в ответе (заголовок, HTML-комментарий) и ловушкой, а наживок в ответах
  ещё нет. У cookie-ловушки наживка и ловушка — одно правило.
- **Хеш сессии в событии** (ADR-0007) — на этап 4. Он нужен профилю
  атакующего и скорингу аутентифицированных пользователей, которые появятся
  там же, а для него нужны ключ HMAC в секретах и знание, какая cookie —
  сессия приложения.
- **Условия на заголовки** (ловушка на запрос с заголовком из фейковой
  документации) — вместе с наживками на шаге 10, если понадобятся.

## Альтернативы

- **Только записывать `Sec-Fetch-Site` и решать на этапе 4.** Меньше кода
  сейчас, но старые браузеры этих заголовков не присылают, и межсайтовое
  касание от них не отличить. Правило модели угроз требует preflight.
- **Считать касанием и «простой» запрос к ловушке с `preflight_only`,
  но с пониженной уверенностью.** Больше данных, но касание, которое может
  вызвать чужая страница, всё равно попадало бы в события с адресом
  пользователя. Выбрано проще: не касание, запрос идёт в приложение.
- **Учитывать нестандартные заголовки для `preflight_only`.** Точнее, но
  браузеры добавляют свои заголовки, и ошибка превратилась бы в ложные
  касания.
- **Отвечать на preflight во всех режимах.** Надёжнее против T2, но режим
  наблюдения тогда менял бы поведение приложения.
- **Не отвечать на preflight, полагаться на приложение.** Не работает
  с приложениями, которые одобряют CORS для всех (Juice Shop).
- **Cookie-наживка ко всем ответам.** Проще, но `Set-Cookie` на картинках
  и скриптах может отключить кэширование в CDN у клиента.
- **Cookie-ловушка с режимом `enforce`**, отвечающая вместо приложения.
  Выдала бы ловушку сразу; пользы от ответа нет.
- **Прореживать по соединению, а не по клиенту.** Без таблицы, но браузер
  открывает до 6 соединений к сайту — всё равно шесть событий на страницу.
- **Проверять cookie только на переходах по страницам.** Меньше событий без
  таблицы, но атакующий, изменивший cookie в Burp для запроса к API,
  остался бы незамеченным.
- **Удалять `X-Original-URL` и записывать событие.** См. выше: шум.

## Последствия

- Формат политики v1 расширен необязательными полями; старая политика
  остаётся верной, кроме ловушек `high` и `very_high` без `preflight_only` —
  их сенсор теперь отвергает.
- Ответ сенсора на preflight отличается от ответа приложения: внимательный
  атакующий может заметить, что на одном пути CORS ведёт себя иначе (T5).
  Защита от T2 важнее.
- Сенсор впервые меняет ответы приложения: добавляет `Set-Cookie`.
  Имя cookie не должно совпадать с cookie приложения — иначе у всех
  пользователей значение «изменится», и касания будут ложными. Новое правило
  сначала проверяйте на стенде.
- Смена `value` в политике делает «изменёнными» cookie у всех, кто получил
  прежнее значение. Меняйте имя, а не значение: cookie со старым именем
  сенсор просто перестанет проверять.
- Не закрыто:
  - поддомен сайта, захваченный атакующим, может подбросить cookie
    с `Domain` родительского сайта (`SameSite` его не остановит). Префикс
    `__Host-` защитил бы, но требует `Secure` — вместе с TLS;
  - XSS на самом сайте может отправить «непростой» запрос со страницы
    сайта. XSS на сайте — и так полная компрометация его пользователей;
  - заголовки переопределения метода (`X-HTTP-Method-Override`) условие
    `methods` не учитывает: атакующий, пославший `POST` вместо `DELETE`,
    не вызовет касания ловушки только для `DELETE`. Это пропуск касания,
    а не ложное касание.
  Все — в долгах roadmap. Реакции на касания до этапа 4 нет, и скоринг для
  аутентифицированных пользователей остаётся главной мерой против T2.
