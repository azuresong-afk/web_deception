# ADR-0019. Учебные цели для проверки сенсора: Juice Shop и VulnBank

Статус: принято. Дата: 2026-09-23.

Дополняет [ADR-0014](0014-containers.md) (правила контейнеров).

## Контекст

Сенсор нужно проверять за настоящими приложениями, а не только за
тестовыми заглушками: правка HTML, приманки и нормализация путей ведут себя
по-разному в зависимости от того, как устроено приложение.

Сейчас в стенде одна цель — OWASP Juice Shop. Это одностраничное
приложение (SPA) на Angular с API на Express: HTML почти пустой, страницы
рисует JavaScript, формы уходят в API как JSON. Для сенсора это значит,
что правка HTML проверяется на одной странице, а поведение с формами,
которые браузер отправляет сам, не проверяется вообще.

Владелец продукта предложил добавить **VulnBank**
([Commando-X/vuln-bank](https://github.com/Commando-X/vuln-bank), лицензия MIT) —
намеренно уязвимое банковское приложение на Flask. Оно устроено иначе:
страницы рисует сервер через шаблоны Jinja, есть классические HTML-формы
со скрытыми полями, REST API, GraphQL, JWT, загрузка файлов, чат-бот с LLM.

Изучение исходников VulnBank (коммит `4bb7cd5`) показало, что его штатный
способ запуска несовместим с правилами проекта:

| Что в VulnBank | Чем опасно |
|---|---|
| Flask запускается с `debug=True` | отладчик Werkzeug — исполнение кода в контейнере |
| загрузка картинки по URL: `requests.get(url, verify=False)` | SSRF: запросы от имени контейнера в любую доступную ему сеть, включая облачные метаданные `169.254.169.254` |
| их compose публикует PostgreSQL на все интерфейсы с паролем `postgres` | база открыта в сеть машины, где запущен стенд |
| сервис autoheal с `/var/run/docker.sock` и образом `latest` | доступ к Docker — это root на хосте |
| процесс от root, образ `python:3.9-slim` по тегу | нарушение правил ADR-0014; Python 3.9 уже без исправлений |

Для учебной цели уязвимости внутри приложения — это нормально, ради них
его и берут. Ненормально, если они выходят за пределы приложения:
на машину разработчика, в нашу инфраструктуру или в интернет.

## Решение

1. **Используем обе цели.** Juice Shop — представитель SPA с API,
   VulnBank — представитель серверного рендеринга с формами. Этого
   достаточно, чтобы проверить правку HTML, ловушки и cookie-приманки
   на двух принципиально разных архитектурах.

2. **Штатный compose VulnBank не используем.** Свой Dockerfile и описание
   сервисов по правилам ADR-0014:
   - исходный код по полному SHA коммита, а не по ветке;
   - базовый образ по digest;
   - зависимости Python с хешами;
   - процесс не от root, `cap_drop: [ALL]`, `no-new-privileges`,
     лимиты памяти и процессов;
   - файловая система только для чтения, каталог загрузок — в tmpfs;
   - своя отдельная база PostgreSQL, а не база продукта;
   - без autoheal и без доступа к Docker.

3. **Изоляция целей.** Каждая цель — в своей сети с `internal: true`:
   нет выхода в интернет, нет доступа к сети `backend` с нашими базой,
   очередью и control plane. Снаружи цель доступна только через свой
   экземпляр сенсора, порт которого опубликован на 127.0.0.1.
   SSRF и отладчик VulnBank работают, но дотянуться могут только
   до самой цели, её базы и входа сенсора.

   Juice Shop переводится в такую же сеть в том же шаге: у него тоже есть
   задания на SSRF, а сейчас он в сети `edge` с выходом в интернет.

4. **Один экземпляр сенсора на цель.** Сенсор этапа 2 проксирует ровно
   одно приложение. Две цели — два сервиса из одного образа сенсора
   с разными переменными окружения.

5. **Только профили demo.** Цели не входят в `make dev` и никогда не входят
   в упаковку продукта (этап 10).

6. **В CI сначала только Juice Shop.** Его образ публикуется автором
   и закрепляется по digest. VulnBank собирается из исходников: это время
   и исполнение чужих шагов сборки на машине CI. Решение о VulnBank в CI —
   когда появятся сквозные проверки приманок.

## Альтернативы

- **Только Juice Shop.** Слепое пятно на серверном рендеринге: именно
  такие приложения чаще всего встречаются у клиентов, и именно на них
  правка HTML рискованнее всего.
- **DVWA, WebGoat, bWAPP.** Тоже серверный рендеринг, но без современного
  API, GraphQL и JWT. Можно добавить позже, если понадобится стек PHP или Java.
- **Штатный compose VulnBank как есть.** Быстрее на один шаг, но открытая
  база, доступ к Docker и root нарушают правила проекта, и проверка
  политики контейнеров в `make lint` справедливо это не пропустит.

## Последствия

- Добавлена угроза T16 — взлом учебной цели и выход за её пределы.
- Dependabot не следит за коммитами чужих репозиториев в Dockerfile:
  обновлять VulnBank придётся вручную. Записано в технический долг.
- `make dev-demo` станет дольше при первом запуске: VulnBank собирается
  из исходников.
- VulnBank ходит к LLM (DeepSeek) за ответами чат-бота. Без выхода
  в интернет чат-бот работать не будет — это приемлемо, он вне задач сенсора.
