# Модель угроз

Версия 1.7, этап 2. Метод: STRIDE. Пересматривается при добавлении компонента,
новой внешней интеграции или изменении границ доверия.

Изменения в 1.1: исходный код продукта опубликован (ADR-0011) — уточнена мера
к угрозе T5 и добавлен принятый риск R4.

Изменения в 1.2: добавлена угроза T14 — небезопасные настройки сторонних
образов; найдена на шаге 4 в конфигурации NATS по умолчанию.

Изменения в 1.3: меры к T12 дополнены правилами CI (ADR-0015).

Изменения в 1.4: меры к T1, T4, T7, T12 подкреплены автоматическими проверками
(ADR-0016); добавлен принятый риск R5 — уязвимости без исправления в базовых образах.

Изменения в 1.5: меры к T10 и T12 дополнены правилами ветки main и git-хуками
(ADR-0017); добавлен принятый риск R6 — ассистент действует от учётной записи
владельца.

Изменения в 1.6: политика обнаружения управляется из веб-интерфейса
(ADR-0018) — добавлена угроза T15 и уточнена мера к T6; в стенд добавлена
вторая учебная цель (ADR-0019) — добавлена угроза T16.

Изменения в 1.7: control plane переведён на distroless (ADR-0020) — принятый
риск R5 пересчитан: уязвимостей вдвое меньше, и теперь сканер видит
сам интерпретатор Python.

## Активы

- Трафик клиентов, проходящий через сенсор (пароли, токены, персональные данные).
- Доступность защищаемого приложения.
- Целостность конфигурации сенсоров.
- Журнал событий и профили атакующих.
- Секреты продукта: ключ подписи конфигурации, HMAC-ключи canary-токенов,
  токен Telegram-бота.
- Репутация продукта.

## Границы доверия

1. Интернет → сенсор. Весь вход враждебен.
2. Сенсор → control plane. Сенсор работает у клиента и может быть скомпрометирован.
3. Control plane → администратор (дашборд, Telegram).
4. CI/CD → артефакты (образы, релизы).

## Принятые риски

- **R1.** В режиме fail-open обнаружение отключено. Принимаем ради доступности
  приложения клиента, компенсируем алертом о переходе в обход (T3).
- **R2.** При переполнении буфера события теряются. Принимаем, чтобы не замедлять
  приложение; потери учитываются счётчиком и видны в мониторинге.
- **R3.** Атакующий, который знает реальную уязвимость и идёт к ней напрямую,
  не касаясь приманок, обнаружен не будет. Продукт — слой обнаружения,
  а не замена WAF, пентеста и безопасной разработки.
- **R4.** Исходный код продукта публичен, поэтому атакующий может изучить
  логику обнаружения. Принимаем ради бесплатных проверок безопасности
  GitHub и ради того, чтобы стойкость не опиралась на секретность кода
  (ADR-0011). Компенсируется тем, что конкретные приманки генерируются
  под клиента и в репозитории не хранятся.
- **R5.** В базовых образах бывают уязвимости, для которых исправление ещё
  не выпущено. Проверка Trivy на них не падает — обновиться не на что, —
  но показывает их в сводке. После перехода control plane на distroless
  (ADR-0020) это 22 записи уровня HIGH (12 уникальных уязвимостей): в Python
  3.13 из Debian (HTML-парсер, tarfile, разбор XML), в expat, ncurses и
  libuuid. Control plane не разбирает XML, HTML и архивы, утилит монтирования
  в образе нет. Если control plane начнёт разбирать XML, HTML или архивы,
  уязвимости в этих модулях станут достижимыми, и риск нужно пересмотреть.
  Python из Debian отстаёт от upstream по патч-версиям: исправления
  переносятся не все и не сразу. Снижается еженедельным прогоном, который
  покажет, когда исправление появится, и обновлением digest через Dependabot
  (ADR-0016).
- **R6.** Код пишет AI-ассистент, и в GitHub он действует от учётной записи
  владельца. Правила ветки main не отличают действие владельца от действия
  ассистента: слияние PR по поручению в чате выглядит так же, как слияние
  вручную. Принимаем, пока проект ведёт один человек и каждое слияние
  происходит по его явному поручению. Снижается отдельной учётной записью
  или GitHub App для ассистента с правами только на ветки и PR (ADR-0017).
