# Сенсор

Reverse proxy на Go. Стоит перед защищаемым приложением, внедряет приманки
в ответы, обслуживает фейковые эндпоинты и отправляет события о касаниях.

Находится в критическом пути трафика клиента, поэтому:

- режим **fail-open**: при любом сбое запрос уходит в приложение напрямую;
- никогда не ждёт очередь событий (локальный буфер фиксированного размера);
- бюджет производительности: **не более +5 мс к p99** задержки приложения.

Решения: [ADR-0001](../docs/adr/0001-sensor-go.md) (почему Go),
[ADR-0003](../docs/adr/0003-config-pull.md) (почему конфигурация по pull).

## Что уже сделано

Сенсор работает как **прозрачный прокси** ([ADR-0021](../docs/adr/0021-proxy-transparency.md)):
принимает запросы на клиентском слушателе и передаёт их приложению, адрес
которого задан в конфигурации. Записывает события в файл JSON Lines
([ADR-0023](../docs/adr/0023-sensor-events.md)): запуск, остановку, попытки
`CONNECT`, касания ловушек. Ловушки задаются файлом политики
([ADR-0025](../docs/adr/0025-policy-format.md)) и перечитываются по `SIGHUP`.

Что сенсор делает сам, а не прозрачно:

- адрес приложения — только из `SENSOR_UPSTREAM_URL`, никогда из запроса;
  `CONNECT` отвергается (угроза T17);
- адрес клиента — адрес соединения или, если соединение от прокси из
  `SENSOR_TRUSTED_PROXIES`, самый правый недоверенный адрес `X-Forwarded-For`
  ([ADR-0022](../docs/adr/0022-client-ip-trusted-proxies.md));
- все `X-Forwarded-*`, `Forwarded`, `X-Real-IP` и подобные от недоверенных
  соединений удаляются, `X-Forwarded-For`, `-Host`, `-Proto` сенсор
  выставляет сам; варианты с подчёркиванием удаляются всегда (T1, T18);
- таймауты заголовков, сроки простоя тела и ответа, предел соединений (T3);
- при сбое приложения — нейтральный `502`, `504` или `408`;
- события — через буфер без ожидания: полон — вытесняется самое старое,
  потеря учитывается; в пути маскируются токены и идентификаторы (T3, T4, T19).
- fail-open ([ADR-0024](../docs/adr/0024-fail-open.md)): паника в обнаружении
  пропускает запрос в приложение и записывается событием; при перегрузке
  проверяется каждый 10-й запрос; защита при этом не отключается (T3).

Кроме того: проверка конфигурации с отказом стартовать при неверной,
служебный слушатель с проверками живости и готовности, корректная остановка
по SIGTERM.

## Служебные эндпоинты

Живут на отдельном слушателе, а не на порту клиентского трафика. Причина
из модели угроз: `/healthz` на публичном порту выдаёт присутствие нашей
защиты (T5) и даёт точку для нагрузки в обход приложения (T3).

| Путь | Ответ | Смысл |
|---|---|---|
| `GET /healthz` | всегда `200 ok` | процесс жив, перезапускать не надо |
| `GET /readyz` | `200 ready` или `503 not ready` | можно ли слать сюда трафик |
| `GET /metrics` | счётчики в формате Prometheus | потери событий, отказы приложения, насыщение соединений |

Всё остальное — `404`, любой метод кроме `GET` и `HEAD` — `405`. Редиректов
нет: путь из запроса не попадает в ответ ни в каком виде.

Разница между живостью и готовностью проявляется при остановке: сенсор
ещё жив (`/healthz` = 200), но уже не готов (`/readyz` = 503), и балансировщик
успевает увести трафик до закрытия слушателя.

## Конфигурация

Только переменные окружения. Неверное значение — отказ стартовать
с кодом возврата **2** (ошибка конфигурации) вместо **1** (ошибка работы).

| Переменная | По умолчанию | Описание |
|---|---|---|
| `SENSOR_UPSTREAM_URL` | нет, обязательна | адрес приложения: схема, хост и порт, например `http://app:3000` |
| `SENSOR_LISTEN_ADDR` | `:8080` | клиентский слушатель |
| `SENSOR_MAX_CONNS` | `1024` | предел одновременных соединений клиентов |
| `SENSOR_TRUSTED_PROXIES` | пусто — никому | адреса и сети доверенных прокси через запятую, например `10.0.0.5, 10.0.1.0/24` |
| `SENSOR_ADMIN_ADDR` | `127.0.0.1:9090` | адрес служебного слушателя |
| `SENSOR_SHUTDOWN_TIMEOUT` | `10s` | сколько ждать завершения запросов, максимум `60s` |
| `SENSOR_LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `SENSOR_EVENTS_FILE` | `/var/lib/sensor/events.jsonl` | файл событий; не открылся — сенсор не стартует |
| `SENSOR_POLICY_FILE` | пусто — без ловушек | файл политики; ошибка в нём не мешает запуску, остаётся последняя валидная |
| `SENSOR_POLICY_CACHE_FILE` | `/var/lib/sensor/policy.last-valid.json` | копия последней валидной политики |

По умолчанию служебный порт доступен **только с локальной машины**. Привязка
к другому адресу разрешена (в Kubernetes иначе нельзя), но сопровождается
предупреждением в логе — решение должно остаться видимым при разборе инцидента.

Уровень `debug` увеличивает количество служебных сообщений и никогда
не включает логирование тел запросов или заголовков авторизации.

## Запуск и проверка

```bash
make dev-demo                       # из корня: Juice Shop за сенсором на 127.0.0.1:8080
curl -s http://127.0.0.1:8080/ | grep -o '<title>[^<]*'   # OWASP Juice Shop

# или локально, к любому приложению на 127.0.0.1:3000:
make run-sensor SENSOR_UPSTREAM_URL=http://127.0.0.1:3000

curl -i http://127.0.0.1:9090/healthz    # 200 ok
curl -i http://127.0.0.1:9090/readyz     # 200 ready
curl -i -X POST http://127.0.0.1:9090/healthz   # 405
```

Остановка по `Ctrl+C` или `docker stop` — в логе появятся строки
«остановка: завершаем активные запросы» и «сенсор остановлен».

## Самопроверка

```bash
./bin/sensor healthcheck; echo "код: $?"    # 0 — готов, 1 — нет
```

Нужна для Docker: образ сенсора собран на distroless, в нём нет ни shell,
ни curl, поэтому опросить `/readyz` может только сам бинарник. Проверяет
готовность, а не живость, — в Docker статус здоровья используется, чтобы
зависимые сервисы ждали готовности. Возвращает только 0 или 1: код 2
в проверке здоровья Docker зарезервирован.

## Структура

```
cmd/sensor/        точка входа: два слушателя, обработка сигналов
internal/proxy/    клиентский слушатель: прокси, таймауты, предел соединений
internal/respond/  единственный способ ответить самому: нейтральный текст
internal/admin/    служебный HTTP-сервер и его таймауты
internal/config/   чтение и проверка переменных окружения
internal/healthcheck/  самопроверка для Docker: `sensor healthcheck`
internal/version/  версия сборки (только для логов, не для HTTP-ответов)
```

Пакеты лежат в `internal/` не по привычке: компилятор Go запрещает
импортировать их из других модулей, поэтому граница проведена заранее.
